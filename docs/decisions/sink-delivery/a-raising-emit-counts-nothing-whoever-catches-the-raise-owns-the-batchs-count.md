---
type: Decision
title: "A raising `emit` counts nothing; whoever catches the raise owns the batch's count"
description: "the worker, the orphan path (`orphan_lost`) and `MultiSink` are the only catchers, so at every shipped site (SPEC-058's five, SPEC-059 the rest) a per-event drop is counted and announced only by an `emit` that returns, through one `Deferral` (`sinks/_deferral.py`); counted inside a raising `emit` it is counted once per worker attempt. `MultiSink` therefore counts every child raise it swallows, a reporting child's too, reversing SPEC-036 FR-005's \"a reporting child reports itself\". (SPEC-058, SPEC-059)"
---

**A raising `emit` counts nothing; whoever catches the raise owns the batch's count** — the worker retries a raised batch whole, so a drop decided inside an `emit` that then raises is decided again on every attempt, and a sink that counted it as it decided counted one event once per attempt: `HTTPSink` read `dropped_oversized == 4` for one oversized event and `SQSSink` `dropped == 4` for one, while the worker's abandon line counted the batch again. A sweep of `sinks/` for the shape — a count reported through `losses().dropped`, then a raise in the same `emit` — found it in 18 sink classes at `324936e`, probed in five and read from code in thirteen. `_socket.py`'s docstring called it unfixable from inside a sink and said the fix "belongs one level up"; the deferral is sink-local, and **safe only because every catcher counts what it swallows**. There are exactly three catchers — `grep -rn '\.emit(' src/log_foundry` at `324936e` finds the worker's `_emit`, the orphan call in `api.py` and `MultiSink.emit` catching, and `TransformSink`, `FilteringSink` and `LogstashSink` only delegating — and the principle hands each its count: the worker's abandon line and `failed_batches` after its retries, `orphan_lost` for the one-event batch, and `MultiSink`'s own. A sink that counts inside a raising `emit` puts one event in two terms.

**One helper, written once.** `Deferral` (`sinks/_deferral.py`) holds one call's pending counts and diagnostic lines, is built as a `with` item inside `emit` and never stored — so the drain thread and any number of orphan callers never share pending state (SPEC-028) — and on a clean exit commits the counts under the owner's `_counter_lock`, **read at commit time** because a fork repair rebinds an owned instance's lock, then writes the lines outside the lock; on a raise it discards both. An AST check in `tests/test_deferral.py`, with a fixture corpus asserting its failure text and its silent cases, refuses a second accumulate-then-commit in each module of a roster of deferring sites: SPEC-058's five (`transform`, `filtering`, `multi`, `sqs`, `http`), which SPEC-059 widened to every shipped sink that decides a per-event drop. It follows `self.<method>()` calls within each class, so a counter bumped in a helper is seen, and names the stores kept immediate on purpose — `failed` counts, which are upper bounds (`MultiSink.failed` among them), `dropped_unadjudicated`, which feeds `failed`, and state that is not a count — in an allowlist it holds exact over the tree. ~~That allowlist also held `HTTPSink._drop_refused`'s `413` drop as an immediate store~~ — SPEC-059 FR-004 deferred it and it left the allowlist, which can no longer excuse a counter some `losses()` reports as `dropped`: the entry *A `dropped` count is written only by a `Deferral` commit* enforces that.

**`MultiSink` counts every raise it swallows, which reverses part of SPEC-036 FR-005.** It counts `len(batch)` for every child that raises while a sibling delivered — a reporting child's included — in a private absorbed count reported through `losses().failed`; when every child raises it re-raises the first and counts nothing; its public `failed` (child *calls*) and its per-raise `_diag.absorbed` line are unchanged. SPEC-036 had left a reporting child to report itself, trusting it to have counted before raising, and its AC-2 recorded the opposite choice as 6 lost events reading 12 against a real `SyslogSink` on a closed port. Any deferral breaks that trust, and three models at `69dac4f` showed where: an oversized event under `MultiSink(HTTPSink, MemorySink())` read `(dropped=1, failed=1)` before and `(0, 1)` under the deferral alone, in no term; a wrapper that turned "reporting" after its first counted failure left the next nine events counted nowhere, where the silent-child rule had counted twelve; and a wrapper over a failing `HTTPSink` already left all 30 events uncounted, with no spec applied. The maintainer chose the count (2026-10-19) and accepted its costs: `failed` over-counts when a reporting child had counted its own failures before raising, and it is a documented upper bound; ~~a not-yet-deferred sink's counted drop is in `dropped` and in `MultiSink`'s `failed` until the follow-up spec defers it~~ — SPEC-059 deferred the last shipped sink that counted before raising, so this remains a cost only for a third-party sink that does, and never twice in `dropped`; and a raising wrapper child is charged `len(batch)`, declined events included. The reversed passage is struck and marked in the decision *A sink that delivered nothing raises*, in the SPEC-036 spec and delivery doc, and in `multi.py`.

**Do NOT** count a per-event drop inside an `emit` that can still raise; do NOT have a sink un-count on a retry, since the worker hands back the original events and the sink cannot know it has seen them; do NOT restore the silent-child-only rule in `MultiSink`; do NOT recount `failed`, an upper bound by design. ~~The sinks that still count before raising — `SyslogSink` and `LogstashSink` through `_socket.py`, `MongoDBSink`, `KinesisSink`, `FirehoseSink`, `SNSSink`, `AzureEventHubsSink`, `KafkaSink`, `GooglePubSubSink` — and `HTTPSink._drop_refused`'s conditional path belong to a follow-up spec, each needing its own reading of when its `emit` raises.~~ — done by SPEC-059: each was read and defers, and the entry *A `dropped` count is written only by a `Deferral` commit* holds the rest of the tree to it. (SPEC-058 FR-002, FR-004, FR-005, FR-007)
