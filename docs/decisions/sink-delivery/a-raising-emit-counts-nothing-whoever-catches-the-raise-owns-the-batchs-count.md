type: Decision
title: "A raising `emit` counts nothing, nor does a `deliver`; whoever catches the raise or receives the failed run owns the batch's count"
description: "the worker, the orphan path (`orphan_lost`) and `MultiSink` catch a raising `emit`, so at every shipped site (SPEC-058's five, SPEC-059 the rest, SPEC-069 every sink's encode step) a per-event drop is counted and announced only by an `emit` that returns, through one `Deferral`; counted inside a raising `emit` it is counted once per worker attempt, and `MultiSink` counts every child raise it swallows (reversing SPEC-036 FR-005). A `deliver` counts nothing: the engine is the one writer of `SinkCounters`, a failed run commits no drop and its catcher (worker, orphan path, the adapter's raise) owns the batch, and the engine is a fourth catcher, for a `deliver` that raised. (SPEC-058, SPEC-059, SPEC-069, SPEC-072)"
---

**A `deliver` counts nothing either; whoever receives a failed run owns the batch's count** (SPEC-072, extending this decision to the optional `deliver(batch) -> Verdict`). A `deliver` reports and never counts: the delivery engine (`sinks/_engine.py`) is the one writer of a sink's `SinkCounters`, and it commits once, at the end of a run, through one `Deferral` built on those counters — so the lock is read at commit time, as at every deferring site, and `tests/test_deferral.py` lists the engine's `_run` among its deferring sites and refuses a store to `dropped_events` through any attribute chain. A run that **fails** (nothing accepted, something rejected, unresolved or in a raising round, nothing unknown) commits only `failed_events`, the upper bound, and **no `dropped_events`**: whoever receives the failure owns the batch — the worker's abandon or declined line and `failed_batches`, the orphan path's `orphan_lost`, or the inline adapter's `SinkDeliveryError` and whoever catches that. That is why a worker's retry of an adapter's raise cannot count a drop twice: pinned through a real `Worker` with `max_retries=1` and a third-party wrapper delegating to `inner.emit`, `[REJECTED, DROPPED]` ends with `dropped_events == 0` after both attempts and `failed_batches == 1` (`tests/test_delivery_paths.py`). A run that settles commits `dropped_events` as well, exactly, and `failed_events` takes each event at most once per run, never once per round. The engine is a **fourth catcher** beside the worker, the orphan path and `MultiSink`: it owns the count of a `deliver` that raised, counting that round's events in `failed_events` and announcing the exception's type once per run, after the commit. Shipped sinks keep their 1.x counters until they adopt `deliver` (SPEC-073 onward); none defines it at SPEC-072.

**A raising `emit` counts nothing; whoever catches the raise owns the batch's count** — the worker retries a raised batch whole, so a drop decided inside an `emit` that then raises is decided again on every attempt, and a sink that counted it as it decided counted one event once per attempt: `HTTPSink` read `dropped_oversized == 4` for one oversized event and `SQSSink` `dropped == 4` for one, while the worker's abandon line counted the batch again. A sweep of `sinks/` for the shape — a count reported through `losses().dropped`, then a raise in the same `emit` — found it in 18 sink classes at `324936e`, probed in five and read from code in thirteen. `_socket.py`'s docstring called it unfixable from inside a sink and said the fix "belongs one level up"; the deferral is sink-local, and **safe only because every catcher counts what it swallows**. There were exactly three catchers of a raising `emit` — `grep -rn '\.emit(' src/log_foundry` at `324936e` finds the worker's `_emit`, the orphan call in `api.py` and `MultiSink.emit` catching, and `TransformSink`, `FilteringSink` and `LogstashSink` only delegating — and the principle hands each its count: the worker's abandon line and `failed_batches` after its retries, `orphan_lost` for the one-event batch, and `MultiSink`'s own. A sink that counts inside a raising `emit` puts one event in two terms.

**One helper, written once.** `Deferral` (`sinks/_deferral.py`) holds one call's pending counts and diagnostic lines, is built as a `with` item inside `emit` and never stored — so the drain thread and any number of orphan callers never share pending state (SPEC-028) — and on a clean exit commits the counts under the owner's `_counter_lock`, **read at commit time** because a fork repair rebinds an owned instance's lock, then writes the lines outside the lock; on a raise it discards both. An AST check in `tests/test_deferral.py`, with a fixture corpus asserting its failure text and its silent cases, refuses a second accumulate-then-commit in each module of a roster of deferring sites: SPEC-058's five (`transform`, `filtering`, `multi`, `sqs`, `http`), which SPEC-059 widened to every shipped sink that decides a per-event drop, and SPEC-069 to every record-building sink's encode step (`sinks/_encode.encode_events`), adding `stdout`, `file`, `clickhouse`, `rabbitmq`, `sqlite`, `postgres` and `redis` to the roster and `_unencodable` to the counters an `emit` that returns commits. It follows `self.<method>()` calls within each class, so a counter bumped in a helper is seen, and names the stores kept immediate on purpose — `failed` counts, which are upper bounds (`MultiSink.failed` among them, and the `_failed` that `SQLiteSink` and the file sinks add before raising a driver error, SPEC-069 FR-004), `dropped_unadjudicated`, which feeds `failed`, and state that is not a count — in an allowlist it holds exact over the tree. ~~That allowlist also held `HTTPSink._drop_refused`'s `413` drop as an immediate store~~ — SPEC-059 FR-004 deferred it and it left the allowlist, which can no longer excuse a counter some `losses()` reports as `dropped`: the entry *A `dropped` count is written only by a `Deferral` commit* enforces that.

**`MultiSink` counts every raise it swallows, which reverses part of SPEC-036 FR-005.** It counts `len(batch)` for every child that raises while a sibling delivered — a reporting child's included — in a private absorbed count reported through `losses().failed`; when every child raises it re-raises the first and counts nothing; its public `failed` (child *calls*) and its per-raise `_diag.absorbed` line are unchanged. SPEC-036 had left a reporting child to report itself, trusting it to have counted before raising, and its AC-2 recorded the opposite choice as 6 lost events reading 12 against a real `SyslogSink` on a closed port. Any deferral breaks that trust, and three models at `69dac4f` showed where: an oversized event under `MultiSink(HTTPSink, MemorySink())` read `(dropped=1, failed=1)` before and `(0, 1)` under the deferral alone, in no term; a wrapper that turned "reporting" after its first counted failure left the next nine events counted nowhere, where the silent-child rule had counted twelve; and a wrapper over a failing `HTTPSink` already left all 30 events uncounted, with no spec applied. The maintainer chose the count (2026-10-19) and accepted its costs: `failed` over-counts when a reporting child had counted its own failures before raising, and it is a documented upper bound; ~~a not-yet-deferred sink's counted drop is in `dropped` and in `MultiSink`'s `failed` until the follow-up spec defers it~~ — SPEC-059 deferred the last shipped sink that counted before raising, so this remains a cost only for a third-party sink that does, and never twice in `dropped`; and a raising wrapper child is charged `len(batch)`, declined events included. The reversed passage is struck and marked in the decision *A sink that delivered nothing raises*, in the SPEC-036 spec and delivery doc, and in `multi.py`. **An engine child is such a reporting child** (SPEC-075 FR-004): `MultiSink` offers no `deliver` and calls each child's `emit`, and an engine child's `emit` is SPEC-072's adapter, which runs the child's engine inline and commits a failed run's events into the child's own `failed_events` before it raises `SinkDeliveryError`. So each such event is in `losses().failed` twice, once from the child and once from the fan-out's `_absorbed`, and once more in the worker's or the orphan path's term when every child raised. That extra count is invariant 2's recorded upper bound, kept because recounting it would reclassify a 1.x count, the same shape as 1.x `HTTPSink`'s `_abandon`. No event is counted twice in `dropped`: a failed child run commits no drop.

**Do NOT** count a per-event drop inside an `emit` that can still raise; do NOT have a sink un-count on a retry, since the worker hands back the original events and the sink cannot know it has seen them; do NOT restore the silent-child-only rule in `MultiSink`; do NOT recount `failed`, an upper bound by design. ~~The sinks that still count before raising — `SyslogSink` and `LogstashSink` through `_socket.py`, `MongoDBSink`, `KinesisSink`, `FirehoseSink`, `SNSSink`, `AzureEventHubsSink`, `KafkaSink`, `GooglePubSubSink` — and `HTTPSink._drop_refused`'s conditional path belong to a follow-up spec, each needing its own reading of when its `emit` raises.~~ — done by SPEC-059: each was read and defers, and the entry *A `dropped` count is written only by a `Deferral` commit* holds the rest of the tree to it. (SPEC-058 FR-002, FR-004, FR-005, FR-007)
