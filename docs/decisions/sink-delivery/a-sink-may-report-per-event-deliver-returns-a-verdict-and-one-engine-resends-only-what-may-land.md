**A sink may report per event: `deliver` returns a `Verdict`, and one engine resends only what may land** — under `emit` a sink answers "did the batch land, and is it safe to send again?" with one bit: raise, and the worker resends the **whole** batch, events already accepted included; return, and the sink must count its own loss. Three fixes (#276, #283, #286) answered that one question in three places, and twelve modules under `sinks/` each still assign their own `_BACKOFF_BASE = 0.1` (`grep -rln '^_BACKOFF_BASE' src/log_foundry`, at `fda134a` and at `d11e9e90`), deleted as each sink adopts the engine. SPEC-072 writes the answer once, as a contract and an engine, and changes no shipped sink: the seam is inert until the HTTP family adopts it (SPEC-073) and then the SDK and driver sinks (SPEC-074).

**The contract** (`sinks/verdict.py`, public, re-exported from `log_foundry`). `Outcome` has six members: `ACCEPTED`; `RETRYABLE`; `REJECTED` and `DROPPED`, the two forms of "rejected for good", which differ only in landing in `SinkLosses.failed` or `.dropped`, so **no count is reclassified**; `UNKNOWN`, an event that may have landed, which the engine must not mistake for `RETRYABLE`; and `SKIPPED`, a deliberate non-send the engine counts nowhere, which is **not** `ACCEPTED` for the run-failed rule, so a filter batch of one declined event and a rejected rest still fails. `Outcome` is **closed for 1.x**: it is an input a sink writes, not a result a caller reads, so invariant 10's "results grow by new values" does not reach it, and a new member would break a typed sink's exhaustive `match`. A `Verdict` is a frozen, keyword-only dataclass: `outcomes[i]` is the fate of `batch[i]`, plus an advisory `retry_after`; a malformed one is refused where it is built, routed on the real type and named by its stored name (invariant 13). `SinkCounters` is the counter object a sink owns as `log_foundry_counters` — on the sink, not the worker, so the counts survive a swap, a new worker and a fork — with names chosen unique in the tree (`dropped_events`, `failed_events`), since a plain `dropped` would meet `NullSink.dropped`, which no `losses()` reports.

**The probe** (`read_deliver`) reads the sink's **type**, never its dynamic attributes, and runs no `__getattr__`, property or metaclass hook: `deliver` must be a plain function in a class namespace; the `emit` ordinary lookup resolves must be a plain function on or below the class defining `deliver`, and no class may define `__getattribute__` as a plain function, so a subclass whose `emit` stamps or scrubs and calls `super().emit()`, an `emit` set on the instance, or a `__getattribute__` that substitutes one keeps running; and `log_foundry_counters` must be exactly a `SinkCounters`, so a sink with no counters keeps delivering through `emit` and the engine never counts somewhere dishonest. A class attribute `deliver = None` opts out of the offer. `deliver` is **not** on the `Sink` Protocol, which stays structural for the reason `losses()` is not on it.

**The engine** (`sinks/_engine.py`, private) is called first by the worker and the orphan path, which fall back to `emit` unchanged when nothing is offered, and inline by `emit_via_deliver` — public at `log_foundry` and `sinks.verdict` since the 1.2.0 follow-up fix, delegating to the engine (*The frozen surface is the import path, not just the class*) — which an engine sink makes its `emit` so a wrapper calling `inner.emit(batch)` sees the 1.x contract. It resends only the events still to send, within **the 1.x total of attempts** — `(s + 1) × (w + 1)` on the worker path, the sink's `max_retries` times the worker's, which is Andrew's decision of 2026-11-04 — and **the 1.x wait schedule**: `w + 1` cycles of `s + 1` attempts, the sinks' 0.1 s backoff restarting each cycle and the worker's `cycle_backoff` between cycles, a usable `retry_after` replacing the wait it falls on under the sink's `max_retry_after`, every wait cut short by the stop event and SPEC-062's prediction asked before every further round. It counts once, at the end of the run, through one `Deferral`, and since SPEC-073 commits the counts a sink registered on the run's context the same way, one `Deferral` per owner (*The HTTP family delivers in rounds on the engine, and a run context keeps its counters' units*); a run fails only when nothing was accepted, something ended rejected, unresolved or in a raising round, and nothing ended unknown (*A raising `emit` counts nothing, nor does a `deliver`* says who owns a failed run's count). An exception escaping `deliver` fails its round, since it is not a response (*A client exception costs its chunk*); an `UNKNOWN` outcome or an unreadable verdict settles, counted, since `deliver` returned and the events may have landed (*After a status line the status decides*). Either is resent only by a sink declaring `log_foundry_idempotent = True` — exactly `True` — and an exception only when the sink's `_retryable_error`, bound and asked through `is_retryable`, accepts it.

**Rejected.** A single retry layer, the sink's alone: a spec-review probe showed an `HTTPSink` answered nine `503`s then a `200`, delivered on the tenth request today, would be lost at the fourth, and `HTTPSink(max_retries=0)` under the default worker would fall from four tries to one. A single exponent across all fifteen worker-path rounds: `0.1 × 2**14` is about 27 minutes before the last. Reading `deliver` with ordinary attribute access: a proxy whose `__getattr__` delegates would offer its inner sink's `deliver` and be bypassed, filter and scrubber included, and third-party code would run in the probe. A whole-batch resend by the worker around an engine run: the budget already holds the worker's share, and the resend is the duplicate the contract exists to remove. Counters on the worker: they would not survive a swap back, a new worker or a fork.

**Do NOT** add an `Outcome` member, a per-event reason or `retry_after`, or an async `deliver` before 2.0; declare `deliver` on the `Sink` Protocol; call a sink's own `emit` from its `deliver`, or mutate the list `deliver` is handed; nest engine rounds (the worker never calls the adapter for a sink that offers `deliver`); or resend an `UNKNOWN` or unreadable outcome for a sink that has not declared itself idempotent. `MultiSink`, `KafkaSink` and `GooglePubSubSink` never get `deliver`. (SPEC-072 FR-001 to FR-006)

## History

### 2026-11-08

- **Applied** by SPEC-073, fence unchanged: the HTTP family is the first shipped family on the
  engine. The engine gains a family-neutral run context on which a sink keeps its 1.x counters'
  units, and writes no settled line of its own beside a sink line that will commit. A run started
  inside another run's round — a hook's `_send`, or a third-party `deliver` calling an engine
  sink's `emit` — is an independent run with its own context; the *Do NOT* on nesting rounds still
  means the worker never wraps an engine run in the adapter.
- **Refined (the 1.2.0 follow-up fix, no spec), at Andrew's direction.** `emit_via_deliver` is public, a fifth name beside the four this decision made public, at `log_foundry` and `sinks.verdict`; the engine it delegates to stays private. The reasoning is in *The frozen surface is the import path, not just the class*.

### 2026-11-07

- **Settled** (SPEC-072). The budget is Andrew's decision of 2026-11-04 and the wait schedule the orchestrator's, following it.
