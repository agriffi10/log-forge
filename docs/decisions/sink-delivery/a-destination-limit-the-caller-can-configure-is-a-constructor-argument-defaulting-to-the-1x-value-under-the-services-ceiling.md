---
type: Decision
title: "A destination limit the caller can configure is a constructor argument, defaulting to the 1.x value, under the service's ceiling"
description: "`SQSSink` and `SNSSink` take `max_message_bytes`, keyword-only and appended, defaulting to `None` so `MAX_BYTES` still sets the limit on an instance, a subclass or the class as in 1.x; a value outside 1,024 to 1,048,576 is refused at construction; each round holds every message and each request's sum to one limit capped at 1,048,576; the default stays 256 KiB, and the limit is never read from AWS. (SPEC-096)"
---

**The caller says the destination's limit; the sink holds it.** A queue's or topic's `MaximumMessageSize` is the destination's own setting, from 1,024 bytes to 1 MiB, and since SQS raised its ceiling on 2025-08-04 a queue's default is 1 MiB while a topic's is still 256 KiB. So `SQSSink` and `SNSSink` each take `max_message_bytes: int | None = None`, keyword-only and appended after their other parameters, so every 1.x call binds as before (invariant 10). The caller copies the destination's `MaximumMessageSize` into it, in bytes. It is a new argument, so under *A bad argument is floored if it works and refused if it is already broken; a new one is refused* it is refused, never floored: read through `_retry.exact_int` after every refusal the constructor made before, then refused with a `ValueError` outside 1,024 to 1,048,576, the range AWS gives `MaximumMessageSize` on a queue (`CreateQueue`) and on a topic (`SetTopicAttributes`), with the value rendered by `sanitize._int_text`, all before any client is built (invariant 13). The judgement is written in each `__init__`, not in a shared helper, so the numeric-door roster, which follows one call level within a module, sees both. The name is the house spelling of a byte bound, `max_<what>_bytes`, and not the vendor's, because *A sink's constructor keeps the vendor's own spelling* governs a keyword the sink forwards to its client, and this one is never forwarded.

**The default is `None`, not 262,144.** `MAX_BYTES` is a public class attribute that 1.x code sets three ways: on the instance after construction, by a subclass override, and by leaving the class's own value. The suite relies on the first. With an `int` default the constructor cannot tell a caller who left the limit alone from one who passed 256 KiB, and all three ways would stop working without a word. So `None` means the sink reads `MAX_BYTES` through `self` once per round, as 1.x did, and a value the caller passes wins over it whatever `MAX_BYTES` holds. `PostgresSink.connect_timeout` defaults to `None` for the same reason. `MAX_BYTES` keeps its value, 262,144, on both classes, and is neither validated nor removed: the frozen surface lets it grow and never shrink.

**One limit per round, capped at the service's ceiling.** Each round reads `max_message_bytes`, else `MAX_BYTES`, and then the smaller of that and 1,048,576 (`_SERVICE_MAX_BYTES` in each module), and every decision of the round uses that one value: the per-message drop, counted in `dropped_oversized` with the oversize line naming it, the bound on each request's sum, and the number the line names when the run settles. A judged argument never reaches the cap, since its range ends there; the cap binds only a `MAX_BYTES` raised past 1 MiB, which in 1.x sent requests the service refuses whole. With `MAX_BYTES` at 2 MiB, six 300 KiB events were all lost in one refused call, counted in `failed` (`docs/audits/2026-11-14-probes/sinks/spec096_destination_below_limit.py`, S5); under the cap each message over 1 MiB is dropped alone and requests are split under it. A request's sum is held to the message limit rather than to a separate request limit: SQS's batch total is 1 MiB whatever the queue's limit, so the message limit is never above it, holding the sum lower costs requests and never a refusal, and at the default it keeps every request byte for byte what 1.x sent, apart from each entry's `Id` (recorded at `10ba21ee`, `tests/data/spec096_requests_10ba21ee.json`). On SNS the sum is the topic's own rule ("The combined size of all messages in the batch ... must not exceed the topic's MaximumMessageSize", `PublishBatch`), and `SNSSink` now costs a request in UTF-8 bytes, the unit the topic counts, where it counted characters, which agreed only while `json.dumps` escaped every non-ASCII character.

**The default stays 256 KiB.** Asked on 2026-11-16 whether `SQSSink`'s default should stay 256 KiB or become 1 MiB, Andrew chose "Keep 256 KiB (Recommended)". The case for 1,048,576: it is the service's default for a queue created today, under it a caller who never reads the README lands an event between 256 KiB and 1 MiB that the 256 KiB default drops (S3 against S1), and it needs no configuration to use a limit AWS has offered since 2025-08-04. The case against, which carried: a 1.x caller sees nothing change; a caller whose queue still holds 262,144 keeps S1's outcome, one event dropped and counted with a line naming the limit, where a 1 MiB default gives S2's, in which a refusal of the whole call cost all ten events, nine of which fit, counted in `failed` under a line that names no size; and an event over 256 KiB takes many large fields, since assembly bounds each value at `max_value_bytes`. Whether real SQS refuses the call or names the entry, and how many queues still hold 262,144, are both unmeasured. On `SNSSink` the default was never in question: every topic defaults to 262,144, and a 1 MiB sink against such a topic lost two 200 KiB messages in one refused call (T1) where 256 KiB sent them in two calls (T2).

**Rejected:** reading the limit from AWS with `GetQueueAttributes` or `GetTopicAttributes`, which needs a permission a send-only role lacks, adds a network call to construction, and reads a value the owner can change at any time; an `int` default of 262,144, for the reason above; a default of 1 MiB, by Andrew's choice above; validating `MAX_BYTES`, or a `max_message_bytes` assigned after construction, which could be judged only on the drain thread (invariant 13), so only their upper side is held, by the cap.

**Do NOT** default either sink above the destination's own default without a decision that weighs the whole-call refusal; do NOT read a destination's limit over the network at construction; do NOT size a message or a request past the service's ceiling, whatever `MAX_BYTES` holds. `KinesisSink`'s record and request limits are a separate question, open in `docs/architecture.md` §12.
