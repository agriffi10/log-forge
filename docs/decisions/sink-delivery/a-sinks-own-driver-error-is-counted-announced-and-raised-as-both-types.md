---
type: Decision
title: "A sink's own driver error is counted, announced and raised as both types"
description: "When `SQLiteSink`'s insert raises `sqlite3.Error`, the sink adds the batch to a private `_failed` at once, writes one line naming the class and type, and raises an instance of both `SinkDeliveryError` and the driver's own class, built by `sinks/_driver_error.delivery_error`, which has no public name. The file sinks raise the same dual type, for any `Exception` their handle raises, only from an inline `emit` whose run landed nothing; on `deliver` they report each event by the bytes taken and count once per run. (SPEC-069, SPEC-082)"
---

**Counted, announced, then raised.** `SQLiteSink.emit` let `sqlite3.Error` escape and the two file sinks let `OSError` escape (`OSError(28)` from a full disk was measured), with no `losses()` to report it and no line of their own; only the worker's abandon line, after its retries, said anything. SPEC-069 made each do what every counting sink does, and `SQLiteSink` still does it this way: under its own `_counter_lock`, never the emit lock, so a `losses()` poll does not wait behind a write (SPEC-028 FR-003), it adds `len(batch)` to a private `_failed`, reported as `losses().failed`; it writes one `_diag.lost` line, `<Sink>, <Type>`; and it raises. The count lands before the raise and again on each worker retry of the batch — the recorded upper bound of invariant 2 — and `tests/test_deferral.py`'s `IMMEDIATE` names the store. An event the same call dropped as unencodable is discarded with the raise, as any per-event drop is, and so sits in the `len(batch)` the call counted. A closed sink still raises a plain `SinkDeliveryError` and counts nothing.

**The file sinks count through the engine since SPEC-082.** They hold no `_failed`: `FileSink` and `RotatingFileSink` offer `deliver`, the engine counts each event that did not land once per run in their `SinkCounters`, and a failed run counts its unencodable events with the rest (`When.FAILED`), which keeps the `len(batch)` above. Their one line is the engine sinks' `raised_line`, `<Sink>, N attempt(s), <Type>`, followed by `errno=N` when the exception carries one. The worker calls their `deliver` and never resends a batch whole. What stays of this decision for them is the raise: an inline `emit` whose run landed nothing raises the dual type, registered by the round through `RunContext.raise_on_failure` and raised by the adapter, and it is built for any `Exception` the handle raised, a `ValueError` as much as an `OSError`. A run that landed anything, or cut a line, returns.

**Raised as both types, so no `except` clause changes.** Callers wrote `except sqlite3.Error`, `except OSError` and `except PermissionError` around these sinks; the library's word for "this sink delivered none of the batch" is `SinkDeliveryError`. `delivery_error` derives, once per original class and cached, a class whose bases are `SinkDeliveryError` and the original's own class, and builds the instance from the original's `args`. It copies only the attributes the original actually set that `args` does not carry — `filename` and `filename2` when not `None`, and the `sqlite_errorcode` and `sqlite_errorname` the driver stores on the instance — because copying an unset one corrupts `str()` (`filename2=None` renders `... 'f' -> None`; a plain `OSError("plain")` renders `[Errno None] None: None -> None`). The class keeps the original's `__name__`, `__module__` and `__qualname__`, so the worker's abandon line reads as it did in 1.1.0; the original is the `__cause__`; and `__reduce__` rebuilds the original class from its `args` and copied attributes, so a pickled instance unpickles as the driver's own exception — without it every instance fails to pickle, since the class is built at run time. If the class cannot be built (a constructor that rejects its own `args`, bases that cannot share a layout), the sink raises the original unchanged, still counted and announced, because the library never fails the caller on its own fault (invariant 1).

**Not public surface.** A frozen name is inherited and kept for all of `1.x` (*A protocol that is exported is a protocol that will be inherited*), and nothing needs one: `isinstance(exc, SinkDeliveryError)` and the driver's own `except` already match. The derived class is in no `__all__` and has no documented import path; `SinkDeliveryError`'s docstring says a sink may raise such a subclass. Rejected: a static subclass per driver type, which cannot cover a type the driver adds and is not the driver's class for an `except` written against a narrower one. Accepted: this is dynamic inheritance and module state, which the Python rulebook asks to avoid (§15, §13), and `_driver_error.py`'s docstring says so.

**A partial write's duplicates were an accepted edge for 1.2.0, and SPEC-082 closed them for the file sinks.** In 1.2.0 a `FileSink` or `RotatingFileSink` write that failed partway left the earlier lines of the batch on disk, the sink raised, and the worker's retry wrote the whole batch again; a `StdoutSink` or `StderrSink` stream that raises partway still does the same, and stays an accepted edge until SPEC-084. Measured at `a8e91fac` with `RLIMIT_FSIZE` capping the file partway through a 200-event batch of about 24 KB, at caps from 5,000 to 20,000 bytes, and lifted before the second `emit`: 69 to 200 of the 200 events landed twice. At most caps no line was torn, because CPython's `BufferedWriter` kept the unwritten tail in its buffer and the next flush finished it; at a cap of 10,500 bytes it discarded the tail instead, so the 60 bytes of one line already on disk were glued to the retry's first line, leaving one unparseable line. A fault that persists fails the retry too and duplicates nothing, so the duplicates needed the fault to clear between attempts. Two remedies were rejected and stay rejected. Truncating the file back to where the batch began would delete the lines a forked child appended to the same file in between (invariant 12). Flushing per line and reporting a partial write instead of raising loses the unwritten rest, which is never retried even when the disk recovers. The closure is the file sinks on `deliver`: each event is reported by the bytes the write calls returned and only what did not land is resent, which is its own decision, [A file write reports each event by the bytes taken, and a torn line is finished once](a-file-write-reports-each-event-by-the-bytes-taken-and-a-torn-line-is-finished-once.md). The same six caps now leave each of the 200 events on disk once (`tests/test_file_sink_partial_write.py`).

**Do NOT** truncate a file back to where a batch began to undo a partial write; do NOT export the derived class; do NOT copy an attribute the original did not set; do NOT take the emit lock to count; do NOT give the file sinks back a counter of their own beside the engine's. (SPEC-069 FR-004, SPEC-082)
