---
type: Decision
title: "A file write reports each event by the bytes taken, and a torn line is finished once"
description: "`FileSink` and `RotatingFileSink` write through an unbuffered handle and call an event `ACCEPTED` only when the write calls took its whole line. The unwritten rest of a line cut partway is the sink's tail, written before any other byte reaches the file; which occurrence was torn is the run's, kept in its notes. A torn event the run will not offer again is `UNKNOWN`, so no catcher resends the batch whole. Do NOT truncate, flush per line, keep run state on the sink, or add an inline retry. (SPEC-082)"
---

**Each event is reported by the bytes the operating system took.** In 1.2.0 a file sink whose write failed partway raised, the worker resent the whole batch, and every line that had landed landed again: with `RLIMIT_FSIZE` capping the file partway through a 200-event batch and lifted before the retry, 69 to 200 of the 200 events were on disk twice, and at one cap a line was cut and the retry's first line was glued to it. The buffered text stream could not say what had landed, since after a failure it sometimes kept the unwritten bytes and sometimes threw them away. So both sinks write through `open(path, "ab", buffering=0)`, add up what each write call returned, and offer `deliver`: an event whose line's last byte was taken is `ACCEPTED`, and the engine resends only the rest. `RotatingFileSink` writes the lines staged ahead of a rotation, every write call returned, before the rotation is tried, and `_size` grows by the bytes taken.

**The tail belongs to the sink; the torn occurrence belongs to the run.** A write that stops inside a line leaves that line's prefix on disk, and anything appended after it would join it into one line that does not parse. The unwritten remainder, the tail, is therefore kept on the sink, and every write section, and the release a `close()` runs, writes it before any other byte; a rotation never starts while one is pending, and a forked child drops the one it inherited, since the parent finishes it. Which event was torn is a fact about one run, so it lives in that run's notes with the tail record cut from it, and the run finds the occurrence again as the first offered event that is that object. It compares the record by identity to the sink's: still that record, the round writes the tail and not the line; any other, another section finished it and the event is `ACCEPTED` with nothing written. A slot on the sink was tried first and duplicated a line when another section finished the tail between two rounds.

**A torn event the run will not offer again is `UNKNOWN`.** That is a tear on the run's last round, under an error the predicate does not retry, and in a direct `deliver` outside any run, whose notes end with the call. Its prefix is on disk and the next section writes its tail, so it may land. Reported `RETRYABLE` or `REJECTED` it could fail a run in which nothing else landed, and every catcher that resends whole (`MultiSink` through the worker's 1.x loop, a wrapper calling `emit`, a caller's own `except OSError`) would write the line again after its tail. As `UNKNOWN` the run settles and `emit` returns. The cost is stated: on a one-round run, an inline `emit` or a `MultiSink` child, the events after a failure are counted in `failed` and not written, where 1.x could deliver them with duplicates. The torn event is counted once though it may land, the upper bound invariant 2 records, and it is announced on a line of its own that ends `; outcome unknown; they may have landed`, the HTTP sinks' words for an event they cannot adjudicate, so the line does not call lost an event the next write finishes (invariant 11).

**The count a write call returns is stored where no signal handler can run first.** A blocking write to a pipe is cut short by a signal and returns a partial count, and a handler's exception is raised at the next bytecode boundary, which with `wrote = stream.write(chunk)` falls before the assignment: the count was lost in 40 of 40 interrupts. `counts.extend(map(stream.write, (chunk,)))` appends inside C, and was exact in 40 of 40 on Python 3.12 and 3.13. One idempotent step then brings the tail, `_size` and the owed byte order mark to the stored counts, on the normal path and again when an `Exception` or a `BaseException` passes through, and the round settles any `Exception` from the bytes taken before it, not only an `OSError`. This hardens a pipe beyond 1.x and makes a regular file's bookkeeping exact; it repairs no regression. An offset-based guard was rejected: a pipe has no offset, and a descriptor's own offset is wrong once another descriptor has appended.

**Rejected.** Truncating the file back to where the batch began deletes the lines a forked child appended in between (invariant 12). Flushing per line and reporting instead of raising loses the unwritten rest, which is never resent. A `max_retries` on the file sinks, or a second inline round, would resend inside `emit`, which 1.x never did and `MultiSink` cannot bound. Two residues stay: a run the worker declines, or a sink closed during a backoff, after a round that reported the torn event `RETRYABLE` can count that event in `failed_batches` as well as `failed`, with nothing written twice; and an exception a signal handler raises after the write section has finished and before `emit` returns reaches a retrying caller with the batch on disk, as in 1.x.

**Do NOT** truncate a file to undo a partial write; do NOT flush per line; do NOT keep which event was torn on the sink; do NOT report a torn event `RETRYABLE` on a run's last round or outside an engine run; do NOT add a `max_retries` or an inline retry to the file sinks; do NOT store a write call's count with a Python-level assignment; do NOT read an offset or a file size to learn what was taken. (SPEC-082)
