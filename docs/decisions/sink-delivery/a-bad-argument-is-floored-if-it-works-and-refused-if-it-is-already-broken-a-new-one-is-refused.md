---
type: Decision
title: "A bad argument is floored if it works and refused if it is already broken; a new one is refused"
description: "an unusable timeout, a CRLF header or token, a non-`http` URL, a non-positive chunk size or interval, a bad DSN, an argument the chosen backend cannot use and a build option beside an injected client raise at construction; `max_bytes<0`, `overflow_timeout=inf` and the `usable_timeout` callers floor, as those deliver. A value outside the declared type of a floored or range-checked `int` or a stored callable is a named `TypeError` before anything is built, read or not, never floored; an `int` subclass (`bool` too) is floor-side, kept as the builtin. `flush()`/`shutdown()` read `inf` as unbounded and refuse `nan`. An HTTP sink URL with an `@` is refused unquoted though it delivered; its other refusals quote only scheme and host. (SPEC-049, SPEC-065, SPEC-066, SPEC-071)"
---

**A bad argument is floored if it works and refused if it is already broken; a new one is refused** — one rule for every degenerate constructor argument in the sink family, stated once (SPEC-049 FR-001) and applied across four FRs. The library already *floored* `max_retries` at zero, `max_batch_count` at one, libpq's `connect_timeout` at two, and `KafkaSink`/`NATSSink`'s timeouts back to their module defaults through `_retry.usable_timeout`; every one of those lands on a configuration that delivers, so flooring is a no-op for a sane caller and a silent rescue for the rest. Every *refusal* SPEC-049 added is on a value that, measured at `212fd16`, either destroyed data silently or raised an uncounted exception on every batch for the life of the process: `HTTPSink(timeout=-1)` raised a raw `ValueError` out of every `emit`; `ClickHouseSink(chunk_size=-5)` returned normally having inserted nothing; `RotatingFileSink(interval=0)` left two of fifteen lines on disk; CR/LF in a header or bearer token, a `file://` URL, a Sentry DSN with no host, a whitespace `app_name` or index name, and an argument the selected backend cannot consume (`LogstashSink(url=…, host=…)` and the reverse, `NATSSink(client=X, servers=…)`, a non-positive `max_reconnect_attempts`) all fail later or never. Those raise `ValueError` at the constructor, naming the argument and — unless it may hold a credential, below — the value, through `_retry.require_timeout`/`require_positive` — raising siblings of `usable_timeout` sharing its `NaN`-safe `not (0 < v < inf)` test. **A value that may hold a credential is not quoted:** an HTTP sink URL carrying a user or password before its host is refused naming the argument alone, and refused although it delivered through an HTTP proxy, because `urllib` sends userinfo as part of the host name — in cleartext to the proxy — and never as an `Authorization` header, so through the default opener it authenticated nowhere and leaked everywhere it went (an injected `opener=` receives `full_url`, userinfo included, and does what it likes with it). A literal `@` anywhere else in an HTTP sink URL is refused too, in fixed text naming the argument and the `%40` remedy, although it delivered as written, because a password holding `#`, `?` or `/` ends the host before its `@` — `http://elastic:12#ss@es:9200/x` constructed and sent every request to host `elastic:12`; `SentrySink` is exempt, since an `@` in a DSN's path prefix is a path the SDK posts to. Every other refusal of an HTTP sink URL quotes only its scheme and host, because a path, query or fragment is where a credential sits (`?api_key=`, `#access_token=`): when anything follows the host it names the parser's error by its type alone and chains nothing, unless the URL holds an `@` in any form (`%40`, fullwidth), or its host a `/`, `?` or `#` in a form other than ASCII (fullwidth, as CJK input methods type them, or percent-encoded), when it is not quoted at all; when nothing follows it quotes the URL whole with the parser's reason chained; and a URL that does not start with `scheme://` is not quoted at all. `DatadogSink`'s `site` and `HoneycombSink`'s `dataset` are not quoted when they hold an `@`, `/`, `?` or `#`, in any of those forms. No `SentrySink` DSN refusal prints the DSN or chains an error that quotes it, because its userinfo is the public key, and a DSN on port `0` is refused, since the SDK posts to that port and no request there delivers. **The floor side is protected, not merely tolerated:** `RotatingFileSink(max_bytes=-1)` and `(backup_count=-1)` behave identically to the documented `0` and are floored to it, and `GooglePubSubSink(overflow_timeout=inf)` *delivers* against a healthy client, so it became the third `usable_timeout` caller rather than a refusal — refusing `inf` there while flooring it for Kafka would have been two rules for one value; the spec's first draft refused both and its reviews caught each. **A newly added argument is refused** (the FR-005 driver bounds: `MongoDBSink`'s `socket_timeout` and `server_selection_timeout`, `RabbitMQSink`'s `blocked_connection_timeout`, `socket_timeout` and `stack_timeout`, `ClickHouseSink`'s `send_receive_timeout`) because it has no working configuration to protect, and is refused beside an injected client, which cannot consume it (SPEC-043). **Precedence for a bound the caller may also have written into a URI:** the library default applies only when the URI names nothing; an explicit keyword overrides the URI; the default never does — pika's model, and deliberately not `PostgresSink`'s DSN override, because pika and pymongo let the two be told apart where libpq did not. **Found by sweeping, not by reading:** the system-frame diff review enumerated every numeric constructor argument in `sinks/` and ran each degenerate value, and the rule had been left unapplied on `PostgresSink`'s chunk loop, `SocketTransport`'s `port` and `max_datagram_bytes`, `HTTPSink`'s `max_batch_bytes` (a floor at `1` that delivered nothing — a floor must land on a value that *delivers*, or it is a refusal wearing a floor's clothes) and `body_format`, and three `maxlen`s; a spec that applies a rule to the sites it noticed owes a sweep of the sites it did not. **Refined by SPEC-065: the test is asked of values of the declared type.** "Does it work" decides floor-or-refuse only for a value the signature admits. A value outside it is refused at the door — by `configure()`, `require_positive` and `require_timeout` — with a `TypeError` naming the argument and the type, *even where it happened to work*, and is never floored: `configure(max_keys=2.5)` kept three of four list entries, `max_value_bytes=2.5` emptied `fields`, and `inf` left strings unbounded, measured at `71e42dd`, but a float ceiling is outside `int | None`, so it was already a `mypy` error and no type-checked caller breaks (invariant 10), and `math.ceil` would hide the mistake behind a ceiling the caller never chose. A `bool` or other `int` subclass *is* of the declared type, so it is floor-side — accepted and normalised to the exact builtin with `int.__index__` (`float.__float__` for a float duration), which ignores a subclass's comparisons and conversions, so one whose `__lt__` or `__le__` lies about a zero is judged by the number it holds and `get_config().max_keys` reports `1` for `True`. That holds at `configure()` (`config._require_positive`, the four payload ceilings) and in `_retry.require_positive`, `require_timeout` and `usable_timeout`, which now return the exact builtin and whose two discarding callers (`chunk_list`, the rotation interval) use the return — the same move `_require_text` makes with `str.__str__` (SPEC-055). **Do NOT** convert the floor-side callers into refusals for consistency's sake — that is a breaking change at 1.0 for a configuration that works (floor-side means a value *of the declared type*; a float ceiling was never one), and the pins in `tests/test_sink_retry.py` and `tests/test_sinks_pubsub.py` exist to fail such a change; do NOT floor a new argument, which would hide the caller's mistake behind a default they never chose; do NOT validate a value the selected backend never reads (`SentrySink(backend="sdk")` never parses the DSN) — refusing it would invent a failure rather than report one. **Applied by SPEC-066 to the doors SPEC-065 left.** Every `int`-annotated constructor argument that the constructor itself floors with `max` or range-checks — `max_retries` on twelve sink constructors and `Worker.__init__`, `RotatingFileSink`'s `max_bytes` and `backup_count`, `HTTPSink`'s `max_batch_count`, `PostgresSink`'s `connect_timeout`, `GooglePubSubSink`'s `max_pending`, `SocketTransport`'s `port` and `NATSSink`'s `max_reconnect_attempts` — goes through `_retry.exact_int` or `floor_count`, which refuse a non-`int` with a `TypeError` naming the class, argument and type and floor the exact `int`; a float there constructed and then raised out of `range()` on every batch (`HTTPSink(max_retries=2.5)`), killed a sink on its first rollover (`backup_count=2.5`), or passed a range check and raised from every send (`port=2.5`). The judgement precedes any client, connection or file the constructor builds, so a refusal leaves nothing behind. **The reach of a type refusal:** it is asked of every `int` argument the constructor's own body floors or range-checks, whether or not the selected branch reads it — `PostgresSink(connection=c, connect_timeout=2.5)` is refused — because the clause above is about *value* validation, such as parsing a DSN that `backend="sdk"` never uses, not about a type the signature already rules out. A delegating sink refuses through its delegate only, so `SentrySink(backend="sdk", max_retries=2.5)`, which builds no delegate, stays accepted. `GooglePubSubSink(max_pending=inf)`, which meant no bound, is refused with the other floats; a large `int` asks for that. The one `float` door its second diff review found unjudged for type, `HTTPSink.max_retry_after`, refuses a value that is not an `int` or `float` through `_retry.exact_seconds` — a `str` or `None` constructed and raised out of `emit` on the first `Retry-After` — while its value stays floor-side: `clamp_server_delay` answers a zero, negative or `nan` ceiling with exponential backoff, as it did. **The two public waits are the owner's call, not this rule's**, because `inf` and `nan` are of their declared `float | None`: `inf` or any value above `threading.TIMEOUT_MAX` is the unbounded wait `None` is, `nan` is a `ValueError`, a value outside `int | float | None` a `TypeError`, a `bool` or number subclass the exact builtin, and a value below `-threading.TIMEOUT_MAX` is `0.0`, all at entry through `_retry.wait_budget` before anything is claimed or counted. `tests/test_numeric_door_roster.py` derives the `int` doors from the AST and fails naming any left unjudged, since the defect was found three times by a sweep and never by a test. **Applied by SPEC-071 to the options a sink builds its client from.** "An argument the chosen backend cannot use" covered the bounds five constructors refused by hand beside an injected client, while the options the client is *built from* were ignored there silently — `RedisListSink(client=c, url=…)`, `AzureEventHubsSink(producer=p, connection_str=…)` and seven more constructed and never read the argument, which is invariant 13's "silently ignored because another was given". Every such option whose default is `None` is now refused through `sinks/_args.refuse_with_injected`, one copy of the check and one message (`<Sink> cannot apply <names, sorted> to an injected <kind>; pass them where the <kind> is built, or drop <kind>=`), tested with `is not None`, never truthiness, so `producer_config={}` is still refused. `PostgresSink.connect_timeout` defaults to `None`, meaning 5, so a value the caller gave can be told from one left out; the type only widens. Its type judgement (`floor_count`) still runs before the refusal, so `connect_timeout=2.5` beside `connection=` is SPEC-066's `TypeError`; `ClickHouseSink` and `RabbitMQSink` refuse the combination before judging `max_retries`, as their earlier bound refusals did. `tests/test_injected_client_roster.py` derives each constructor's build options from its AST rather than from the message, so a sink that *ignores* an option is reported, not only one that lost a copy of the check, and it fails closed on a build it cannot locate. **The one recorded exception is `SQLiteSink.database`:** it is required and positional and documented as ignored beside an injected connection, so refusing it would break every 1.x caller that injects one; it is pinned by name, so a second such argument is noticed, and invariant 13 records it. **The reach of a type refusal extends to every callable argument a constructor stores** (SPEC-071 FR-005), whether or not the selected branch reads it: `SQSSink`'s `message_group_id` and `message_deduplication_id`, `FilteringSink.predicate`, `HTTPSink.opener`, `CallbackSink`'s `fn` and `on_close`, and `TransformSink.fn` go through `_args.require_callable`, which refuses a non-callable with a `TypeError` naming the owner, the argument and the type. `SQSSink(message_group_id=5)` is refused on a standard queue too, which never reads either id and delivered — the clause against validating an unread value is about a *value*, and a non-callable where a callable is declared is outside the type, already a `mypy` error, so no type-checked caller breaks: SPEC-065's reasoning for the ceilings. A delegating sink still refuses through its delegate only: `SentrySink(dsn, opener=5)` is refused by the `HTTPSink` it builds and names it, and `SentrySink(backend="sdk", opener=…)`, which builds none, keeps its `ValueError`. (SPEC-049, SPEC-065, SPEC-066, SPEC-071)

## History

### 2026-11-07

- **Refined (SPEC-071).** Two extensions, both recorded in the fence. An option a sink builds its client from, passed beside an injected client, producer or connection, is refused at construction (nine options across eight sinks that ignored it silently), through one helper whose guard derives the options from the build path; `SQLiteSink.database` is the recorded exception, because refusing a required argument would break every caller that injects a connection. And the reach of a type refusal extends from floored or range-checked `int`s to every callable argument a constructor stores, whether or not the selected branch reads it — so `SQSSink` refuses a non-callable id source on a standard queue — for SPEC-065's reason: the value is outside the declared type, so no type-checked caller breaks. The "do NOT validate a value the selected backend never reads" clause is unchanged; it is about a value, not a type.

### 2026-11-04

- **Refined (sink-URL gaps, no spec).** Three more departures from the rule as written, Andrew's call. "Floored if it works" would have kept a literal `@` outside an HTTP sink URL's host, which delivered as written (`http://h/a@b`, `HoneycombSink`'s dataset `d@x`); it is refused instead, with `%40` as the remedy, because the same shape is a password holding `#`, `?` or `/` that ended the host early and sent every request to a host the caller never named, and the two cannot be told apart. `SentrySink` is exempt, since the SDK posts to an `@` in a DSN's path prefix as written. A refusal named "the argument and the value"; a refused HTTP sink URL is now quoted only as far as its scheme and host, since its path, query and fragment are where a credential sits. And a Sentry DSN on port `0`, which under `backend="http"` delivered to the default port because `0` was dropped as falsy, and never delivered under the SDK, which keeps it, is refused rather than kept.
- **Refined (SPEC-066).** The `max(x, 0)` floors SPEC-065 left — `max_retries`, `backup_count` and the other `int` floors — and the two comparison-only `int` doors, `SocketTransport.port` and `NATSSink.max_reconnect_attempts`, now refuse a non-`int` through `_retry.exact_int`/`floor_count` before any client is built, and floor or range-check the exact `int`; the fence no longer says they are not yet held to the rule. The reach of a type refusal is written down, so the "do NOT validate a value the selected backend never reads" clause is not read as protecting `PostgresSink(connection=c, connect_timeout=2.5)`. The owner's verdict for `flush()`/`shutdown()` timeouts (2026-11-03) is recorded beside it: `inf` waits unbounded, `nan` and a non-number are refused at entry. Its second diff review added `HTTPSink.max_retry_after`'s type refusal, its value left floor-side.
- **Refined (userinfo fix, no spec).** Two departures from the rule as written, both deliberate. A refusal named "the argument and the value"; a URL carrying a user or password is refused naming the argument only, since its value is the credential, any other refusal of a URL or Datadog `site` holding an `@` stopped quoting it, and `SentrySink`'s DSN refusals stopped printing the DSN, for the same reason. And "floored if it works" would have kept such a URL, which delivered through an HTTP proxy that forwards by the absolute URI to an endpoint needing no auth — measured with a local fake proxy, which received the user and password in the request line and `Host` header; it is refused instead, because it never authenticated and it put the password in front of every proxy and resolver on the path. Andrew's call.

### 2026-11-03

- **Refined (SPEC-065).** The floor-or-refuse test is asked of values of the declared type. `configure()` accepted a float payload ceiling (`2.5`, `inf`, `nan`) and stored it as given, and the sink validators tested the caller's own object, so an `int` subclass whose comparison lied passed holding zero. A value outside the declared type is now refused at the door with a named `TypeError` and never floored (`usable_timeout`, a floor-side helper, still lets a non-number raise the comparison's own `TypeError`), which breaks no type-checked caller; an `int` subclass, `bool` included, is floor-side and stored or returned as the exact builtin. Written here because the earlier "do NOT convert the floor-side callers" clause could have been read to protect `max_keys=2.5`, which it does not.

### 2026-09-05
