type: Decision
title: "A sink round resends only what failed, and an SQS FIFO group keeps its order"
description: "the SDK, driver and socket sinks make one attempt per chunk, message or frame per round and the delivery engine resends only what may land within 1.x's total budget, so a failed chunk is resent after its round's later ones; only an SQS or SNS FIFO message group holds a later message back, per chunk at send time, for its predecessor's `max_retries + 1` sends, across calls and not inside one, and in the run's last round holds nothing. (SPEC-074, SPEC-100)"
---

**A sink round resends only what failed, and an SQS FIFO group keeps its order** — `SQSSink`, `SNSSink`, `KinesisSink`, `FirehoseSink`, `ClickHouseSink`, `MongoDBSink`, `PostgresSink`, both Redis sinks, `RabbitMQSink`, `AzureEventHubsSink`, `NATSSink` and `SocketTransport` each make **one attempt per chunk (message, frame, pack) per round** and report every event's fate; the delivery engine resends only the `RETRYABLE` ones, waiting the 1.x backoff between rounds with no lock held, within `(s + 1) x (w + 1)` rounds on the worker path — 1.x's total — and `s + 1` through the inline adapter. A chunk that failed is resent **after** the later chunks of its round, where 1.x's loop retried it before moving on, so one entry that keeps failing costs only itself (measured by the spec reviewer: 100 SQS events with one entry failing every attempt landed 99 under 1.x and would have landed 36 had a round stopped at its first retryable chunk).

**The one exception is a FIFO message group, on an SQS FIFO queue and, since SPEC-100, an SNS FIFO topic**, whose order each service documents as a guarantee and 1.x's SQS loop kept for as long as it retried a chunk. The hold is decided per chunk at send time, from the run's replies so far, by one function both FIFO sinks call (`sinks/_fifo.hold`, with `_fifo.block`, both called from the one round loop the two sinks share, `_fifo.send_round`, which also holds the last-round gate and the done marks; `sqs._hold` and `sqs._block` are bound to them): an event is held (`RETRYABLE`, not sent) only when an earlier event of its group was sent in an earlier round or an earlier chunk of this round and has neither landed nor used up its `max_retries + 1` sends, this round's send counted, or when that earlier event is itself held. Same-group events never sent travel together in one chunk, as 1.x sent them, so a healthy one-group batch is one call. **In the run's last round nothing is held** (`RunContext.last`): a held event is sent right after its predecessor's final send, chunks going out in batch order, as 1.x sent it after giving up on that predecessor, so the last round lets no message land ahead of an earlier one of its group (past the predecessor's `max_retries + 1` sends, an earlier round may, as above). Only a run that ends before its budget — the worker declining a further round — leaves a held event unsent, and it is counted `failed` with the line `<Sink>, <n> attempt(s), held behind an earlier message of its FIFO group`, naming `SQSSink` or `SNSSink`. A detached `deliver()` round is not the last either, since only its caller knows whether another follows; it keeps no send counts across calls, so a hold there never releases over the caller's own loop and the held event is announced on every call. That is the documented contract, not a defect: a direct `deliver()` outside a run is a single detached round, a caller looping it sees the held or giving-up line on each call, and `emit_via_deliver` is the retrying path (SPEC-075, the base `Sink.deliver` docstring; no behaviour change). **What the hold guarantees, as SPEC-100 measured it** (`docs/audits/2026-11-14-probes/sinks/spec100_ordering.py`, identical on the two sinks): it keeps a later *call* from overtaking an earlier message of its group, for that message's `max_retries + 1` sends — twelve events of one group need two calls, and when the first call's first entry failed once the second call's two events landed after it, where with the hold off they landed first (case D). It does not order the entries of one call: a fake service that accepted the later entries of the call in which the first failed landed them before it, with the hold and without (cases A and D), and SNS documents ordering within a group and within a batch without saying what it does with a batch's later entries when an earlier one fails. Its cost: when a whole first call failed, the hold resent one message per group per round until the last round, four calls instead of two (case C), each after a backoff wait `shutdown()` cuts short. Rejected: holding the group for the worker's whole budget (it trades delivery for an order the consumer can rebuild from `timestamp`), holding one event per group per round (a healthy five-event group then took four rounds and lost the fifth — plan review B1), and counting an event still held when the budget runs out as `failed` unsent (SPEC-074 shipped it first; 1.x delivered that event, so it was a compatibility break — Q4).

**Do NOT** make a round stop at its first retryable chunk; do NOT let any sink but `SQSSink` and `SNSSink` FIFO hold an event back for order (Kinesis `PutRecords` promises none across records), nor give either a hold of its own outside `sinks/_fifo.py`; do NOT hold a lock across the engine's wait.

## History

### 2026-11-24

- **Refined** by SPEC-100 FR-004, Andrew's call of 2026-11-17 ("Hold, as SQS (Recommended)"; the alternative was no hold, leaving a FIFO topic's order to the service and the order of calls): a FIFO `SNSSink` holds a group's later message exactly as `SQSSink` does, through `sinks/_fifo.hold` and `block`, so the "do NOT" names both FIFO sinks. SPEC-100's diff review found the round loop around them copied into each sink, with a mutant of the SNS copy's last-round gate surviving the suite; the loop is now `_fifo.send_round`, one copy both sinks call, and the engine suite's FIFO tests run on both. The guarantee is now stated as SPEC-100 measured it, across calls and not inside one.

### 2026-11-09

- **Documented** by SPEC-075 (SPEC-074 handover item 1a, Andrew's call): a direct `deliver()` outside a run is a single detached round, so a looped caller sees the held or giving-up line each call and a FIFO hold is not released; `emit_via_deliver` is the retrying path. No behaviour change.
- **Settled** by SPEC-074 FR-002 to FR-005.
- **Revised** the same day (Q4, Andrew's call): the run's last round holds nothing, so an event held behind a failing predecessor is sent after that predecessor's final send rather than counted `failed` unsent.
