---
type: Decision
title: "An event a sink cannot encode costs only itself, and a batch of nothing encodable settles, counted"
description: "Every record-building sink encodes the whole batch through `sinks/_encode.encode_events` before its first bulk call, outside any lock or retry loop; an event it cannot encode is dropped alone, counted `dropped` by the call's `Deferral` and announced once per call by type, and a batch of nothing encodable returns rather than raising. `NATSSink` and `SentrySink` keep counting it `failed`. (SPEC-069)"
---

**One encode step, before the first bulk call.** A batch is the worker's unit of retry, so one event a sink could not encode cost every event beside it, and in eight classes (`StdoutSink`, `StderrSink`, `FileSink`, `RotatingFileSink`, `ClickHouseSink`, `RabbitMQSink`, `KafkaSink`, `AzureEventHubsSink`) it cost more: the events ahead of the bad one were already written, produced or batched when the encode raised, and the worker's retry delivered them again. `PostgresSink` and both Redis sinks encoded inside their retry loop and counted the whole batch `failed` once it was spent. Each record-building sink now pulls its per-event work into an `encode` function and runs it over the whole batch through `sinks/_encode.encode_events` at the top of `emit`, outside any lock and outside any retry loop, and makes its first write, produce, request or insert only once every event has been through it. The helper is SPEC-058's `HTTPSink._items` rule written once: a guard catching `Exception` and never `BaseException`, the failures recorded on the call's `Deferral` — counted and announced only when that `emit` returns (*A raising `emit` counts nothing*) — and one `_diag.lost` line per call, `<Sink>, encoding raised <Type>`, naming the class and the first failure's exception type and never its message or the event (invariant 11). A roster test in `tests/test_encode.py` derives from the tree every class whose `emit` reaches `json.dumps` and refuses one that is on neither the helper nor a named exemption, with a pinned floor and a fixture corpus.

**Where the count lands.** In each sink's private `_unencodable`, folded into `losses().dropped`; in `rejected` for `KafkaSink` and `GooglePubSubSink`, the dropped counter they already had; and on `SocketTransport._unencodable` for `SyslogSink` and socket-mode `LogstashSink`, whose ledger the transport owns, so `dropped_oversized` still means oversize only. `StdoutSink`, `StderrSink`, `FileSink`, `RotatingFileSink` and `SQLiteSink` had no `losses()` and gained a public one, which returns `None` until the sink has counted something, so a default-configured process logging clean events still reads `health().sink is None`. An event both unencodable and oversized counts once, as unencodable, because the encode step runs first.

**A batch of nothing encodable settles.** The sink makes no bulk call and returns, each event counted `dropped` and announced. Andrew chose this on 2026-11-04 over the arc plan's wording, which said such a batch raises. Raising and counting nothing would also have kept invariant 2; what decided it is that re-encoding identical input in the sink's own code fails identically, so a retry spends the worker's attempts on an input no attempt can change — SPEC-058 FR-005's rule for an all-unrenderable HTTP batch and the rule every sink already applied to an all-oversized one. It is deliberately not the all-failed re-raise of *Caller code that fails for one event costs only that event*, which exists because a caller's callable can fail differently next time. The ledger stays whole: when the encodable remainder fails, the call raises and counts nothing, the unencodable events included, and the call that finally returns counts them once; a closed sink still raises and counts nothing — `SocketTransport.send_all`'s closed check now runs before its empty-list return, so a closed socket sink does not settle an all-unencodable batch. Through the worker the batch reads `flush()` truthy and `failed_batches == 0`, with the loss in `health().sink.dropped`.

**The two declared exceptions.** `NATSSink` and `SentrySink` already isolated an unencodable event per event, counted it `failed` and never retried it, so their outcome did not change and they keep their counter, and an all-unencodable batch on either still raises. The principle is that an outcome that has not changed keeps its counter: no count is reclassified in a minor release (Andrew, 2026-11-04). The sinks this decision moves — Postgres, both Redis sinks and Mongo, which lost and retried the whole batch — moved because their outcome changed, and every move is listed in the release notes.

**Do NOT** encode inside a lock or a retry loop; do NOT hand anything to the destination before the whole batch is encoded; do NOT count an unencodable event in a call that raises; do NOT re-raise for an all-unencodable batch; do NOT move `NATSSink` or `SentrySink` to `dropped` in `1.x`; do NOT catch `BaseException` in the guard. A stream or file that fails partway through a batch still leaves its earlier lines written — this closes the encode route to that duplicate, not the I/O route. (SPEC-069 FR-001, FR-002)
