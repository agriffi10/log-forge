# log-foundry 1.1.0 — an OTLP log sink

**A feature release under the `1.x` freeze: one new public import path, nothing removed, nothing
renamed.** `from log_foundry.sinks.otlp import OTLPSink` is new and is now frozen until `2.0.0`
like every other documented sink path. `log_foundry.__all__` is the same 30 names it was at
`1.0.2`, no shipped sink's constructor signature changed
(`NATSSink.close()`'s bound is now the sink's own 1 s default rather than the driver's
unreachable 10 s — see *Fixed*), and the core still has no
runtime dependency, so a `>=1,<2` pin takes this release without a code change unless the code
passes a `float` payload ceiling to `configure()`; passes a `float` (`nan` and `inf` included) or a
numpy integer to an `int` sink argument such as `max_retries`, `backup_count`, `port` or
`GooglePubSubSink`'s `max_pending`; passes `flush()` or `shutdown()` a NaN `timeout`, or a
`timeout` that is not an `int`, a `float` or `None` but worked (a `Fraction` to `flush()`, a numpy
integer scalar to either); passes `HTTPSink` or a sink that forwards to it a `max_retry_after` that
is not an `int` or a `float` (a numpy integer worked; a `Fraction`, `Decimal` or numpy `float32`
raised out of `emit` once a `Retry-After` exceeded it, and a `str` or `None` on the first one);
configures a sink with a value its constructor now refuses — one that sent its events somewhere
other than the destination it named, an HTTP sink URL with a user or password before its host, or
one of the few that reached it, which their *Fixed* sections name; or gives `SentrySink` a DSN with
a path prefix, which now posts where Sentry's own SDKs post it; or relies on the text of a container
mapping key in `fields`, which is now JSON (see *Fixed* for each). **This release follows `1.0.2`**,
whose notes say there is no OTLP sink in it; both are true.

## New: `OTLPSink` (SPEC-056)

`OTLPSink(endpoint="http://localhost:4318/v1/logs", **http_kwargs)` POSTs each batch as an
OTLP/HTTP **JSON** `ExportLogsServiceRequest` to a Collector or to any backend that ingests OTLP —
Datadog, New Relic, Honeycomb, Grafana, Splunk, Elastic — so your logs arrive under the
OpenTelemetry names those backends already index: `severityNumber`/`severityText`, `traceId` and
`spanId`, `service.name`, `service.version`, `deployment.environment.name`, `exception.type`,
`exception.message`, `exception.stacktrace`, `code.function.name`, with the library's own fields
beside them under a reserved `log_foundry.` prefix (`parent_span_id`, `truncated`, `duration_ms`,
`status`) and one attribute per key of `fields`. The README's *OTLPSink: what it sends* subsection
is the contract a query can rest on; the mapping itself is private. No OpenTelemetry SDK or API
enters the runtime, and no `OTEL_*` environment variable is read: the endpoint is used exactly as
written, with no path appended.

What differs from the rest of the HTTP family, on purpose:

- **Retry set.** `429`, `502`, `503` and `504` only — OTLP's own — where every other sink retries
  `429` and any `5xx`. A `500` is abandoned on the first request, counted in `health().sink.failed`
  and announced. `Retry-After` is honoured. A `413` still halves the byte budget and re-sends in
  smaller requests, since nothing landed.
- **Partial success.** A `2xx` whose `partialSuccess.rejectedLogRecords` is non-zero is counted on
  `.rejected_records` and never retried; a `2xx` whose verdict cannot be read — a count that is not
  a usable integer, a body over 4 MiB — is counted on `.dropped_unadjudicated`, also never retried.
  Both feed `health().sink.failed`. A chunk whose every record was rejected raises, so the worker's
  retry and `failed_batches` show a permanent rejection. A body that is empty, not JSON or carries
  no `partialSuccess` is full success; the server's `errorMessage` never reaches stderr.
- **The response is read under a 4 MiB bound.** A longer non-`2xx` is abandoned on the first
  request whatever its status. Every other sink still reads its responses whole.
- **The budget includes the envelope.** Each record is charged its resource group's framing, so a
  chunk carries fewer records than `max_batch_bytes` alone would allow — more requests, never one
  the destination rejects. The generic defaults (1,000 records, 5,000,000 bytes) apply.
- **`endpoint`, not `url`**, and `method` must be `"POST"`; `body_format` is pinned. Each refusal
  names its argument at construction.

## Fixed

### `HoneycombSink` counts the events Honeycomb rejects

Honeycomb's `/1/batch/<dataset>` answers `200` whatever happened to the events, with one
`{"status": ...}` per event in the body — `202` accepted, `400` rejected, with an `error` beside it.
`HoneycombSink` ignored that body, so an event Honeycomb refused inside a `200` was counted nowhere
and announced nowhere. It now reads the array:

- **A rejected event** — any per-event status outside `2xx` — is counted on the new
  `.rejected_events`, announced as `lost N event(s); HoneycombSink, rejected by the server`, and not
  re-sent, since the chunk's other events landed. The server's `error` text never reaches stderr.
- **A batch none of whose chunks had an event accepted raises**, so the worker's retry engages and
  `failed_batches` moves, as for any delivery that landed nothing. A rejected chunk beside an
  accepted one does not raise; its events are counted instead.
- **A `200` whose verdict cannot be read** — an empty or unreadable body, one that is not an array of
  objects, an array whose length is not the chunk's, an entry whose `status` is not an integer — is
  counted whole on the new `.dropped_unadjudicated`, with a line saying the events may have landed,
  and is not re-sent.

Both counters feed `health().sink.failed`, so **if you alert on it, it can now move for a Honeycomb
destination where it stayed at zero** — those events were being lost before, silently.

### `HoneycombSink` refuses a dataset it cannot send

`HoneycombSink` places `dataset` in `/1/batch/<dataset>` as written, and a dataset with URL meaning
in it constructed and then sent its events somewhere other than the dataset named: `d#x` and `d?x`
both landed in `d` with nothing counted (urllib drops the fragment; `?` starts a query string), and
`a/b` went to a different path. The constructor now raises `ValueError`, naming `dataset` and never
echoing the API key, for a dataset that:

- holds `/`, `?` or `#`, or a backslash, which a WHATWG parser reads as `/`;
- is `.` or `..`, or their percent-encoded forms (`%2e`, `.%2E`, `%2E%2e`), which a normalizing hop
  removes from the path;
- is empty or only whitespace, which names no dataset.

**Every dataset that delivered before still goes where it went.** `dataset` is taken as an already
percent-encoded segment: `my%20data` still reaches `my data`, and a literal `%` is written `%25`.
Trailing whitespace is still floored, as urllib floors it on every URL.

### `current_baggage_header()` always returns, and what it returns always parses (SPEC-064)

`current_baggage_header()` is what you put on an outbound request so the next process continues the
trace. It rendered every baggage value with a bare `str()`, which could hang or raise although its
docstring says it never raises, and which could emit a header the next log-foundry process refused
whole. It now renders each value as event assembly coerces it, and it no longer fails on:

- a value that is a shared-sublist structure (`y = [y] * 16`, repeated), which never returned;
- a value whose `__str__` raises, which raised into your code;
- a lone surrogate in a value or a key (`set_baggage(k="\ud800")`, or an inbound
  `continue_trace(baggage="k=\ud800")`), which raised `UnicodeEncodeError`;
- an integer of more than 4,300 digits, which raised `ValueError`.

**What a value looks like in the header has changed.** Each value is coerced as an event's fields
are, then rendered as text. The header's coercion is a pass of its own over the baggage alone, so
a member that an event's `defaults` or per-call fields crowd out of `max_keys` or a work budget can
still reach the header:

| Baggage value | Header before | Header now |
|---|---|---|
| `datetime(2026, 1, 1)` | `2026-01-01 00:00:00` | `2026-01-01T00:00:00` |
| an `Enum` member | `E.A` | its value, `a` |
| a `Path` | its path | `<unserializable: PosixPath>` |
| `(1, 2)` or `{1, 2}` | `(1, 2)` or `{1, 2}` | `[1, 2]` |
| `b"ab"` | `b'ab'` | `ab` |
| a non-finite float, `float("nan")` or `float("inf")` | `nan`, `inf` | `<float: nan>`, `<float: inf>` |
| a string past `max_value_bytes` | all of it | clipped, ending `…[truncated]` |

A string within the ceilings and without a lone surrogate, a finite number, `True` and `None` are
unchanged. A dict is still sent as its repr, with its contents coerced, so `{1: "a"}` is now
`{'1': 'a'}` and `{"a": (1, 2)}` is `{'a': [1, 2]}`. A value nothing can render becomes
`<unserializable: Type>`, naming the type and never the value. Members
past `max_keys` (256 by default) are left out, as they are from an event. **If a downstream service
matches a header value by its exact text, check it against the table above.**

**The header is at most 8192 bytes**, the size the next log-foundry process accepts. A value at the
default `max_value_bytes` alone could exceed that, and the whole header was then refused on arrival,
losing the members that did fit. Members are now kept in the order you set them while they fit; the
first one that does not fit ends the header, and it and every member after it are left out, so a
later small member is never sent in its place. A member with an empty key is skipped, because the
parser refuses a header containing one. Neither is silent: the call that makes the first drop
writes `log-foundry: lost N baggage member(s); running total; members dropped from the outbound
baggage header` to stderr, where N is the running total after that call, and a line follows at
every 1,000th drop. Each line carries the running total and never a key or a value. `health()` is unchanged: a baggage member is not an event.

`set_baggage` and `get_baggage` are unchanged, and so are `continue_trace` and
`parse_baggage_header` for an exact `str` header; what they do with a value that is not an exact
`str` is in the SPEC-067 entry below. `get_baggage()` still returns what you stored, surrogate
included.

### `configure()` refuses a payload ceiling that is not an `int` (SPEC-065)

`configure()` took `max_value_bytes`, `max_stack_bytes`, `max_keys` and `max_depth` as `int | None`
but checked only that the value was not below 1, so a float passed and every event was then
assembled with arithmetic on it. Measured at `71e42dd`: `max_value_bytes=2.5` emptied `fields`,
`nan` lost the event, `inf` left strings unbounded and turned `bytes` into
`<unserializable: bytes>`, and `max_keys=2.5` kept three of four list entries. `"5"` was refused,
but by the comparison's own `TypeError`, which named neither the ceiling nor the type. The call now
raises `TypeError` naming the ceiling and the type for any value that is neither `None` nor an
`int`: `2.5`, `100.0`, `nan`, `inf` and `"5"` alike. A float is refused, not rounded, and a refused
call changes nothing.

- **`True` and other `int` subclasses keep working**, and are stored as the exact `int` they hold,
  so `get_config().max_keys` reports `1` for `True`. A subclass whose comparisons lie about a zero
  is judged by the number it holds and refused with the existing `ValueError`.
- **The sink validators agree.** The timeout, count and interval checks the sinks share now judge an
  `int` or `float` subclass by the number it holds and return the exact builtin, so
  `MemorySink(maxlen=...)` and `RotatingFileSink(interval=...)` refuse a subclass holding zero that
  they used to accept: `MemorySink` then kept nothing, and `RotatingFileSink` left 2 of 15 lines on
  disk. A plain `int` or `float` behaves as before.

**Who must change code:** only a caller passing a `float` ceiling, which was already a `mypy` error
against `int | None`; pass an `int`. Everything else behaves as it did.

### `shutdown()` closes the sink within its budget when the sink fails slowly (SPEC-062)

When a sink's `emit` was slow and then failed, the exit drain retried the batch up to
`max_retries + 1` times, because the wait between attempts returns at once while `shutdown()` is
stopping the worker. The retries could outlast `shutdown(timeout)`; the wait for the drain then
expired and the sink was left open, never closed, with the events inside the emit unannounced. A
sink whose `emit` waits 0.5 s and raises, under `shutdown(timeout=1.2)`, took 1.21 s, made 3
attempts, called `close()` 0 times and reported `lost 0 item(s)`; it now takes 1.01 s, makes 2
attempts and calls `close()` once.

- **The rule.** Before each retry on the exit drain, the worker declines it when the batch's
  longest attempt so far, plus a fixed 0.1 s, would end after the `shutdown()` deadline. The first
  attempt of every batch is always made, a retry predicted to fit is made, and no attempt already
  under way is cut short. With `shutdown(timeout=None)` there is no deadline and nothing is
  declined, so it behaves as before. `flush()` and a sink swap are not budgeted either.
- **A new line.** A declined retry counts once in `health().failed_batches` and writes
  `lost N event(s); retry declined after K emit attempt(s); the next was predicted to end after
  the shutdown() deadline`. **If you alert on `failed_batches`, it now also moves for a batch the
  exit drain declined to retry**, not only one that exhausted its attempts; the exhausted line,
  `batch abandoned after N emit attempts`, is unchanged.
- **The expiry line changed.** When the wait still expires with a batch inside `emit`, the
  `shutdown timed out` line appends `; N event(s) in flight, counted when the emit returns`. The
  same line also stopped calling the queue lost in this release; see the next section (SPEC-068).
- **What to expect.** On a sink that fails slowly, the exit drain makes fewer attempts than before,
  trading a late retry the process would not have lived to see for a sink that is closed. There is
  no new parameter: the budget is the `timeout` you pass. How long `close()` itself takes past that
  timeout is unchanged.

### `shutdown()`'s timeout line no longer calls queued events lost (SPEC-068)

When `shutdown(timeout)` expired with the worker thread still inside a sink's `emit`, its line
opened `lost N item(s)`, counting everything queued, and once the stuck emit returned and the
queued events failed, they were announced lost a second time. `N` also counted the internal marker
`shutdown()` had just queued: with one span stuck and two queued behind it, the line read
`lost 3 item(s)`, the later lines `lost 1 event(s)` and `lost 3 event(s)`, so four events were
announced as seven. The line now reads `log-foundry: shutdown timed out after Ts; the sink is left
open because the worker thread is still using it`, then `; N event(s) in flight, counted when the
emit returns` when a batch is inside `emit`, and `; M submission(s) still queued` when spans are
queued — each clause only when its count is not zero. It no longer claims a loss: if those events
are lost, the drain's own `lost N event(s)` line says so, once per batch. **If you match
`lost N item(s)` on this line, match `shutdown timed out` instead.**

### A sink swap that could not be confirmed no longer calls queued events lost (SPEC-068)

When `configure(sink=…)` could not confirm the previous sink had drained, its line opened
`lost N item(s)` for spans still queued on a live worker, which may well reach the new sink, and
counted the swap's own internal marker. It was also longer than the library's line bound, so it
shipped cut off mid-word. It now reads `log-foundry: the previous sink could not be confirmed
drained within Ts; it is left open until a shutdown() finds the drain thread ended`, then
`; M submission(s) still queued, which may reach the new sink` when spans are queued, and fits the
bound. `health().incomplete_swaps` counts it as before.

### `shutdown()` called from inside a sink's `emit` returns instead of raising or waiting

A sink whose `emit` called `log_foundry.shutdown()` made the worker thread the caller. If it was the
first call, it raised `RuntimeError` out of a function documented to raise nothing. If another
`shutdown()` was already waiting, it blocked for its whole timeout on its own thread, and could make
that other call's wait expire. Given a valid `timeout`, it now stops the worker and returns at
once, the worker finishes after that `emit` returns, and the next `shutdown()` from another thread
does the waiting — and writes the `shutdown timed out` line if that `emit` never returns, instead
of every later call, `atexit`'s included, waiting out its budget with nothing written (SPEC-068).

### HTTP sinks refuse a base URL whose query or fragment swallowed the path they append

`ElasticsearchSink`, `OpenSearchSink`, `LokiSink` and `HoneycombSink` append a path to the `url` you
pass — `/_bulk`, `/loki/api/v1/push`, `/1/batch/<dataset>` — and a `?` or `#` anywhere in that base
moved the appended path out of the request path. `LokiSink("http://h?x")` posted to
`/?x/loki/api/v1/push`, `ElasticsearchSink("http://h:9200?pipeline=p", ...)` to
`/?pipeline=p/_bulk`, so the pipeline was never applied, and `HoneycombSink(url="https://h#f")` to
`''`, the path dropped with the fragment. Whatever the server answered there was counted as the
outcome. Each constructor now raises `ValueError` naming `url`, without echoing it (a query is where
a credential would sit), for a base containing `?` or `#` — an empty query or a bare `#` included.
The appended path is never spliced in front of your query, since that would send a request you never
wrote. A base with a path (`https://proxy/es/`) composes as before. `OTLPSink`, `SplunkHECSink`,
`HTTPSink` and `LogstashSink` send to their URL as written, so a query there still goes where you
put it.

### `DatadogSink` refuses a `site` that is not a host name

`site` is placed into the intake host as written, so `site="datadoghq.com#"` posted to an empty
path, `"datadoghq.com?x"` to `/?x/api/v2/logs` and `"datadoghq.com/x"` to `/x/api/v2/logs`;
`"datadoghq.com@evil.example"`, `""`, `..` and `%2e` were accepted too. The constructor now raises
`ValueError` naming `site` for any value that is not dot-separated letters, digits and hyphens. That
refuses two values that did reach the intake, a port (`"datadoghq.com:443"`) and a trailing dot
(`"datadoghq.com."`), because neither is a site Datadog names, and a trailing slash
(`"datadoghq.com/"`), which reached the intake's host at `//api/v2/logs`. Every documented site
(`datadoghq.com`, `us3.datadoghq.com`, `us5.datadoghq.com`, `datadoghq.eu`, `ap1.datadoghq.com`,
`ap2.datadoghq.com`, `ddog-gov.com`) still constructs.

### `SentrySink` reads a DSN's path as Sentry's SDKs do

**This changes where some DSNs post.** The HTTP fallback builds its envelope URL from the DSN, and
it read the DSN's path differently from `sentry_sdk`. The fallback is built whenever you pass a
`dsn` and the backend is not `"sdk"` — under the default `"auto"` too, with the SDK installed — so
the refusal below applies there as well:

- **A path prefix was misplaced.** `https://key@host/prefix/1` posted to `/api/prefix/1/envelope/`.
  It now posts to `/prefix/api/1/envelope/`, as the SDKs do: the last segment is the project id and
  the rest is a prefix placed before `api/`. **If you run Sentry behind a path prefix, check where
  its events arrive after upgrading.**
- **`;params` were dropped from the project id.** The DSN was parsed with `urlparse`, so project
  `1;x` posted to project `1`. It is now split as the SDK splits it.
- **A project id the SDK refuses is refused** with `ValueError` naming `dsn` — one Python's `int`
  cannot read, as the SDK's rule is: `..` had posted to `/api/../envelope/`, `1/` to
  `/api/1//envelope/` and `1;` to project `1`. The public key is not echoed. An id `int` reads
  leniently (`+1`, `1_0`) is sent as the SDK sends it, `1` and `10`, so no project id the SDK
  accepts is refused.
- **An IPv6 host keeps its brackets.** `https://key@[2001:db8::1]/1` lost them and posted to host
  `2001:db8:` on port `1`. The SDK has the same defect, and this sink does not copy it.

**A DSN with no prefix posts exactly where it did**, the hosted
`https://<key>@o<n>.ingest.sentry.io/<id>` form included. So do `//1` and `01`, which the SDK sends
to `//api/1/envelope/` and project `1`. The SDK's own `backend="sdk"` path is unchanged.

### Keys, impostor scalars and hostile classes (SPEC-063)

Nothing here adds a name or a setting; each is a behaviour a caller or a query can see.

- **A container key is written as JSON, not as a `repr`.** A mapping key that is a `tuple`, `list`,
  `dict`, `set` or `frozenset` (a namedtuple included; an `Enum` member is excepted) was `str(key)`,
  so `(1, 2)` was the key `"(1, 2)"` and a member object's `repr` was written inside it. It is now
  the JSON of the key coerced like a value: `"[1, 2]"`, `'["a"]'`, `"[1]"`, and an object member is
  `<unserializable: T>`. **A query, alert or index on the old text must change.** The key's members
  now spend the pass's node and byte budgets as a value's do, so a huge key stops the entries after
  it, and a shared-substructure key that took doubling time per level — forty levels never
  returned — now returns, with `truncated` set. A `bytes` or `bytearray` key is priced before it is
  rendered, so one longer than about a quarter of the remaining 16 MiB budget becomes `<size limit>`
  without being rendered, even a printable one. An object that is itself the key keeps its own
  `str()`.
- **An object that only claims a scalar type is a placeholder.** One whose `__class__` returns
  `bool`, `float` or `int`, or whose metaclass hashes and compares as `int`, reached a sink as the
  object itself and made its bare `json.dumps` raise. It is now `<unserializable: T>` naming its
  real type, as is an `Enum` member whose value claims `float`. A genuine `int` or `float` subclass
  is written as an exact number, and a `float` subclass key no longer renders through its own
  `__str__`; an `Enum` key, `(float, Enum)` included, still reads as its name. A real `tuple`,
  `dict`, `bytes` or other builtin subclass that claims `UUID`, `Decimal` or `Enum` through
  `__class__` is rendered as what it is, never through its `repr`. An `Enum` member with a `tuple`,
  `list`, `dict`, `set`, `frozenset`, `bytes` or `bytearray` mixin is written as `Type.NAME`, as a
  value and as a key: a `ReprEnum` such member was its mixin's `repr` before, and now reads as
  every other such member does.
- **A hostile `fields=` or `echo=` no longer raises into your code.** A `fields=` mapping whose
  `__bool__` or `__len__` raises is ignored and announced ("merging the fields= argument"), and an
  `echo=` whose `__bool__` raises echoes nothing and is announced ("echoing to the console"); the
  event is delivered either way, and inside a `@trace`d function the span no longer records
  `status=error` for an exception you never raised.
- **A hostile exception class no longer costs its span's events.** An exception whose class's
  metaclass defines `__name__` or `__module__` as a property that raises (or `__name__` as a
  non-`str`) lost the span's events; `error.type` and `error.module` now read the class's stored
  name and module, `error.module` is `"?"` when the stored module cannot be rendered, and the
  announcement of an absorbed failure names the stored type instead of being swallowed.
- **A hostile key in the defaults no longer costs the event.** Two keys whose hashes collide and
  whose comparison raises lost the whole event; the lower-precedence key is dropped and `truncated`
  is set, and on that path only the merged keys come out highest-source-first.

### Integer sink arguments and the `flush()`/`shutdown()` timeout refuse what is not a number (SPEC-066)

SPEC-065's rule now holds at the sinks' own `int` arguments. `max(max_retries, 0)` passed a float
straight through, so `HTTPSink(url, max_retries=2.5)` constructed and then raised out of every
batch with nothing counted, as did `nan` and `inf`; `RotatingFileSink(backup_count=2.5)` killed
the sink on its first rollover; `SocketTransport` (and so `SyslogSink` and `LogstashSink`) took
`port=2.5` past its range check and raised from every send. Every `int` argument a sink
constructor floors or range-checks — `max_retries` wherever a sink takes one (on `SentrySink`,
wherever it builds its HTTP fallback, which `backend="sdk"` does not) and on the worker,
`RotatingFileSink`'s `max_bytes` and `backup_count`, `HTTPSink`'s `max_batch_count`,
`PostgresSink`'s `connect_timeout`, `GooglePubSubSink`'s `max_pending`, the socket `port` and
`NATSSink`'s `max_reconnect_attempts` — now raises `TypeError` at construction, naming the class,
the argument and the type, for a `float` (`nan` and `inf` included), a `str`, `None` where the
argument does not take it, or a number that only worked by duck typing, such as a numpy integer.
It is refused before the sink builds a client, connection or file, so a refused construction
leaves nothing behind.

- **A negative `max_retries` still floors to zero** and the sink still delivers, as every other
  `int` floor still floors; `True` and other `int` subclasses keep working and are stored as the
  exact `int` they hold.
- **`GooglePubSubSink(max_pending=inf)`, which meant no bound, is refused** with the other floats.
  Pass a large `int`, such as `sys.maxsize`, for that.
- **`HTTPSink`'s `max_retry_after` must be an `int` or a `float`**, refused at construction with a
  `TypeError` naming it, through every sink that forwards it to `HTTPSink` too. A `str` or `None`
  constructed and then raised an uncounted `TypeError` out of `emit` on the first `Retry-After`
  header. A `Fraction`, `Decimal` or numpy `float32` delivered only while the server asked for
  no more than the ceiling, and raised out of `emit` once it asked for more; a numpy integer
  worked. All are now refused, like any number that is not an `int` or `float` instance. An
  accepted ceiling is stored as the exact builtin, so a `float` subclass whose comparisons lie is
  judged by the number it holds. Its value is judged as before: zero, a negative or `nan` falls
  back to exponential backoff.
- **`RotatingFileSink`'s rollover period must fit a `float`.** `when="S", interval=10**400` raised a
  raw `OverflowError` after opening the file; it is now a `ValueError` naming `interval`, raised
  before the file is opened. Every period that fits still works.
- **A refusal that names an integer too long to print names it `<int: ~N digits>`**, the
  placeholder events already use. `SocketTransport("h", 10**5000)` and the positive-count,
  timeout, `max_reconnect_attempts` and `configure()` ceiling refusals raised CPython's own
  "Exceeds the limit (4300 digits)" `ValueError` out of the message, naming neither the argument
  nor the class; they now raise their own.
- **`flush(timeout=inf)` now waits.** `inf`, or any value above `threading.TIMEOUT_MAX`, is the
  unbounded wait `None` is: `flush(math.inf)` used to report `thread-died` at once with the drain
  thread alive, and `shutdown(math.inf)` raised `OverflowError` into the caller.
- **A NaN `timeout` raises `ValueError`, and a non-number `TypeError`**, both naming `timeout`, at
  entry to `flush()` or `shutdown()`, before anything is drained or counted — so a refused
  `shutdown()` does not retire the process and a retry with a good value works. "Non-number" means
  anything not an `int`, a `float` or `None`. A `Fraction` worked for `flush()` only, and a numpy
  integer scalar on both calls; both are now refused. A `str`, a `Decimal` or a numpy `float32`
  already failed, `flush()` misreporting it as `thread-died` and `shutdown()` raising a bare
  `TypeError`, and now fails with the named `TypeError` at entry. A numpy `float64` is a `float`
  and keeps working. Zero and negatives keep meaning "do not wait", and `shutdown(-10**400)`, which
  raised `OverflowError`, now behaves as `shutdown(-1)`.

**Who must change code:** a caller passing a float, or a numpy integer, to one of the `int`
arguments above — already a `mypy` error against `int` — a NaN or non-number `timeout`, or a
`max_retry_after` that is not an `int` or a `float`. Pass an `int`, or a `float` or `None` for a
timeout and an `int` or `float` for `max_retry_after`. Everything else behaves as it did.

### `continue_trace` always returns, and a refusal is always announced (SPEC-067)

`continue_trace` takes values off the wire that are `str` only by annotation. Before this release a
value it refused was echoed to stderr through a `repr` of the whole value, taken before the echo was
cut to 64 characters, and the parsers called the value's own methods. So a shared-sublist list
passed as `traceparent` never returned; a value whose `__repr__` raised reported
`reason="rejected"` with no line written; a `str` subclass or an object with a spoofed `__class__`
raised into your code; and a valid `str` subclass was adopted as itself, so a later
`current_traceparent()` raised that subclass's own exception. None of this runs any code of the
value now, and a refusal always writes its line. What you can see change:

- **A value that is not a `str` is echoed by its type name.** `continue_trace(traceparent=b"00-bad")`
  now writes `<bytes>` where it wrote `b'00-bad'`; an `int` is `<int>`.
- **A `str` longer than 64 characters is cut before it is quoted**, so its quoting can differ:
  `"x" * 100 + "'"` now opens with `'`, where it opened with `"`. An exact `str` of at most 64
  characters is echoed exactly as before.
- **The parsers refuse a `str` subclass when called directly.** `ids.parse_traceparent`,
  `ids.is_valid_trace_id`, `ids.is_valid_span_id` and `context.parse_baggage_header` accept only an
  exact `str`. `continue_trace` still adopts a valid header in a `str` subclass.
- **An adopted `str` subclass is stored as the exact `str` it holds**, so the ids on your events
  and from `current_traceparent()` are plain `str`, and `current_traceparent()` no longer raises the
  subclass's own exception.

**Who must change code:** no caller. The changes are to stderr text and to modules outside the
frozen surface, and every exact `str` header is adopted or refused as it was.

### HTTP sinks refuse a URL that carries a user or password

`HTTPSink`, the HTTP sinks that take a URL from you and `LogstashSink` accepted credentials written
before the host: `ElasticsearchSink("http://elastic:pw@es:9200", index="i")` constructed. `urllib`
never turns them into an `Authorization` header; it keeps them as part of the host name. Measured
without a proxy, every request asked the resolver for a host named `elastic:pw@es`, failed, and was
counted as a connection error. Measured through an HTTP proxy, `urllib` sent `elastic:pw@` to the
proxy in cleartext, in the request line and the `Host` header, and sent no `Authorization` header.
The same URL without a port (`http://elastic:pw@es`) was already refused, by accident, with a
message that printed the URL, password included. Each constructor now raises `ValueError` for a
`user@`, `user:password@`, `:password@` or bare `@` before the host, percent-encoded (`%40`) or not,
naming the argument you wrote — `url`, `OTLPSink`'s `endpoint`, `DatadogSink`'s `site` — and where
credentials go instead: `auth=` or an `Authorization` header in `headers=`, `SplunkHECSink`'s
`token`, or `HoneycombSink`'s and `DatadogSink`'s `api_key`. The message never contains the URL, the
user or the password, and chains no exception that does. An `@` in a path, query or fragment
(`http://h/a@b`, `http://h/?x=a@b`) is not a credential separator and constructs as before.
`SentrySink` is unaffected: a DSN carries its public key before the `@` by design.

Most other refusals of an HTTP sink URL printed the URL, and two also chained a parser error
quoting part of it, so a password holding `#`, `?` or `/` leaked: those end the host before the
`@`, so `http://elastic:pa#ss@es:9200/x` reads as no userinfo and was refused with
`nonnumeric port: 'pa'` and the URL. A refused URL that holds an `@` anywhere, and a refused
`DatadogSink` `site` that does, is now described in fixed text, naming the argument and the reason
and chaining nothing; a URL with no `@` is quoted as before.

### `SentrySink` never echoes the key in a DSN it refuses

A DSN missing its scheme, host or project id was refused with the whole DSN in the message, public
key included. One `urlsplit` cannot read was refused with `urlsplit`'s reason in the message and its
error chained, and that reason quotes the DSN's whole netloc, key included, for a character NFKC
normalization turns into a URL delimiter, and on some Python releases (3.13.1, for one) the
bracketed text for a bad bracket, which in `https://[key]@h/1` is the key. Both refusals still name
`dsn` and what is wrong; neither prints the DSN or chains an exception that does. A DSN whose host
holds a percent-encoded `@` (`https://key@h%40x/1`), which `urllib` would have decoded into the host
it connects to, is now refused too, under the same rule.

### `NATSSink` asks the server before it publishes, and closes under its own deadline (SPEC-061)

`NATSSink` reported success for events that never left the process, and after any outage it never
published again: it drove its event loop only inside a call, so the driver's reader, ping and
reconnect tasks got no CPU between calls, and its only liveness evidence was a flag the driver
could not update. Measured against a paused server, 75 of 75 emits were accepted over 148 s with
nothing raised or counted; after a stop and start the sink was still refusing 40 s later.

- **The loop runs on a thread the sink owns** from construction to `close()`, so the driver's own
  tasks run between calls and a reconnect completes on its own (measured: 0.50 s after the server
  restarted).
- **A publish waits for the server.** For a client the sink connected itself, `emit` sends a PING
  and publishes only after the PONG arrives, inside the same `publish_timeout`, in core and
  JetStream modes; a stalled server is refused within that budget with no counter moved, and every
  later caller is refused at once while the PING is known to be unanswered. The wait is never
  cancelled, because a late PONG on a cancelled wait kills the driver's reader.
- **A core batch is confirmed or counted.** After its last publish has reached the transport (the
  sink waits for the driver's pending buffer to drain, since a PING written ahead of queued
  publishes would confirm nothing about them), a core batch waits for a second round trip; when
  the buffer does not drain or the server does not answer in time the published events are
  counted in `health().sink.failed` and announced, and `emit` returns rather than raises, because
  the bytes may still land and a retry would duplicate them. A JetStream publish that blocks past
  the deadline is abandoned and counted the same way rather than holding the thread. The next
  call is refused, so the stall is still reported. A core `emit` therefore costs two server round
  trips on the calling thread (one event: 0.47 ms against 0.04 ms before; 500 events: 1.26 ms
  against 0.90 ms).
- **`close()` is bounded by the sink.** It no longer calls the driver's `drain()`, whose final
  flush ran to its own 10 s whatever `drain_timeout` said. `drain_timeout` now sets the deadline of
  the sink's own close sequence, **1 s by default**, under which it confirms the outbound buffer
  with the server, closes the client, and stops its loop thread; a close against a stalled server
  raises `TimeoutError` at that deadline instead of `FlushTimeoutError` at 10 s. The value is still
  forwarded to `nats.connect`.
- **`flush()`** goes through the same round trip, bounded by `publish_timeout`, and raises
  `SinkDeliveryError` when the server does not answer.
- **In a forked child** the sink refuses rather than publishing on an inherited connection.
- An injected `client=` is never probed and keeps the driver's flag as its only guard. Three
  things did change for it: `close()` now closes it without draining it (before this release
  `close()` called the driver's `drain()` on an injected client too); its `flush()` is bounded by
  `publish_timeout`, after which the call is reported as `SinkDeliveryError` and the sink stays
  open; and a publish that does not return within `publish_timeout` is counted in
  `health().sink.failed` and announced instead of holding the thread.
- **A publish the driver never returns from refuses the calls behind it.** On any client, while
  a publish abandoned at the deadline is still pending, every later `emit` and `flush` raises
  `SinkDeliveryError` at once instead of queueing behind the same blocked write; the sink accepts
  again as soon as that publish finishes.

## What did not change

A second `shutdown()` after one that expired still returns at once, whatever its timeout, and
leaves the sink open while the worker thread is still inside `emit`; a later call that finds the
thread ended closes it. So in a process that exits through `atexit` after an expired `shutdown()`,
a sink still inside `emit` is neither flushed nor closed — the exit does not spend a second budget
after yours ran out. SPEC-068 records that as a decision rather than changing it.

Every other sink's wire format, its own retry loop and response handling, apart from where a
prefixed `SentrySink` DSN posts and `NATSSink`'s delivery and close behaviour (its *Fixed*
entry above); and `HoneycombSink`'s wire format and retry loop. The worker's
retry of a failed batch is not a sink's retry; on the exit drain it is the only retry that changed
(SPEC-062), and elsewhere it retries as before. The `type: ignore` on
`sinks/pubsub.py` gained a code and `pyproject.toml` a `mypy` override for `google.cloud.*`, both
because the new **dev-only** `opentelemetry-proto` dependency (the generated classes a test parses
the sink's output with) installs `protobuf`; nothing a consumer installs changed.

The baggage on events, the `baggage` header's W3C format and `set_baggage`'s storage of arbitrary
objects are as they were; the change in `current_baggage_header()` is only in what it renders from
them (SPEC-064).
