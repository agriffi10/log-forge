# log-foundry 1.1.0 — an OTLP log sink

**A feature release under the `1.x` freeze: one new public import path, nothing removed, nothing
renamed.** `from log_foundry.sinks.otlp import OTLPSink` is new and is now frozen until `2.0.0`
like every other documented sink path. `log_foundry.__all__` is the same 30 names it was at
`1.0.2`, no shipped sink's constructor signature or default changed, and the core still has no
runtime dependency, so a `>=1,<2` pin takes this release without a code change. **This release follows
`1.0.2`**, whose notes say there is no OTLP sink in it; both are true.

## New: `OTLPSink` (SPEC-056)

`OTLPSink(endpoint="http://localhost:4318/v1/logs", **http_kwargs)` POSTs each batch as an
OTLP/HTTP **JSON** `ExportLogsServiceRequest` to a Collector or to any backend that ingests OTLP —
Datadog, New Relic, Honeycomb, Grafana, Splunk, Elastic — so your logs arrive under the
OpenTelemetry names those backends already index: `severityNumber`/`severityText`, `traceId` and
`spanId`, `service.name`, `service.version`, `deployment.environment.name`, `exception.type`,
`exception.message`, `exception.stacktrace`, `code.function.name`, with the library's own fields
beside them under a reserved `log_foundry.` prefix (`parent_span_id`, `truncated`, `duration_ms`,
`status`) and one attribute per key of `fields`. The README's *OTLPSink: what it sends* subsection
is the contract a query can rest on; the mapping itself is private. No OpenTelemetry SDK or API
enters the runtime, and no `OTEL_*` environment variable is read: the endpoint is used exactly as
written, with no path appended.

What differs from the rest of the HTTP family, on purpose:

- **Retry set.** `429`, `502`, `503` and `504` only — OTLP's own — where every other sink retries
  `429` and any `5xx`. A `500` is abandoned on the first request, counted in `health().sink.failed`
  and announced. `Retry-After` is honoured. A `413` still halves the byte budget and re-sends in
  smaller requests, since nothing landed.
- **Partial success.** A `2xx` whose `partialSuccess.rejectedLogRecords` is non-zero is counted on
  `.rejected_records` and never retried; a `2xx` whose verdict cannot be read — a count that is not
  a usable integer, a body over 4 MiB — is counted on `.dropped_unadjudicated`, also never retried.
  Both feed `health().sink.failed`. A chunk whose every record was rejected raises, so the worker's
  retry and `failed_batches` show a permanent rejection. A body that is empty, not JSON or carries
  no `partialSuccess` is full success; the server's `errorMessage` never reaches stderr.
- **The response is read under a 4 MiB bound.** A longer non-`2xx` is abandoned on the first
  request whatever its status. Every other sink still reads its responses whole.
- **The budget includes the envelope.** Each record is charged its resource group's framing, so a
  chunk carries fewer records than `max_batch_bytes` alone would allow — more requests, never one
  the destination rejects. The generic defaults (1,000 records, 5,000,000 bytes) apply.
- **`endpoint`, not `url`**, and `method` must be `"POST"`; `body_format` is pinned. Each refusal
  names its argument at construction.

## Fixed

### `HoneycombSink` counts the events Honeycomb rejects

Honeycomb's `/1/batch/<dataset>` answers `200` whatever happened to the events, with one
`{"status": ...}` per event in the body — `202` accepted, `400` rejected, with an `error` beside it.
`HoneycombSink` ignored that body, so an event Honeycomb refused inside a `200` was counted nowhere
and announced nowhere. It now reads the array:

- **A rejected event** — any per-event status outside `2xx` — is counted on the new
  `.rejected_events`, announced as `lost N event(s); HoneycombSink, rejected by the server`, and not
  re-sent, since the chunk's other events landed. The server's `error` text never reaches stderr.
- **A batch none of whose chunks had an event accepted raises**, so the worker's retry engages and
  `failed_batches` moves, as for any delivery that landed nothing. A rejected chunk beside an
  accepted one does not raise; its events are counted instead.
- **A `200` whose verdict cannot be read** — an empty or unreadable body, one that is not an array of
  objects, an array whose length is not the chunk's, an entry whose `status` is not an integer — is
  counted whole on the new `.dropped_unadjudicated`, with a line saying the events may have landed,
  and is not re-sent.

Both counters feed `health().sink.failed`, so **if you alert on it, it can now move for a Honeycomb
destination where it stayed at zero** — those events were being lost before, silently.

### `HoneycombSink` refuses a dataset it cannot send

`HoneycombSink` places `dataset` in `/1/batch/<dataset>` as written, and a dataset with URL meaning
in it constructed and then sent its events somewhere other than the dataset named: `d#x` and `d?x`
both landed in `d` with nothing counted (urllib drops the fragment; `?` starts a query string), and
`a/b` went to a different path. The constructor now raises `ValueError`, naming `dataset` and never
echoing the API key, for a dataset that:

- holds `/`, `?` or `#`, or a backslash, which a WHATWG parser reads as `/`;
- is `.` or `..`, or their percent-encoded forms (`%2e`, `.%2E`, `%2E%2e`), which a normalizing hop
  removes from the path;
- is empty or only whitespace, which names no dataset.

**Every dataset that delivered before still goes where it went.** `dataset` is taken as an already
percent-encoded segment: `my%20data` still reaches `my data`, and a literal `%` is written `%25`.
Trailing whitespace is still floored, as urllib floors it on every URL.

### `current_baggage_header()` always returns, and what it returns always parses (SPEC-064)

`current_baggage_header()` is what you put on an outbound request so the next process continues the
trace. It rendered every baggage value with a bare `str()`, which could hang or raise although its
docstring says it never raises, and which could emit a header the next log-foundry process refused
whole. It now renders each value the way the event carries it, and it no longer fails on:

- a value that is a shared-sublist structure (`y = [y] * 16`, repeated), which never returned;
- a value whose `__str__` raises, which raised into your code;
- a lone surrogate in a value or a key (`set_baggage(k="\ud800")`, or an inbound
  `continue_trace(baggage="k=\ud800")`), which raised `UnicodeEncodeError`;
- an integer of more than 4,300 digits, which raised `ValueError`.

**What a value looks like in the header has changed.** Each value is coerced as an event's fields
are, then rendered as text, so a header value is now the same coerced value your events carry, written as text:

| Baggage value | Header before | Header now |
|---|---|---|
| `datetime(2026, 1, 1)` | `2026-01-01 00:00:00` | `2026-01-01T00:00:00` |
| an `Enum` member | `E.A` | its value, `a` |
| a `Path` | its path | `<unserializable: PosixPath>` |
| `(1, 2)` or `{1, 2}` | `(1, 2)` or `{1, 2}` | `[1, 2]` |
| `b"ab"` | `b'ab'` | `ab` |
| a non-finite float, `float("nan")` or `float("inf")` | `nan`, `inf` | `<float: nan>`, `<float: inf>` |
| a string past `max_value_bytes` | all of it | clipped, ending `…[truncated]` |

A string within the ceilings and without a lone surrogate, a finite number, `True` and `None` are
unchanged. A dict is still sent as its repr, with its contents coerced, so `{1: "a"}` is now
`{'1': 'a'}` and `{"a": (1, 2)}` is `{'a': [1, 2]}`. A value nothing can render becomes
`<unserializable: Type>`, naming the type and never the value. Members
past `max_keys` (256 by default) are left out, as they are from an event. **If a downstream service
matches a header value by its exact text, check it against the table above.**

**The header is at most 8192 bytes**, the size the next log-foundry process accepts. A value at the
default `max_value_bytes` alone could exceed that, and the whole header was then refused on arrival,
losing the members that did fit. Members are now kept in the order you set them while they fit; the
first one that does not fit ends the header, and it and every member after it are left out, so a
later small member is never sent in its place. A member with an empty key is skipped, because the
parser refuses a header containing one. Neither is silent: the call that makes the first drop
writes `log-foundry: lost N baggage member(s); running total; members dropped from the outbound
baggage header` to stderr, where N is the running total after that call, and a line follows at
every 1,000th drop. Each line carries the running total and never a key or a value. `health()` is unchanged: a baggage member is not an event.

`set_baggage`, `get_baggage`, `continue_trace` and `parse_baggage_header` are unchanged, and
`get_baggage()` still returns what you stored, surrogate included.

## What did not change

Every other sink's wire format, retry behaviour and response handling, and `HoneycombSink`'s wire
format and retry behaviour. The `type: ignore` on
`sinks/pubsub.py` gained a code and `pyproject.toml` a `mypy` override for `google.cloud.*`, both
because the new **dev-only** `opentelemetry-proto` dependency (the generated classes a test parses
the sink's output with) installs `protobuf`; nothing a consumer installs changed.

The baggage on events, the `baggage` header's W3C format and `set_baggage`'s storage of arbitrary
objects are as they were; the change in `current_baggage_header()` is only in what it renders from
them (SPEC-064).
