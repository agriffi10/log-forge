**A behaviour-correction release: no public name, signature or default changed.** `1.0.2` is a
patch under the `1.x` freeze. `log_foundry.__all__` is the same 30 names it was at `1.0.1`, no
shipped sink's constructor changed, and `pyproject.toml` is untouched, so your `>=1,<2` pin takes
it without a code change. What did change is how a handful of failure paths behave and what the
counters say about them, and **if you alert on `health().sink` you should read the next section
before you bump**, because some counters now move where they were silent.

Nothing here is a new feature. `SPEC-056`, the OTLP log sink, is a Draft on `main` and ships no
code in this release; there is no OTLP sink in `1.0.2`.

## Counters and log lines that now move

- **`ElasticsearchSink` and `OpenSearchSink`: an unreadable `2xx` is now counted.** A `_bulk`
  response that came back `2xx` but whose body could not be decoded (syntax, encoding, nesting past
  the decoder's recursion limit, memory), decoded to something other than an object, or was empty
  used to leave every counter at zero and stderr empty. The sink now adds the request's events to
  `dropped_unadjudicated`, so `losses().failed` and therefore `health().sink.failed` rise, and
  writes one stderr line saying the events *may have landed* and were not retried. Against a server
  answering every POST with an empty `200`, a traced call with one log line (three events) took
  `health().sink` from `SinkLosses(dropped=0, failed=0)` to `SinkLosses(dropped=0, failed=3)`.
  **A non-zero value can mean a proxy answered rather than the cluster.** It is an upper bound,
  like `failed`: the events were not retried, so they may have been indexed. One related case is
  deliberately *not* counted and is recorded as an open item (`docs/architecture.md` §12): a `2xx`
  object with no truthy `errors` key is still read as success, unverified, even if it is an error
  document such as `{"error": ..., "status": 500}`.
- **`ElasticsearchSink`: a response nested too deeply no longer re-sends indexed events.** Such a
  body used to raise `RecursionError` out of `emit`, which the worker read as a failed batch, so it
  re-sent events the server had already indexed and never sent any later chunk of the batch. It is
  now settled and counted like the other unreadable bodies. (#276)
- **A drop is counted once, however many times the worker retries.** Every shipped sink now
  decides a per-event drop (an oversized event, a refused hand-off, a `413`) and counts it only when
  the `emit` that decided it returns, so a batch the worker retried counts the drop once and a batch
  it abandoned counts it zero times at the sink, leaving the abandon line as the only count. Before,
  a retried batch counted the same drop on every attempt. This reaches `SQSSink`, `KinesisSink`,
  `FirehoseSink`, `SNSSink`, `MongoDBSink`, `AzureEventHubsSink`, `SyslogSink`, `LogstashSink`
  in socket mode, `KafkaSink`, `GooglePubSubSink` and the HTTP family. (SPEC-058, SPEC-059)
- **`KafkaSink` and `GooglePubSubSink`: `rejected` no longer counts a batch refused whole.** That
  case raises, and it is counted as `failed_batches` and the abandon line, or as `orphan_lost`
  outside a span. A batch refused on one attempt and accepted on the next counts nothing. An orphan
  refusal is now in `orphan_lost` only, where it used to be in `dropped` as well. (SPEC-059)
- **`MultiSink.losses().failed` now includes the batch for every child that raised and was
  absorbed**, a child that reports its own losses included; it was only children that report
  nothing. When *every* child raises, the fan-out now counts nothing and re-raises the first error,
  leaving the count to the worker; before, it counted per attempt. A reporting child's own `failed`
  and the fan-out's count can both include the same events. The oversized or refused event of a
  child that raises moves from `dropped` to the fan-out's `failed`. (SPEC-058, SPEC-059)
- **HTTP sinks: an unrenderable event is dropped alone and counted.** One event that cannot be
  serialised used to take its whole batch down; it is now dropped by itself, counted in
  `dropped`, and a batch whose every event is unrenderable settles without raising. A single
  unrenderable event outside a span therefore moves from `orphan_lost` to `health().sink.dropped`.
  `ElasticsearchSink.losses().dropped` now includes these as well. (SPEC-058)
- **New stderr lines, and the old ones move.** Each batch with a per-event drop writes one line of
  the form `lost N event(s)`, naming the class and the exception type, from `TransformSink`,
  `FilteringSink`, `SQSSink` (its FIFO id callables) and the HTTP sinks. Oversize, refusal and `413`
  lines are now written after the requests, when `emit` returns, not as each drop is decided, and
  the Event Hubs and socket oversize lines are no longer written under the sink's transport lock.

## One bad event now costs only itself

Each of these used to let one event's failure escape `emit`, so the worker treated the whole batch
as failed.

- **`TransformSink`: a transform that raises, or returns something that is neither a `dict` nor
  `None`, drops that one event.** Before, a raising function failed the batch and a non-`dict`
  result was forwarded to the inner sink. The drop is counted in the wrapper's `losses()`, which is
  now non-`None` once it has counted a drop even over an inner sink that reports nothing. The same
  holds for `FilteringSink` and a predicate that raises.
- **`TransformSink`: a transform's output is coerced for type.** `bytes`, `datetime`, `NaN` and a
  lone surrogate in a result are rendered the way assembly renders them (`b"x"` becomes `"x"`, a
  `datetime` its ISO form) instead of reaching the sink raw, and a result nested past 100 levels is
  cut at `<depth limit>` and the event marked `truncated`. No configured ceiling applies to a
  transform's output.
- **`SQSSink`: a FIFO id callable that raises costs only its event.**

## Assembly is bounded in work

- **A hang on your thread is closed.** Each pass over an event's `fields` now stops after 131,072
  values visited or 16 MiB of text charged. A value that would cross either limit becomes
  `<node limit>` or `<size limit>`, the event is marked `truncated`, and nothing after it is
  visited. Before, a list shared 256 ways at each of seven levels (seven lists of 256 pointers in
  memory) was walked as a tree: against `v1.0.1` it did not finish within a 60 second timeout, and
  against this release it returns in a few hundredths of a second with `<node limit>` in the
  output. Both limits are private constants; no config key was added.
- **The defaults do not reach the byte limit.** `max_value_bytes` defaults to 8,192, so an ordinary
  configuration clips a long string long before 16 MiB. It matters only if you raised the ceiling:
  with `max_value_bytes` at 64 MiB, a 17 MiB string that `v1.0.1` delivered whole now arrives as
  `<size limit>`, and the second of two 9 MiB strings in one event does too.
- **A `bytes` or `bytearray` subclass that overrides `__bytes__` is rendered from the bytes it
  stores.** `v1.0.1` rendered whatever the override returned. The reads that produce text are also
  bounded by the ceiling now, which `docs/spec-delivery/SPEC-057-assembly-work-budget.md` describes
  in full, including the types it treats as an impostor.
- **It costs a little on the hot path.** Re-run for this release on three five-field events (mixed
  values, short strings, integers), `sanitize_fields` took about a quarter longer per call at commit
  `061d085` than at the `v1.0.1` tag (CPython 3.13.1, default configuration, minimum of 30 repeats,
  two interleaved runs each). Absolute times depend on the machine; the ratio held on every shape.

## One sink fixed on its own

- **`LokiSink` timestamps are exact.** The conversion to epoch nanoseconds scaled float seconds by
  `1e9`, which is inexact at current epochs: `2026-10-05T12:34:56.789Z` became `1791203696788999936`
  and truncates to the wrong millisecond. It now counts whole microseconds, so the same timestamp is
  `1791203696789000000`. A timestamp that is absent or cannot be parsed still falls back to the
  time of emit. `LokiSink` is the only caller. (#255)

## What did not change

- No public name, signature or default. A symbol-by-symbol comparison of every module's `__all__`,
  public functions, classes and `__init__` signatures between `v1.0.1` and this release found
  nothing changed except private additions (`sinks/_deferral.py`, and a required `pending` argument
  on the private `SocketTransport.send_all`).
- No dependency changed for you. `pyproject.toml` is unchanged; the lockfile, CI action pins and
  development tooling moved, which affects how the library is built and audited and not what it
  installs.
- The `1.x` freeze is unchanged: behaviour is not frozen by it, and every change here fixes a
  defect except one. The 16 MiB per-pass text bound is a new limit, taken to close the hang above; it
  changes what a configuration with `max_value_bytes` raised past 16 MiB delivers.
