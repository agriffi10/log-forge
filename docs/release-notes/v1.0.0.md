**The first stable release.** The public API is now under semantic versioning: everything in
`log_foundry.__all__`, the `Sink` protocol, and every shipped sink class keep their behaviour
across `1.x`.

`1.0.0` is not a feature release. The API has been signature-stable since `v0.7.0` — an AST diff
of every public symbol across that range shows zero removals or renames and three additive keyword
parameters. What changed is the part that decides whether you can trust a logging library: its
failure modes. A ten-spec audit arc (SPEC-024..033) went through every path where the library
could lose an event, fail its caller, or report health it could not back up, and closed them.

## What that arc fixed

Each of these was a real, measured defect, not a hypothetical:

- **Per-request context leaked between requests.** Baggage and an adopted trace context were
  written into `contextvars` and never taken back out, so on a thread serving requests
  sequentially one request's `user_id` reached the next request's events, and a warm container
  kept joining a trace whose process had exited. Both are now released at the root span.
  *This is the one finding that put **wrong** data in your logs rather than losing it.*
- **Sinks that lost everything reported success.** A dead syslog socket produced `flush() == True`
  and an all-zero `health()` while every message was lost. A sink that delivered nothing now
  raises, so the retry engages and the loss is counted; one that absorbed partial loss reports it
  through `health().sink`.
- **A sink's backoff paused all delivery, including through `shutdown()`.** `HTTPSink` passed a
  server-supplied `Retry-After` straight to `time.sleep` — a measured `Retry-After: 8` blocked
  `shutdown()` for 22 s, and `86400` would have stalled logging for a day. Every wait is now
  bounded, clamped, and cut short by a shutdown.
- **Concurrent emitters could corrupt a sink.** A level call with no active span emits on your
  thread, against the same sink object the worker is draining into. Unlocked, `SQLiteSink` did not
  merely lose rows — it killed the interpreter with a bus error. The sinks holding transport state
  now lock.
- **Closed sinks silently accepted work.** `KafkaSink` produced into a batch nothing would flush,
  and the Redis sinks *succeeded* by reconnecting a client they had just disconnected. They refuse
  now.
- **Two lifecycle mistakes were invisible.** Logging after `shutdown()`, and a late
  `configure(sink=...)` that updated what `get_config()` reported while every event continued to
  the old sink (measured: sink A got 4 events, B got 0, the config claimed B). Both are now
  reported, and the swap actually swaps — on the buffered path and, as of the last spec in the
  arc, on the synchronous one too.
- **Diagnostics could leak your data.** Twelve of the library's stderr sites printed
  `repr(exception)`, and a psycopg repr reprints the statement *and* its bound parameters. Every
  line the library writes about itself now names an exception by type only.

## `Health` gains five fields

`sink`, `retired`, `submitted_after_shutdown`, `incomplete_swaps` and `closing_sinks` join the
four that shipped in `v0.7.0`. `Health` is a `NamedTuple` and grows by **appending**, so every
existing field keeps its position — but unpacking it whole
(`queued, dropped, failed = health()`) now raises `ValueError`. **Read it by attribute.** That is
the only change here likely to break an upgrade, and appending is the only change `1.x` will make
to it.

The README's [Flushing and shutdown](https://github.com/agriffi10/log-forge#flushing-and-shutdown)
table gives each field's meaning and the fix it implies.

## Also worth knowing when upgrading from `0.10.x`

- **A custom sink's contract is now explicit**: raise on total failure, tolerate concurrent
  `emit`/`close`, and refuse after `close()` if you released transport state. `sinks/base.py`
  states it, and a lint enforces the roster. A sink written against `0.10.x` still satisfies the
  `Sink` protocol — the optional `losses()` and `stop_signal` are probed by name, not declared.
- **`shutdown()` takes a `timeout`** (additive; defaults to 30 s). An unbounded join in an
  `atexit` handler is a process that will not exit.
- Nothing was removed, renamed, or made stricter at the call site.
