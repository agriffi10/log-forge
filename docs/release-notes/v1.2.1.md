# The next log-foundry release — sinks count what their destination did not confirm, and the file and stream sinks never write a line twice

**A release under the `1.x` freeze: nothing removed and nothing renamed.** Whether it is
numbered 1.2.1 or 1.3.0 is decided when it is tagged, since the new keyword arguments below are
additive; nothing here depends on the number. `FileSink`,
`RotatingFileSink`, `StdoutSink` and `StderrSink` move onto the delivery engine that 1.2.0
introduced. A write that fails partway no longer leads the worker to write the batch's lines
again, and these sinks now count and announce what they lose. Each of the four gains `deliver`,
`log_foundry_counters` and `log_foundry_stop_signal`. Under a backlog the worker now sends
larger batches, and at exit it sends its backlog in batches it can finish inside the
`shutdown()` budget. An open span's events now ship about once a flush interval rather than only
when the span closes. Sinks now count what their destination did not confirm: a TCP `SyslogSink`
or `LogstashSink` frame written to a connection the collector closed, an event the Sentry SDK
discarded, and an AWS or `_bulk` reply that names no event are counted with a line where they were
silent, and `KafkaSink` and `GooglePubSubSink` move onto the delivery engine, each batch waiting for
the client's report on every message it handed over. Five sinks gain one keyword-only argument
each, appended after their others: `SQSSink` and `SNSSink` take `max_message_bytes`, which sets
their message limit, `SyslogSink` and `LogstashSink` take `ack_wait`, and `RabbitMQSink` takes
`confirm`. No existing argument's default changed (`FlushResult` gains five keyword fields, each
defaulting to zero, and `SinkLosses` one, `resent`, defaulting to zero, so a `SinkLosses` built
with `dropped=` and `failed=` still builds), though a TCP round's new wait for the collector's
acknowledgement is on unless `ack_wait=False` turns it off; no `configure()` setting was added,
and the core still has no runtime dependency. A `flush()`, `shutdown()` or
`configure()` made from a sink's own code, or from a signal handler or finalizer that interrupted
the library, no longer waits on the call it is inside, and `FlushResult.reason` gains
`"re-entrant"` for the `flush()` that would have. An event a sink sends again after a send that
may have landed it is now counted in `health().sink.resent` and announced, since it may be held
twice downstream. A sink's `log_foundry_stop_signal` is now an event of its own, assigned once
each time the sink is installed, rather than the worker's event assigned again at every refresh.

A `>=1,<2` pin takes this release without a code change, with thirty-three exceptions:

- code that matches the text of the file and stream sinks' loss lines, or of the lines a `TransformSink` or
  `FilteringSink` around a stream sink writes;
- code that relies on the worker resending a failed batch to one of the file or stream sinks whole;
- a subclass of one of them that overrides `emit`;
- code that alerts on `losses().failed` for the stream sinks, which never moved before;
- a sink that relies on being handed at most ten spans per call, or the whole exit backlog in
  one call, or a process that goes on running after an expired `shutdown()` and relies on the
  exit drain delivering its later batches late;
- a wrapper of your own whose `close()` leaves its member alone, configured over a sink it holds,
  where `configure()` used to close that sink;
- code that matches the text of the expired-`shutdown()` line or of the line a dying worker
  thread writes, or that reads the loss counters SPEC-088 corrects (*Fixed*, the event ledger);
- code that counts or matches `NATSSink`'s `publish_timeout` lines on the worker path, which a
  batch now writes only when its rounds end with events unresolved, naming only those;
- code that relies on a `NATSSink` call being refused at once while a publish abandoned at an
  earlier deadline is still pending, since a call within one `publish_timeout` of that abandonment
  now waits for it, which for a level call outside any span, for `flush()`'s step that flushes
  the sink, and for `configure(sink=…)` is on the application's own thread, so a
  `flush(timeout)` can overrun its timeout by up to one `publish_timeout`;
- code that compares a `flush()` result with `==`, or reads its `repr()`, since both now include
  the result's loss counts;
- a `flush(timeout=None)` whose drain thread dies under it, which now waits until that thread
  has counted the events it held, where it returned `"abandoned"` at once;
- code that sets `SQSSink.MAX_BYTES` or `SNSSink.MAX_BYTES` above 1,048,576;
- a sink or a downstream consumer that relies on a span's events arriving in one batch, or on
  `span.start` arriving before the span's logs;
- a `continue_trace()` made after the root span has logged, which can now be refused, or code
  that matches the text of its rejection line;
- a `shutdown()` inside the process's first traced call, after which that call's later events
  are now counted as submitted after shutdown rather than delivered;
- code that counts or matches a sink's or the delivery engine's stderr lines at exit, which are
  now folded after the first abandoned exit batch;
- a sink, signal handler or finalizer that calls `flush()` or `shutdown()` from inside the library
  and relies on the call having done its work when it returns: `flush()` there now returns at
  once with `"re-entrant"`, and `shutdown()` can return before its stop has run;
- code that compares a `SinkLosses` by its `repr`, by `dataclasses.astuple` or by
  `dataclasses.fields`, each of which now includes `resent`, so the `repr` ends `, resent=0)`
  even when nothing was resent;
- code that relies on `SinkLosses` or `Health` equality or hash: two snapshots that were equal
  differ once `resent` does, and so do their hashes;
- code that matches stderr: a run that resent an event a send may have landed writes the new
  line `log-foundry: resent <n> event(s) a lost reply may have landed; they may be duplicated;
  <Sink>`, which is not a loss, yet contains the words "lost reply", so a filter such as
  `"lost" in line` matches it;
- code that relies on `MongoDBSink`'s `failed` counting a document whose driver-stamped `_id` was
  refused as a duplicate on the sink's own resend: that document is now delivered, counted
  nowhere and announced by no line;
- a subclass of `HTTPSink` that assigns `_counter_lock` before calling `super().__init__()`, or
  holds it while calling `log_foundry_counters.losses()`: `_counter_lock` is now the counters'
  lock, so assign it only after `super().__init__()`, and never hold it around that call, which
  takes the same lock;
- a sink that relies on its `log_foundry_stop_signal` setter running at every refresh with a fresh
  event, or on finding that event unset when it is delivered to after `shutdown()` with no
  `configure()` between;
- code that relies on a TCP `SyslogSink` or `LogstashSink` batch returning as soon as its frames
  are written, since each now waits up to 0.25 s for the collector's acknowledgement unless
  `ack_wait=False`, or on a connection the collector half-closed being kept, since it is now
  replaced before the next batch;
- code that relies on silence from a TCP `SyslogSink` or `LogstashSink` whose collector closed the
  connection: the frames written to it are now counted in `losses().failed` with a line;
- code that relies on silence from `SentrySink` over events the Sentry SDK discarded at capture,
  sampled out or dropped by `before_send` included: they are now counted in `losses().dropped` with
  a line, and a stand-in `client=` whose `capture_event` returns nothing reads as discarding
  everything;
- code that relies on an SQS, SNS, Kinesis, Firehose or `_bulk` reply that names no event, a test
  stand-in returning `{}` among them, reading as delivered: it is now counted with a line;
- code that matches the text of an unread SQS or SNS reply's line, which now ends `may have landed,
  not retried`;
- code that relies on a `KafkaSink` or `GooglePubSubSink` batch returning as soon as the client
  took each message, since each now waits for its reports: about one broker round trip, the whole
  `flush_timeout` or `overflow_timeout` against a broker that never answers, on your own thread for
  a log call outside any span;
- code that reads a `KafkaSink` or `GooglePubSubSink` loss counted after its batch returned — by a
  later batch, by the `flush()` hook or at `close()` — since every loss is now counted once by the
  batch's own round, with one line per round;
- code that relies on `flush()`'s verdict over these two sinks: a batch whose every report is a
  definitive refusal now makes it false, where it was true, and a Kafka message still queued no
  longer makes it false with `"sink-flush"`, because the `flush()` hook no longer waits or raises;
- code that relies on `GooglePubSubSink`'s `max_pending` bounding the publishes in flight, which it
  no longer does;
- code that relies on a `FilteringSink` or `TransformSink` over either sink calling its `emit`, or
  on either sink's raising `emit` counting nothing, since both are now delivery-engine sinks.

*Changed* lists the first five, the tenth to the seventeenth and the twenty-first to the
thirty-third, *Fixed* the sixth to the ninth, and *Added* the eighteenth to the twentieth.
*Added* lists the new public names: `EventLedger`; `max_message_bytes`, which `SQSSink` and
`SNSSink` each take as an argument and keep as an attribute; `SinkLosses.resent`, with
`SinkCounters.resent_events`, the counter it reads; `ack_wait` on `SyslogSink` and
`LogstashSink` and `confirm` on `RabbitMQSink`; `SentrySink.discarded`; `dropped_unadjudicated` on
`SQSSink` and `SNSSink`; and, on `KafkaSink` and `GooglePubSubSink`, `deliver` and
`log_foundry_counters`, with `log_foundry_stop_signal` on `KafkaSink`. Each is an addition a pinned
caller need not use.

**This release follows `1.2.0`.** It carries SPEC-082 (the file sinks), SPEC-084 (the stream
sinks), SPEC-087 (a sink the old and the new sink graph share), SPEC-088 (the event ledger),
SPEC-089 (the loss counts on a `flush()` result), SPEC-093 (sinks count what their destination did
not confirm), SPEC-094 (`KafkaSink` and `GooglePubSubSink` wait for each batch's delivery reports),
SPEC-090 (larger batches under a backlog,
and an exit drain that sends its backlog in batches), SPEC-102 (a JetStream `NATSSink` resends
the tail its deadline left unattempted), SPEC-096 (the message limit `SQSSink` and `SNSSink`
take), SPEC-091 (an open span's events ship on the worker's interval), SPEC-103 (a dead
sink's repeated lines at exit are folded), SPEC-104 (a `NATSSink` call waits out a publish
abandoned less than one `publish_timeout` ago), SPEC-097 (a call made from inside the library
never waits on the call it is inside), SPEC-095 (a resend of an event a send may have landed
is counted and announced) and SPEC-098 (one stop signal per sink, assigned once per
installation). It closes the 1.2.0 known
gap *A file or stream write that fails partway can leave lines written twice*.

## Added

### Every accepted event is counted in one term: `health().events` (SPEC-088)

`Health` gains one field, `events`, appended and defaulting to an all-zero ledger, so a `Health`
built by keyword still constructs and a reader never tests the field for `None`. It holds an
`EventLedger`, a new public frozen keyword-only type exported from `log_foundry` and
`log_foundry.worker`. Every event is credited to `accepted` at the call that asks for it, and is
then in exactly one other term: the gauges `open_spans`, `queued` and `in_flight`, the exits
`delivered` and `skipped`, or the losses `in_span_lost`, `orphan_lost`, `overflow_lost`,
`batch_lost`, `sink_lost`, `drain_lost` and `stranded`; the properties `pending` and `lost` sum the
gauges and the losses. `unaccounted` is the events the terms cannot place, zero in a correct
library, and `shutdown()` writes one line when it ends above zero, never raising:
`log-foundry: lost <n> event(s); the event ledger does not balance at shutdown(): these are in no term; health().events.unaccounted counts them`.
`events.queued` counts events where `queued` counts submissions and markers, and
`events.in_span_lost` and `events.orphan_lost` are the existing fields. No existing field changes
its unit. README → *Flushing and shutdown* → *The event ledger* lists the terms.

### `SQSSink` and `SNSSink` take `max_message_bytes` (SPEC-096)

Each sink gains one keyword-only argument, appended after its others:
`max_message_bytes: int | None = None`, the most bytes one message may cost and the most a
request's messages may cost together. Pass your queue's or topic's `MaximumMessageSize`, in bytes:
`1048576` for a queue created at the SQS default. The value is read as an `int`, so a `bool` or
an `int` subclass is taken as the `int` it holds, and it is refused when the sink is built, before
any client is: with `TypeError` if it is not an `int`, and with `ValueError` outside 1,024 to
1,048,576, the range AWS gives `MaximumMessageSize`. The default, `None`, keeps 1.x's limit, the
class's `MAX_BYTES` of 262,144 bytes (256 KiB), read as in 1.x, so an assignment on the instance
or a subclass's override still sets it; a value you pass wins over `MAX_BYTES`. The sink keeps the
value as `sink.max_message_bytes`. Whatever the limit, it is capped at 1,048,576 bytes, the most
SQS and any SNS topic take, so no message and no request is sized past 1 MiB. A message over the
limit is dropped, counted in `dropped_oversized` and announced by the oversize line, which names
the limit applied. README → *AWS — the durable-buffer path* says why the default stays 256 KiB.

### A resend after a lost reply is counted: `SinkLosses.resent` (SPEC-095)

When a sink's call times out, loses its connection or gets a `5xx` after the request left, the
destination may have stored the batch, and the library sends it again within its existing retry
rounds. That resend could leave a second copy, and nothing said so: a standard SQS queue held 35
messages for 25 events with `failed=0` and no line. Each such resend is now counted and announced.
The resend itself is unchanged, and no request carries another byte.

- **`SinkLosses` gains `resent: int = 0`**, appended after `failed`, so `health().sink.resent`
  reports it and a `SinkLosses` built by keyword still builds and still equals one with
  `resent=0`. Every shipped sink's `losses()` reports it, and a `MultiSink`'s is the sum of its
  children's.
- **`SinkCounters` gains `resent_events`**, which the delivery engine alone writes, on a run that
  settled and on one that failed, since the sends happened either way.
- **One stderr line per batch that resent anything**:
  `log-foundry: resent <n> event(s) a lost reply may have landed; they may be duplicated; <Sink>`.
  It is not a loss. At exit, after a batch has been abandoned, it is folded like the loss lines.
- **What it counts.** Each time the engine sends an event again after a call that may have landed
  it. A call the sink can show never left is not counted: on the HTTP family and the socket
  sinks a refused connection or a name that did not resolve, a `429`, and on every sink an entry
  the service's reply names as failed (*Changed* lists the sinks that cannot tell a refused
  connection apart). `resent` is an
  upper bound: a FIFO queue inside its 5-minute de-duplication interval, or a client that retried
  inside the call and landed nothing, adds no copy but is counted. It does not count a third-party
  sink's resends, `NATSSink`'s, or the worker's whole-batch resend of a sink with no `deliver`.
- **The de-duplication key is the event's `log_id`**, already in every body and already the
  `MessageDeduplicationId` of an SQS FIFO message; no new key, header or field was added. An event
  no later send landed is still counted in `losses().failed`, and `flush()` is still falsy for a
  batch none of whose sends was confirmed.

### `SyslogSink` and `LogstashSink` take `ack_wait`, and `RabbitMQSink` takes `confirm` (SPEC-093)

- **`ack_wait: bool | None = None`**, keyword-only, appended to `SyslogSink` and, before
  `**http_kwargs`, to `LogstashSink`. Over TCP, `None` and `True` end each batch waiting for the
  collector to acknowledge what it wrote (see *Changed*); `False` keeps the connection checks and
  drops the wait, which gives up a close whose reset arrives late, as on a link with some delay or
  on macOS. A value that is neither `None` nor a `bool` is a `TypeError` naming `ack_wait` in
  every mode, `LogstashSink(url=...)` included, judged before any other argument and never read
  for its truth; a `bool` with `transport="udp"`, or beside `LogstashSink`'s `url=`, is a
  `ValueError`; all before anything is built.
- **`confirm: bool = False`**, keyword-only, appended to `RabbitMQSink`. With `confirm=True` each
  channel the sink opens is put in confirm mode and each publish is sent `mandatory`, for a
  connection it opened or one you passed in. A publish the broker acked is delivered; one it
  returned as unroutable (`UnroutableError`) or nacked (`NackError`) is counted in
  `losses().failed` with the line `RabbitMQSink, N attempt(s), <Type>` and not re-sent; one whose
  connection was lost before the confirm is counted as may have landed, `RabbitMQSink, no confirm
  before the connection was lost (<Type>); may have landed, not retried`, and not re-sent. Before
  each batch the sink checks a connection it opened and reopens one that died while idle; one you
  passed in is not checked, since that would run your consumer callbacks on the worker's thread,
  so a publish on one that died while idle reads as a lost confirm. A confirm costs a broker round
  trip per message: one 1,000-event batch took about 0.25 s at a 0.2 ms round trip, 1.1 s at 1 ms
  and 5.4 s at 5 ms, longer than `flush()`'s 5 s default. A value that is not a `bool` is a
  `TypeError`. The default publishes as before.

### `SentrySink`, `SQSSink` and `SNSSink` each gain a counter (SPEC-093)

- **`SentrySink.discarded`** counts the events the Sentry SDK discarded at capture, which
  `losses()` reports as `dropped` (see *Changed*).
- **`SQSSink.dropped_unadjudicated`** and **`SNSSink.dropped_unadjudicated`** count the entries a
  reply did not adjudicate. On these two sinks it is a sub-count of `failed`, which already holds
  those entries, so `losses().failed` is unchanged by it and the two are not to be added. On
  `KinesisSink`, `FirehoseSink` and the HTTP sinks, which already had it, it stays outside the
  instance's `failed`, as before. A new sink reads zero.

### `KafkaSink` and `GooglePubSubSink` offer `deliver` (SPEC-094)

Both are now delivery-engine sinks: each gains `deliver`, which reports every event's fate,
`log_foundry_counters`, and its `emit` becomes the engine's inline adapter; `KafkaSink` also gains
`log_foundry_stop_signal`, which `GooglePubSubSink` already had. `failed` and `rejected` stay
assignable, now over the engine's counters, and `losses()`, `flush()` and `close()` keep their
names. A `FilteringSink` or `TransformSink` around either now offers `deliver` too. Neither
constructor's signature changed.

## Changed

### The file sinks resend only what did not land (SPEC-082)

- A `FileSink` or `RotatingFileSink` write that fails partway returns where it raised. What did
  not land is counted in `losses().failed`. Through the worker it is resent, and only it is.
- On a run of one round, an inline `emit` or a `MultiSink` child, a partial write loses the rest
  of that batch, counted. 1.x could deliver it, with the head of the batch on disk twice.
- `failed` counts each lost event once per run, not once per worker attempt.
- An error no resend cures (`EACCES`, `EPERM`, `EROFS`, an `OSError` with no `errno`, or any
  exception that is not an `OSError`) costs one attempt. 1.x's worker resent on every raise.
- A closed file-sink subclass that inherits `emit` is not resent, even if it would re-open
  itself. A subclass that wants the resend overrides `emit`.
- The loss line reads `<Class>, N attempt(s), <Type>` where 1.x wrote `<Class>, <Type>`. Each is
  followed by `errno=N` only when the exception carries one. Some events have a line of their
  own that ends `; outcome unknown; they may have landed`: those whose line a write cut partway,
  and which the run will not offer again. The next write finishes such a line, and the event is
  still counted in `failed`.
- A codec that is not a text encoding is refused at construction, now before any file is
  created.
- `FileSink(fifo, encoding="utf-8-sig")` no longer writes a byte order mark into a pipe. 1.x
  wrote one on every open, including a second open of the same FIFO. `utf-16` and `utf-32` wrote
  none into a pipe and write none now.
- A third-party wrapper whose `emit` calls the file sink's `emit` is a one-round caller too, like
  the inline `emit` and a `MultiSink` child. When a write lands part of a batch, the rest is lost
  and counted, and `emit` returns. The count shows in two places:
  - the file sink's own `losses()`;
  - its `lost N event(s); FileSink, 1 attempt(s), OSError errno=N` line, with the torn event on
    a line of its own that says it may have landed.

  It shows nowhere the worker reads: `flush()` returns true with every loss count at zero,
  `failed_batches` stays 0, and
  `health().sink` stays `None` for a wrapper that offers no `losses()`. In 1.x the raise reached
  the worker through the wrapper, and its resend put the head of the batch on disk twice.
- When a file sink lands nothing of an orphan log, one written outside any span, the loss is
  announced by the engine's line. The sink writes `lost 1 event(s); FileSink, 1 attempt(s),
  OSError errno=N`, and the orphan path then writes `lost 1 event(s); orphan log not delivered
  after 1 delivery round(s)`. In 1.x, for the same `ENOSPC`, the sink's line had no
  `1 attempt(s),` and the second line was `absorbed a failure while emitting an orphan log
  (OSError); the event was lost`. `orphan_lost` and `losses()` count the same as before.
- For the `iso2022_*` codecs, a file sink appending to a non-empty file no longer writes the
  three bytes `ESC ( B` ahead of its first line, which 1.x's text stream wrote there. Every
  other codec into a regular file, and these codecs into an empty file, get the bytes 1.x wrote.

### The stream sinks never hand the stream a line twice, and count what they lose (SPEC-084)

- **`StdoutSink` and `StderrSink` now count `failed`.** Each event that did not land is in
  `losses().failed` once per run. In 1.x these sinks counted no `failed` at all, and only the
  worker's abandon line said anything. Each loss is announced on a line of the sink's own, such
  as `lost 3 event(s); StdoutSink, 4 attempt(s), OSError errno=28`. The lines the stream was
  handed before the fault are on a line of their own that ends `; outcome unknown; they may have
  landed`, or `; after an earlier fault; they may have landed` while a fault persists.
  `losses()` is still `None` until something is counted.
- **A failed run raises both types.** When nothing of a batch landed, `emit` raises an instance
  of both the stream's own exception class and `SinkDeliveryError`, with the original as
  `__cause__`. So `except OSError`, `except BrokenPipeError`, `except ValueError` and
  `except SinkDeliveryError` all still catch it. 1.x raised the stream's exception itself.
- **An error no resend cures costs one attempt.** Only `ENOSPC`, `EDQUOT`, `EFBIG`, `EIO` and
  `EAGAIN` are retried. These fail at the first attempt:
  - a broken pipe (`EPIPE`) or `EBADF`;
  - an `OSError` with no `errno`;
  - a closed stream's `ValueError`;
  - any exception that is not an `OSError`.

  1.x's worker resent the batch on every raise.
- **A fault's handed lines are counted rather than written again.** When a buffered stream
  raises partway through a batch, the lines it was already handed are counted in `failed`, as
  lines that may have landed, and are never handed to it again. The lines not yet handed are
  resent through the worker when the error is retryable. 1.x's worker resent the whole batch,
  writing up to all of it twice. On a run of one round, an inline `emit`, a log outside any span
  or a `MultiSink` child, the lines not yet handed are counted lost and not resent.
- **On a buffered stream, the batch during which a fault begins returns, and later batches
  raise.** That batch has handed lines whose fate is unknown, so it settles with them counted,
  where 1.x's `emit` raised. While the fault lasts, every later batch raises. On the unbuffered
  stream that `python -u` gives `sys.stdout`, a line written before the fault is known to have
  landed, and a batch of which nothing landed raises.
- **A wrapper around a stream sink takes the engine path.** A `TransformSink` or `FilteringSink`
  around a stream sink now offers `deliver`, so a caller-code failure writes a different line.
  The counts are unchanged.
  - `TransformSink` now writes `absorbed a failure while transforming a batch (ValueError);
    TransformSink did not forward 1 event(s) its function failed on`, in place of
    `lost 1 event(s); TransformSink, the transform failed with ValueError`.
  - `FilteringSink` now writes `absorbed a failure while filtering a batch (<Type>);
    FilteringSink did not forward N event(s) its predicate failed on`, in place of
    `lost N event(s); FilteringSink, the predicate raised <Type>`.
- **A subclass that overrides `emit` and calls `super().emit` runs one round per call.** A
  retryable tail is therefore counted lost, where 1.x's worker resent the whole batch. If a
  sustained fault clears between the worker's attempts, such a subclass can also write a line
  twice: a line the stream did take during the fault is resent.

### Under a backlog the worker sends larger batches, and the exit drain sends its backlog in batches (SPEC-090)

No argument, setting or environment variable was added; the queue still holds 10,000
submissions. What you can see:

- **A sink sees batches of up to 1,000 events under a backlog, where it saw ten spans.** While
  more is waiting in the queue, a batch grows by whole spans up to what the sink delivered in half
  a flush interval on its last batch, and never past 1,000 events unless it holds ten spans or
  fewer, which a batch could always be. With nothing waiting a batch is ten spans or a second's
  worth, as before. A burst therefore drains in a few large calls: 30,000 spans into a sink
  costing 20 ms a call left its queue in under a second, where it took more than 25 seconds in
  calls of 20 events, and fewer were dropped to a full queue.
- **A sink sees several batches at exit, where it saw one.** `shutdown()` sends what was queued
  when it began by the same rule, so the exit hands no sink more than 1,000 events in one call
  unless the batch holds ten spans or fewer. Submissions made after the exit drain began stay
  queued and are counted, as before, rather than keeping it running.
- **A `flush()` marker met at exit is answered in queue order**, once the batches carrying the
  events ahead of it are sent, where it was answered only after the whole backlog.
- **The expired-`shutdown()` line's in-flight figure can name more than one batch's events.**
  The figure is `health().events.in_flight`, as SPEC-088 made it; what changes is what the worker
  thread can hold when the join expires: besides the batch inside the sink, the batch it was
  building and at most one span it carried over, so the figure counts all three.
- **An exit drain predicted to overrun declines its later batches.** The first batch of the exit
  is always attempted. A later batch predicted, from the longest call the exit has made so far, to
  end after the `shutdown()` deadline, and every batch after it, is not attempted: each moves
  `failed_batches` by one, its events go to `health().events.batch_lost`, and all of them are
  named in one line,
  `log-foundry: lost <n> event(s); <k> exit batch(es) declined unattempted; each was predicted to end after the shutdown() deadline`.
  So the join normally completes and `close()` runs, where the join used to expire with the sink
  left open. The prediction can still run short: a first batch that alone takes longer than the
  budget, a batch the exit has grown since, a retry after a call that failed at once, or a sink
  that turns much slower partway through the exit can still run past the deadline and leave the
  sink open.
  In a process that goes on running after an expired `shutdown()`, those batches used to be
  delivered late by the worker thread; they are now counted lost.
- **The exit drain's abandoned batches after its first share one line.** The first abandoned exit
  batch writes the usual line, and the rest are tallied into one,
  `log-foundry: lost <n> event(s); <k> more exit batch(es) abandoned`, so a dead sink at exit
  writes a few of the worker's own lines rather than one per batch. When the join expires, that
  line comes before the expiry line. An abandoned exit batch leaves the batch size as it was, so a
  sink that dies at the stop is handed the exit backlog in batches of up to 1,000 events, and one
  already failing before the `shutdown()` in batches of `batch_size` spans (ten by default).
- **A dead sink's own lines at exit are folded** (SPEC-103). A sink that writes its own line per
  failed call, as `HTTPSink` does, and the delivery engine's per-run lines used to be written once
  per exit batch. From the first abandoned exit batch on, those lines are folded: each distinct
  line is written once more at the end of the exit, with its summed count and a new tail,
  `log-foundry: lost <n> request(s); <detail>; <k> line(s) folded at exit` (and likewise for an
  `absorbed` or a pending line). So a dead sink at exit writes a few folded lines: a refusing
  `HTTPSink` with 10,000 spans at exit, already failing before the `shutdown()`, writes 6 lines
  where it wrote 1,004, and its requests are unchanged. When the join expires, the folded lines
  come before the expiry line, and a line written after that is written at once. The worker's own
  lines are never folded. Code that counts a sink's exit lines, or matches their text, sees the
  new tail.

### `SQSSink` and `SNSSink` never size a message or a request past 1 MiB (SPEC-096)

- **A `MAX_BYTES` set above 1,048,576 on an instance or a subclass is capped at 1,048,576.** A
  message over 1 MiB is now dropped alone, counted in `dropped_oversized` and named in the
  oversize line, `SQSSink, <size> bytes exceeds the 1048576-byte message limit` or
  `SNSSink, exceeds the 1048576-byte message limit`, where it was sent and, when the service
  refused it, counted in `failed`. Requests are split under 1 MiB: at a `MAX_BYTES` of 2 MiB, six
  300 KiB events went out in one request, and when the service refused it all six were counted in
  `failed`; they now go out in requests of at most 1 MiB.
- **An `SNSSink` request is costed in UTF-8 bytes**, the unit the topic counts, where it was
  costed in characters. The two agree for every body the default `_encode` writes, since
  `json.dumps` escapes every non-ASCII character, so no default request changes. A subclass whose
  `_encode` writes non-ASCII UTF-8 now has its requests split under the limit in bytes, where one
  could reach four times it.
- **Both sinks read their message limit once per `emit`.** A `MAX_BYTES` reassigned while an
  `emit` is retrying no longer reaches that `emit`'s later rounds; the next `emit` reads it. In
  1.x, `SNSSink` read it again every round. A limit set before `emit` behaves as before.

### `flush()` counts what the process lost while it ran, and stays truthy over it (SPEC-089)

A `flush()` whose drain finished could return a truthy result while the sink had lost the batch:
a sink on the verdict contract that dropped every event, answered every event unknown, or took
one and rejected the rest settled its run, and the loss showed only in `health().sink` and on
stderr. **What `bool(flush())` reports does not change**, and neither do the `reason` values.
A truthy result means the drain that carried the events finished and abandoned no batch while
the call was outstanding, not that the sink took every event. What is new is that the result
says what was lost.

- **`FlushResult` gains five `int` fields, each defaulting to 0, and a read-only `lost`** that is
  their sum: `overflow_lost`, `batch_lost`, `sink_lost`, `drain_lost` and `stranded`. Each is
  named for the `health().events` term it counts. They are keyword-only, `__match_args__` stays
  empty, and `ContinueResult` gains nothing.
- **The window.** Each count is the change in its term from just before the call sweeps open
  spans to the moment the drain answers the call's marker. Where no drain
  answers it (no worker, a retired worker, a timeout, a full queue), the call reads the end
  itself once it stops waiting. A loss debited before the call, such as a batch the worker's own
  trigger abandoned earlier, is outside the window and stays in `health()`.
- **The counts over-count.** They are process-wide, so they include other threads' events that
  were queued ahead of the call, other threads' submissions that overflowed while it waited, and
  any orphan log's `sink_lost` in the window. A non-zero count says the process lost events while
  the call ran, not that the caller's own events were among them.
- **What a zero count does not cover.** It covers only the terms the ledger counts. A loss a
  sink takes inside an `emit` that returned, such as a failed Kafka delivery report, a
  `MultiSink` child that raised beside one that accepted, or an `emit`-only sink's own internal
  loss, is in none of the counts and stays in `health().sink`. Events still pending when the
  window ends, and events the call's sweep leaves on open spans (each one's held `span.start`,
  and whatever is logged after the sweep), are in no count either; the latter are in
  `health().events.open_spans`. `in_span_lost` and `orphan_lost` are never counted on the result.
- **`repr()` and `==` include the counts.** A result whose window lost something is no longer
  equal to `FlushResult(ok=True)`; one whose window lost nothing still is.
- **A `flush()` whose drain thread dies under it now waits until that thread has counted the
  events it held** before it reads, so they (`drain_lost`) and the queue behind them
  (`stranded`) are counted. The wait is idle and lasts at most what is left of the call's
  timeout. With `timeout=None` it is unbounded, as the rest of the call is: such a call used to
  return `"abandoned"` at once, and now returns once the dying thread has counted its loss. That
  comes before the thread writes its stderr line, so the wait never includes the write, and a
  `flush()` made while its own thread holds a lock that `sys.stderr` needs returns as it did. A
  `flush()` made on the dying thread itself, from a replaced `sys.stderr`, does not wait.
- **A `flush()` reads its counts as `health()` reads the ledger**, under the ledger's
  registration lock, which a thread takes briefly for its first log. A `flush()` started while
  another thread is inside that section waits for it to end. A `flush()` or `shutdown()` made
  from code running inside it, such as a `__del__`, returns as it did before.

README → *Flushing and shutdown* gives the Lambda handler idiom, which now reads `drained.lost`
and `health().sink`.

### An open span's events ship about once a flush interval (SPEC-091)

A span's events used to wait on the span until it closed, so a process killed while a handler was
still running, as a Lambda timeout or an out-of-memory kill does, lost every event that handler
had logged, uncounted. No argument, setting or environment variable was added; the cadence is the
worker's existing flush interval, a second by default. What you can see:

- **An open span's events reach the sink about once a flush interval, before its `span.start`
  and `span.end`.** The worker takes what every open span has buffered past its `span.start` and
  ships each span's take as a submission of its own. `span.start` stays on the span so that it
  carries the span's final baggage, and ships with `span.end` at the close. A span's events can
  therefore arrive in several batches, with its boundary events last. A process killed by
  `SIGKILL` 3.5 s into an open span now delivers 50 of its 51 events, where it delivered none.
- **`flush()` reaches every thread's and task's open spans**, not only the calling context's. The
  caller's own spans still ship whole, `span.start` included; every other open span ships what it
  has buffered and keeps its `span.start`.
- **The exit drain ships what open spans hold.** `shutdown()`, and the drain at interpreter exit,
  take every open span's buffered events before they drain, so a daemon thread's span still open
  at exit delivers its logs, where it delivered none.
- **The worker is built when the first span opens**, not when it closes, so the process's first
  traced call is swept like any other. A sink's stop-signal setter therefore runs before that
  call's body rather than after it.
- **A `shutdown()` inside the process's first traced call now strands that call's later events,
  counted.** The worker exists when it runs, so it retires it: the call's `span.start`, `span.end`
  and later logs are counted in `submitted_after_shutdown` with the usual line, as they already
  were for every traced call after the first. The logs it had buffered before the `shutdown()`
  ship in the exit drain.
- **`continue_trace()` is refused once a sweep has taken from the root span**, so a call made
  after the root span has logged gets a verdict that depends on timing: the later the call, the
  likelier the refusal, and once a `flush()` has run after the log it is certain. On the entry
  point's first line it is never refused. The rejection line changes from
  `the current span has already been flushed; trace context refused` to
  `the current span's events have already been handed to the worker; trace context refused`.
  A `continue_trace()` made on a thread already inside a sweep, as a garbage-collector callback
  can be, is refused with `a sweep is in progress on this thread; trace context refused`. Both
  return `reason="rejected"`.
- **A take whose hand-in fails is counted in `in_span_lost`**, with a line saying the events taken
  were lost.
- **A sweep never drops.** When the queue is full, the events a sweep would have taken stay on
  their spans and ship at the close; a `flush()` whose sweep of other threads' spans meets a full
  queue leaves those events there, and its result is not made falsy by it.
- **A span's events can be split across a sink swap.** Those swept before a `configure(sink=…)`
  reach the old sink and the rest the new one, each event once.
- **An empty batch is no longer submitted.** A close that finds its span's buffer already empty
  submits nothing, where after a `shutdown()` it was counted as queued, counted as submitted after
  shutdown and announced as a lost submission.

**What a kill still loses.** `SIGKILL`, `SIGTERM` without a `shutdown()`, and `os._exit` lose up
to about one interval of an open span's events, every still-open span's `span.start`, and whatever
is queued or in a batch the sink has not yet accepted, and no counter survives to show it. The
worker takes from open spans between sends, so a kill while it is sending a batch or waiting to
retry one loses everything logged on open spans since it last took from them. README →
*Flushing and shutdown* → *Serverless / short-lived processes* says so.

### A call made from inside the library never waits on the call it is inside (SPEC-097)

A sink's own code, and a signal handler or finalizer that interrupts the library, can call
`flush()`, `shutdown()` or `configure()` while the library is doing something those calls would
wait for. Such a call used to wait on it, for a closer grace, a whole timeout, or for good. The
signatures of `flush()`, `shutdown()` and `configure()` did not change. What you can see:

- **`flush()` made on the drain thread, or from a signal handler or finalizer that interrupted
  the library inside one of its locks, returns at once**, with `ok` false and the new reason
  `"re-entrant"`, having swept, queued and counted nothing. It waited its whole timeout, or for
  ever with `timeout=None`. Code that matches `reason` exhaustively meets a new value, which the
  README says to expect.
- **`shutdown()` made from a sink's own code during a `configure(sink=...)` returns at once**, from
  the sink's stop-signal setter or its `emit` on the drain thread, and the shutdown runs when
  that `configure()` finishes, before it returns, within its swap budget. A close that shutdown
  starts and that outlives the budget goes on in the background, counted in
  `health().closing_sinks`, and the next `shutdown()` or the exit waits for it. It used to run
  under the change and close the sink the change was installing. A `configure()` that gave up
  waiting for another sink change and runs alongside it takes no shutdown: one from its
  stop-signal setter runs there and then, as in 1.2.0, and one from the drain thread runs when the
  other change finishes. If a `KeyboardInterrupt` or `SystemExit` cuts that `configure()` short,
  the shutdown deferred to it still runs as the change unwinds, before the exception propagates.
  Only an interrupt landing in the library's last step of the change, where it ends it, drops the
  shutdown rather than leaving it for a later call: the next `shutdown()`, or the exit, runs as it
  would have.
- **`shutdown()` made from a sink's own code during a `shutdown()`, its `close()` included,
  returns at once**, where it waited out the 2 s closer grace on the close it was inside.
- **`shutdown()` and `configure()` made from a signal handler or finalizer that interrupted the
  library inside one of its locks return at once**, and run when the interrupted library call
  returns, before any later `shutdown()`. They used to wait on a lock their own thread held, and
  the process hung for good. A handler that calls `shutdown()` and then `os._exit()` drains
  nothing when the signal landed inside the library; one that raises `SystemExit` instead, as
  `sys.exit()` does, has its `shutdown()` run as the interrupted call unwinds, before the exit
  drain, including inside a process's very first log or traced call; a held call that fails on
  that path is reported and never replaces the `SystemExit`. A
  `configure(sink=...)` held during a `shutdown()` runs once that shutdown is over, as a
  `configure()` made after `shutdown()` does, or sooner, at the end of a library call a sink's
  own code makes on that thread while the shutdown runs, such as a `close()` that logs.
- **Unchanged:** a sink's own `flush()` hook that calls `flush()`, `shutdown()` or `configure()`
  behaves as before, since the library calls that hook holding none of its locks.

### `MongoDBSink` counts its own resend refused on a duplicate `_id` as delivered (SPEC-095)

`MongoDBSink` keeps a batch's documents, with the `_id` the driver stamped on each, across its
retry rounds, so a resend after an `insert_many` that raised carries the same `_id`, and MongoDB
refuses the copy with a duplicate-key error (code `11000`). That refusal was counted in `failed`
and announced on a `lost` line, although the earlier send had stored the document. It is now read as
delivered, counted nowhere and announced by no line, when the duplicate is on the `_id` index, the
event carried no `_id` of its own, and an earlier call of the same batch carried the document and
raised. Any other duplicate key, including one on an `_id` your own `TransformSink` set, is still
refused and counted.

### The AWS, Event Hubs, Redis and ClickHouse sinks count every failed call they resend (SPEC-095)

`SQSSink`, `SNSSink`, `KinesisSink`, `FirehoseSink`, `AzureEventHubsSink`, `RedisStreamsSink`,
`RedisListSink` and `ClickHouseSink` use clients that retry inside the call, so a call that
finally raised may have landed on an earlier internal attempt, whatever the exception's class.
Each of these sinks therefore counts the resend of every call that raised in `resent`, including a
call whose connection was refused, which adds no copy: their `resent` is an upper bound. A
`FirehoseSink` record coded `ServiceUnavailableException` or `InternalFailure` counts too, since
AWS says such a write might have completed. The clients' own retries are unchanged.

### `HTTPSink`'s counter lock is its counters' lock (SPEC-095)

`HTTPSink` and every sink built on it, `SentrySink`'s HTTP backend included, now commit their own
counts and the delivery engine's in one commit under one lock, so `losses()` never reads a resend
without the request it belongs to. Its private `_counter_lock` is now that lock: a subclass that
assigns it must do so after `super().__init__()`, and must not hold it while calling
`log_foundry_counters.losses()`, which takes the same lock. No counter and no unit changed:
`failed` still counts requests.

### A sink holds one stop signal of its own (SPEC-098)

The library assigns `log_foundry_stop_signal` to a sink so that a `shutdown()` cuts its backoff
short. That event was the worker's, and the library assigned it again whenever the worker's event
changed. Each sink now holds one event of its own. The attribute keeps its name, its type and its
promise that the event is set when a shutdown starts, so a sink written to the README's protocol
needs no change. What you can see:

- **The setter runs at the sink's first delivery, and again when a `configure()` installs the
  sink anew**, with an event that is the sink's own, where it ran at every refresh with the
  worker's event. Two threads making a first delivery at once may both run it, with the same
  event.
- **After a `shutdown()`, a sink delivered to with no `configure()` between finds its event set.**
  Its own backoff waits collapse, and so do the delivery engine's waits on the orphan path; every
  attempt is still made, and worker-path rounds still wait on the worker's stop event. A sink that
  a `configure()` installs again after the shutdown finds its event cleared and backs off as
  before, except a sink a `sink_factory` returns again, which keeps the set event (*Known gaps*).
- **A sink first reached while a shutdown is running is given an event already set.**
- **A forked child's sink keeps the same event object, re-initialised, and its setter does not run
  in the child.** The child's `shutdown()` sets it and the parent's stays as it was. A child forked
  after its parent's `shutdown()` inherits the set event until it configures the sink again.

### A sink counts what its destination did not confirm (SPEC-093)

- **A TCP `SyslogSink` or `LogstashSink` counts the frames it wrote to a connection the collector
  had closed.** Each batch checks the connection before its first frame and replaces one the
  collector closed, so a half-closing collector costs a new connection each batch and loses
  nothing. Frames written to a connection a later write or the end-of-batch check finds closed are
  counted in `losses().failed`, once, with one line, `lost N message(s); SocketTransport, written to
  a connection its peer closed; may have landed, not retried`, and never re-sent. In 1.x they were
  reported delivered: a second batch of 50 after the collector closed lost up to 25 with nothing
  counted; now all 50 arrive, with nothing counted.
- **Each TCP batch ends by waiting for the collector to acknowledge what it wrote**, up to 0.25 s.
  That costs about one round trip plus the collector's delayed acknowledgement on every batch,
  measured at a median of 0.5 to 0.6 ms on loopback, 7.9 ms at 1 ms of delay each way and 44.2 ms
  at 10 ms; a collector that neither acknowledges nor resets costs each batch the whole 0.25 s.
  `ack_wait=False` turns the wait off (*Added*). On a platform whose send queue cannot be read,
  Windows among them, the batch does not wait.
- **`SentrySink` counts an event the Sentry SDK discarded at capture** — the SDK returned no event
  id, as it does for an event sampled out, dropped by `before_send` or an event processor, or with
  no transport — in `discarded`, reported as `losses().dropped`, with one line per batch,
  `lost N event(s); SentrySink, discarded by the Sentry SDK at capture`, where 1.x counted it as
  sent. Sampling and `before_send` drops therefore now move `dropped` and print a line, since the
  SDK reports them the same way as an event it cannot deliver. A stand-in `client=` whose
  `capture_event` returns nothing reads as discarding every event. A batch with any discard returns
  rather than raising. The HTTP fallback is unchanged.
- **An AWS reply that names no event is counted, not read as delivered.** An `SQSSink` or `SNSSink`
  reply with neither `Failed` nor `Successful`, `{}` among them, and a `KinesisSink` or
  `FirehoseSink` reply with neither a failed count nor a record array, now leave every entry of the
  call counted as may have landed and never re-sent; an SQS or SNS reply that lists `Successful`
  counts each entry it names in neither list the same way, with the line `lost N message(s);
  <Class>, a <call> reply named neither success nor failure for N entry(ies); may have landed, not
  retried`. A reply with only `Failed` reads as before. The line for an SQS or SNS reply the sink
  could not read now ends `may have landed, not retried` where it ended `not retried`. Each such
  entry is counted in `failed` and in `dropped_unadjudicated`, a sub-count of `failed` on `SQSSink`
  and `SNSSink` and outside the instance's `failed` on `KinesisSink` and `FirehoseSink`. A test
  stand-in that returns `{}` for success now reads as unadjudicated.
- **A `2xx` `_bulk` object carrying neither `errors` nor `items` is counted.** `ElasticsearchSink`
  and `OpenSearchSink` now count `{}` or an error document such as
  `{"error": {...}, "status": 500}` in `dropped_unadjudicated`, with a may-have-landed line, never
  re-sent, where 1.x read it as success. An object with `items` and no truthy `errors` still reads
  as success.

### `KafkaSink` and `GooglePubSubSink` wait for each batch's delivery reports (SPEC-094)

- **Each batch waits for the client's report on every message it handed over**, within the sink's
  existing timeout, `flush_timeout` (10 s by default) or `overflow_timeout` (30 s by default), and
  until a shutdown's stop signal once the first 50 ms have passed. A batch costs about one broker
  round trip; against a real Kafka broker a batch of ten took a few milliseconds whatever
  `linger.ms` was. A report that arrives after its batch returned changes nothing. Since a sink's
  stop signal stays set after a `shutdown()` until a `configure()` installs it again (SPEC-098), a
  batch delivered to either sink in that window also waits only its first 50 ms.
- **With one Kafka partition stuck, only that partition's messages wait the timeout**, and each
  later batch pays one 50 ms slice; a single blocking flush would have held every later batch for
  the whole timeout.
- **Against a broker that never answers, each batch waits the whole timeout**, and so does a log
  call outside any span, on your own thread.
- **A definitive refusal fails the batch; every other report is counted as may have landed.** A
  refusal that no attempt the client made could have got past — Kafka's codes 21
  (`INVALID_REQUIRED_ACKS`) and 87 (`INVALID_RECORD`), Pub/Sub's `InvalidArgument`, and the
  `FlowControlLimitError` a full Pub/Sub client queue sets — is counted in `failed` with its 1.x
  line, and a batch of nothing else fails, so `flush()` reads false and `failed_batches` moves.
  Every other report, size refusals (Kafka 10 and 18) and authorization refusals (Kafka 29,
  Pub/Sub `PermissionDenied`) among them, and no report by the deadline, is counted in `failed`
  with one line per batch, `KafkaSink, no definitive delivery report within <t>s; may have landed,
  not retried` or `GooglePubSubSink publish unconfirmed (<Type>); may have landed, not retried`,
  never re-sent, and `flush()` stays truthy: a truthy `flush()` means every event was acknowledged
  or counted.
- **The `flush()` hook no longer waits or raises.** `KafkaSink.flush()` serves any pending report
  and returns; `GooglePubSubSink.flush()` has no verdict outstanding to wait for. In 1.x a Kafka message still
  queued made `log_foundry.flush()` falsy with `reason="sink-flush"`, and at the defaults overran
  its 5 s budget.
- **Nothing is counted after a batch's verdict, and the close counts nothing.** `failed` counts
  each lost message once per batch where 1.x counted at every report, and the counts `close()` made
  of messages still queued, or handed over while it was closing, are gone. `close()` still flushes
  the Kafka producer, so a message counted as may have landed can still land, and
  `GooglePubSubSink.close()` waits up to `overflow_timeout`, whatever the shutdown's stop signal
  says, for the publishes its batches counted as may have landed, so a normal exit lets the
  client finish sending them rather than ending its sending thread. That close runs inline, so
  against a Pub/Sub server that never answers an explicit `shutdown(timeout=t)` can return up to
  `overflow_timeout` after `t`, as 1.x's close could and as `KafkaSink.close()`'s flush within
  `flush_timeout` can.
- **`GooglePubSubSink`'s `max_pending` has no effect.** Every publish has its verdict when its
  batch returns, so there is nothing for it to bound; it is still accepted and checked.
- **A `FilteringSink` or `TransformSink` around either sink offers `deliver`**, so the worker
  retries the wrapped sink as it would retry it alone.
- **Their `emit` counts a failed batch before it raises.** It is the engine's inline adapter, which
  counts the batch's events in `failed` before it raises, where 1.x's raising `emit` counted
  nothing.

## Fixed

### A sink `configure()` installs is no longer closed twice when a `shutdown()` closed it before the change decided (SPEC-097)

A `configure(sink=S)` writes S to the configuration before it retargets the worker. A
`shutdown()` landing in between, on another thread or from a sink's own code, could close S, after
which the change armed S again and the exit closed it a second time with nothing written in
between. Forced, that happened on every run; unforced, the model soak found it 1 to 3 times in
9,000 runs.
A `shutdown()` on another thread now meets the change from its configuration write, and a change
whose sink such a `shutdown()` already closed does not arm it again, where no worker is running or
the worker declined the new sink. A `shutdown()` made from a sink's own code during the change
runs when the change ends. S is closed once.

One case remains: a `shutdown()` on another thread that gives up waiting for a change whose
worker already accepted the new sink still closes it, and the exit closes it again at the same
write count, unchanged from 1.2.0.

Because such a `shutdown()` now meets the change from its configuration write, it also waits for
it from there, within its closer grace, and when the change has not decided by the end of that
wait it writes the stderr line `shutdown() could not wait for a sink change in flight to take
effect; ...`. Before, a `shutdown()` landing between the write and the retarget did not see the
change at all, so did not wait and wrote no line.

### A sink the old and the new sink graph share is no longer closed by `configure()` (SPEC-087)

Since `1.0.0`, a `configure(sink=...)` whose new sink still held the previous one closed it while
it was the live destination. A caller who logged to a file and later added a second destination
with `configure(sink=MultiSink(file, other))`, or who dropped that destination again with
`configure(sink=file)`, had `file` closed at the swap, and a sink that has released its transport
refuses from then on: a `FileSink` kept 1 of 4 events logged with no span and 2 of 8 span events.
Now the shared sink stays open and is closed once, at `shutdown()`, at exit, or by a later
`configure()` whose sink no longer holds it. The same holds for `FilteringSink`, `TransformSink`
and a wrapper nested in another, in both directions, and for a change from a `sink_factory=`
configuration to the sink its factory built. A change the other way, from a sink to a
`sink_factory=` that will return that same sink, still closes it, because the factory has built
nothing when the change is made; a factory is meant to build a sink of its own. What you can see:

- **The loss lines of those two sequences are gone.** No `orphan_lost`, no abandoned batch and no
  skipped `MultiSink` child for the shared sink, and its events all arrive.
- **A shared sink that delivers only when it is closed now delivers at `shutdown()`, not at the
  swap.** A sink that buffers and writes on `close()` keeps buffering through the swap; `flush()`
  asks it sooner, and its one close delivers the rest.
- **A sink the new graph does not hold is closed by the swap, as before.** Dropping `other` from
  `MultiSink(file, other)` closes `other` at that `configure()`.
- **A wrapper of your own that leaves its member alone now leaves it unclosed where the swap used
  to close it.** `configure(sink=file)` then `configure(sink=MyWrapper(file))`, where your
  wrapper's `close()` does not close `file`, no longer closes `file` at the swap, and nothing else
  closes it either: close it yourself after `shutdown()`. *Writing your own sink* in the README
  gives the two ways to write a wrapper that loses nothing, and the one sequence to avoid with a
  wrapper that closes its member itself.
- **One new stderr line, in two forms.** When the library's read of the sinks beneath a sink
  stops short, it writes, each time it happens, either
  `log-foundry: reading the sinks beneath a sink stopped short; a sink it shares with another may be closed while still in use`
  when the read passed its bound, or
  `log-foundry: absorbed a failure while reading the sinks beneath a sink (<Type>); it stopped short; a sink it shares with another may be closed while still in use`
  when reading an object raised, naming the exception's type and never its value. What the read
  did not reach is then decided as it was before this release.

### Every accepted event is now in exactly one loss term (SPEC-088)

The ledger's check found these, and each is fixed so the books balance. What you can see:

- **`submitted_after_shutdown` counts a late submission only once its put succeeded.** One that
  met a full queue is in `dropped` alone, where it was counted in both, so the field now reads 0
  when every late submission overflowed.
- **A span that fails to open counts its two boundary events in `in_span_lost`**, where it counted
  nothing, and a span whose close fails counts its `span.end` as well as its buffer, one more than
  before. So `in_span_lost` no longer tells its two causes apart by the size of each step; the
  stderr line still names the site.
- **A failed close's buffer is counted lost and is no longer delivered later** by another thread
  or task that shares the span and flushes, where it was both counted and delivered.
- **An interrupted close's buffer is counted lost in `in_span_lost`**, where a later `flush()` in
  that context delivered it without `span.end`. A `KeyboardInterrupt` or `SystemExit` through any
  of the four guards (an orphan log, an in-span log, a span opening or closing) is now counted in
  the same term an `Exception` is, re-raised unchanged and announced by nothing but itself: an
  interrupted orphan log, such as a sink raising `KeyboardInterrupt`, now moves `orphan_lost`, and
  the other three move `in_span_lost`.
- **An in-span log another thread sharing the span buffered before the close gave up is counted
  lost with that buffer**: in an unforced race measured while the spec was reviewed, 3 events were
  delivered before and 0 after, with `in_span_lost=4`.
- **A level call made after a close that failed or was interrupted, in a context that still holds
  the span, ships at once as an orphan on the span's own trace and span ids**, where it waited in
  the dead span's buffer for a flush that might never come. Such a context is the caller's own
  after an interrupt, and a task created inside the span after either. A log after a span that
  closed normally still gets a fresh trace.
- **A `span.end` built while another thread flushes the span is now delivered**; it could land on
  a buffer already handed over and be lost with every counter at zero.
- **A forked child's `orphan_lost` and `in_span_lost` start at zero.** The child reported the
  parent's counts as its own; its ledger now starts as what it holds, its open spans' events.
- **Two stderr lines changed.** An expired `shutdown()` with a batch still in the sink says
  `<n> event(s) in flight (health().events.in_flight)` where it said "counted when the emit
  returns", a count that never came if the process exited first. A worker thread that dies says
  `worker thread stopped; lost <n> event(s) in <k> undrained event-list(s) it held and <q> queued item(s) undelivered, nothing further will be delivered`,
  and those `<n>` events are now in `drain_lost`, where they were in no counter.

### A `NATSSink` resends the tail its deadline left unattempted (SPEC-102)

`NATSSink` bounds a whole call by one `publish_timeout`. When the budget ran out partway through a
batch, the events it never reached were counted lost whenever something else in the call was
published, and the worker never offered them again. Those events never reached the driver, so
sending them again cannot duplicate them, and through the worker they are now resent by its
existing retry rounds; no wait was added. This mattered more in this release than before it,
because a batch under a backlog now grows to half a second's worth: before this fix a JetStream
`NATSSink` with a 2 ms ack, 200 spans and a 0.2 s budget acked 193 of 400 events, and with it 19 of
20 runs acked all 400. What you can see:

- **The worker's `publish_timeout` lines name only what was still undelivered when the batch's
  rounds ran out.** A 5-event batch whose first publish spends the budget, with `max_retries=2`,
  used to make one call, count `failed` 4 and write `lost 4 event(s); NATSSink publish_timeout
  0.2s`; it now makes three calls, counts `failed` 2 and writes `lost 2 event(s); NATSSink
  publish_timeout 0.2s`. When the batch's last round is refused because a publish abandoned at the
  deadline is still pending, the line is `lost <n> event(s); refused by NATSSink after others
  landed, SinkDeliveryError` in place of the `publish_timeout` line, and the events are still
  counted once.
- **The fix has a bound.** A backlog batch is delivered when its delivery fits in the worker's
  `max_retries + 1` rounds of one `publish_timeout` each, four rounds by default, and a run that
  slows by more than that margin still loses the tail past its last round, counted in
  `losses().failed` and named by that round's `publish_timeout` line, never silently: with a 0.2 s
  budget the rounds give 0.8 s against a half-second batch, and one run in twenty lost 39
  events that way. At the default 10 s budget the rounds give 40 s.
- ~~**A tail behind an abandoned publish is still lost while that publish is pending.** It is
  delivered once the publish finishes, if a round is left. On the exit drain the waits between
  rounds are zero, so such a tail is lost there unless that publish finishes between two rounds,
  counted and named.~~ **Fixed by SPEC-104**, below: a round in the abandoned publish's first
  `publish_timeout` waits for it, so the tail is delivered whenever that publish finishes inside
  that window, on the exit drain too. Behind a longer stall it is still lost, counted and named.
- **A resend round in which only a raised publish ran sends that publish again.** A round that
  publishes nothing is answered whole, as before, and that now includes a round resending a tail:
  its raised publish is resent by the next round and counted in `losses().failed` once per round
  it raised in, in either mode, as 1.x already did for a batch's first round. A publish that raises
  every time, such as one too large for the server, is therefore counted once per round, an
  over-count of `failed` only: `health().events` counts the event once. A JetStream ack wait that
  expired may have persisted the event, so that resend can duplicate it; the `Nats-Msg-Id`
  deduplication item would close that.
- **`emit`, and a `NATSSink` under `MultiSink`, are unchanged:** each runs one round and counts,
  writes and raises what 1.2.0 did. A `FilteringSink` or `TransformSink` around a `NATSSink`
  resends the tail as the worker does, and a direct `deliver` call now returns `RETRYABLE` for the
  unattempted events where it returned `REJECTED`.

### A `NATSSink` stall a little longer than one `publish_timeout` no longer loses batches (SPEC-104)

When the driver does not return from a publish inside `publish_timeout`, `NATSSink` abandons it,
counts it and never cancels it. Until this release every later call was then refused at once while
that publish was still pending. The worker gives a batch four rounds a few hundredths of a second
apart, and at the stop no time apart at all, so a stall only a little longer than one budget lost
every batch the drain made during it, and at the stop the whole backlog, although the stalled
publish would have finished long before the `shutdown()` deadline. With one publish taking 3 s
against a 2 s budget and 2,000 events, 1,632 to 1,636 events were lost in batches at the stop and
182 to 202 in the steady drain; now no batch is lost there. Where the worker drives the sink's
rounds itself, directly or through a `FilteringSink` or `TransformSink`, which forward them, the
resend above then delivers the stalled round's unattempted tail too, so no event is lost but the
abandoned publish's own. A path that calls the sink's `emit`, as `MultiSink` does for each child,
makes one round with no resend, so it still loses that tail, counted and announced on a `NATSSink
publish_timeout` line: with a `MultiSink` around a `NATSSink`, 200 events, a 0.4 s budget and one
publish taking 0.6 s, the sink received 151 of the 200 in the steady drain and 102 at the stop,
where before this change it received 0 and 1. What you can see:

- **A call made within one `publish_timeout` of the abandonment may now wait up to one
  `publish_timeout` where it was refused at once.** It waits for the abandoned publish, goes on if
  that publish finishes inside the window, and is refused with the same error if it does not. That
  includes a level call outside any span, which runs on your application's own thread, so it can
  now block there for up to one `publish_timeout`, 10 s at the default. A call queued behind the one
  that abandoned the publish can take about two `publish_timeout`s.
- **`flush(timeout)` can overrun its timeout by up to one `publish_timeout` during that window.**
  After the drain, `flush()` asks the live sink to flush its own client, on your thread, and its
  timeout does not bound that step; a `NATSSink` now waits there for the abandoned publish, where
  it was refused at once. With a 0.1 s timeout and the default 10 s budget, a `flush()` with no
  worker running took 9.95 s where before this change it was refused at once, and one queued
  behind a round that is itself waiting can take about two `publish_timeout`s. This matters most
  on the serverless path, where `flush()` sits in a `finally` before the handler returns: a
  function timeout set close to the handler's own run time can now expire inside it. Lowering
  `publish_timeout` lowers the overrun with it.
- **`configure(sink=…)` can spend its whole swap budget.** It waits for the worker's drain to
  reach the new sink, and a drain round now waits out the abandoned publish, so with a 10 s
  budget a swap during the window took the full `DEFAULT_SWAP_TIMEOUT`, 5 s, where before this
  change it took 0.41 s. It then leaves the previous sink open and counted in
  `health().incomplete_swaps`, as any swap past its budget does.
- **A longer stall costs one window in all.** A call made after the window is refused at once, as
  before, so a stall that outlasts the window delays `flush()` by the rest of that window once,
  rather than by a budget per round. The exit drain's bound, the `shutdown()` budget plus up to two
  `publish_timeout`s, is unchanged.
- **Nothing overtakes the abandoned publish.** No call publishes while it is pending, so the tail
  the resend above sends never lands ahead of it, and the error text is unchanged. No setting,
  diagnostic line, counter or `health()` field was added.

## Known gaps

### A stream the sink does not own can still tear a line, or lose one counted as delivered

A stream sink cannot see inside a stream it does not own. Four cases remain:

- **A torn line.** A buffered stream that drops the unwritten tail of a line it cut leaves that
  line's start in its output, and the next line joins it as one line that does not parse. On
  the unbuffered `python -u` stream, a short write can tear a line that is counted as delivered.
- **A non-blocking unbuffered stream.** If that unbuffered stream's descriptor is non-blocking, a
  write that would block writes nothing and raises nothing, so whole lines are lost while counted
  as delivered, with no diagnostic line.
- **Another writer's fault.** Another writer on the same stream, such as the application's own
  `print()`, can hit a fault that drops this sink's pending lines. Those lines are then counted as
  delivered.
- **A fork.** A forked child's flush can write the parent's pending lines a second time.

Each was true of 1.x too, and none duplicates a line through the sink's own resend.

### A JetStream `NATSSink` backlog batch that outlasts the worker's rounds still loses its tail

The fix above resends the tail within the worker's `max_retries + 1` rounds of one
`publish_timeout` each. A backlog batch whose delivery outlasts them, as when the process is
starved of CPU, still loses the tail past its last round, counted in `losses().failed` and
announced by a `NATSSink publish_timeout` line. With a 2 ms ack, 200 spans and a 0.2 s budget
under CPU load this happened in about 1 run in 20 to 1 in 30; it was not seen at the default 10 s
budget.

### An owned core `NATSSink` can still lose batches to a stall a little longer than one budget

The fix above does not reach a core `NATSSink` that connected its own client, in the common shape
of such a stall, a pending buffer above 2 MiB behind an earlier blocked write. The abandoning call
then leaves an unanswered liveness probe behind, and that probe's own latch refuses at once every
call that arrives after the abandoning call returned, so such a sink keeps most of 1.2.0's loss,
counted and announced. A JetStream client and every injected client are fixed. This is read from
the code, not measured against a real server.

### A `NATSSink` stall that ends just before a call's deadline can cost one more event

When an abandoned publish finishes in the last few milliseconds of a waiting call's deadline, that
call goes on to publish with only those milliseconds left, so its first publish is abandoned too.
Against the test double every event still arrived, but one more was counted as lost and announced
on a `NATSSink unconfirmed` line. Against a real JetStream server the timed-out ack is retried,
and that event can be stored twice. This was measured against a double, not a real server.

### An event a lost reply may have landed is still counted lost when no later send lands it

When every send of an event may have landed it but none was confirmed, as when a destination
stores every batch and every reply is lost, the event is still counted in `losses().failed`, and a
batch none of whose events was confirmed fails, so `flush()` is falsy. `resent` says how many extra copies may exist: with every
reply lost, 10 events held 16 times each read `failed=10` and `resent=150`.

### `SNSSink` cannot write an SNS FIFO topic

`SNSSink` sends no `MessageGroupId`, which SNS requires on a FIFO topic, so every batch to one is
refused. This is unchanged from 1.2.0.

### A `KafkaSink` or `GooglePubSubSink` a `shutdown()` left open waits one slice

Delivered to after a `shutdown()` that left it open, with no `configure()` between, either sink
finds its stop signal set (*A sink holds one stop signal of its own*, above), so each round waits
only its first 50 ms for the client's reports and counts what is still unconfirmed as may have
landed, in `failed`, never re-sent; `flush()` stays truthy. Measured with reports arriving 0.3 s
after the publish: a `KafkaSink` round in that window read its message as may have landed, and
with the signal left set, five later publishes to either sink were all counted in `failed`.
Configured again, the sink finds its signal cleared and waits its full timeout: the same five
were all confirmed, with nothing counted. `GooglePubSubSink.close()` still waits for what such a
round left unconfirmed.

### A sink a `sink_factory` returns again after a `shutdown()` keeps its set signal

A `configure(sink_factory=f)` made after a `shutdown()` clears nothing for the sink `f` builds,
because `f` has not built it yet when the `configure()` clears the events of what it installs. If
`f` returns a sink it built before, whose signal that `shutdown()` set, the sink keeps the set
signal and its own backoff waits collapse, where in 1.2.0 it was handed a fresh one: measured, a
1 s backoff waited 0.0 s against 1.01 s. Its attempts are all still made. Configuring the sink
itself, or a `MultiSink` holding it, clears it as described above. A factory that builds a new sink
each time is unaffected.

### One value `ClickHouseSink`'s typed columns refuse still costs its whole insert chunk

This is unchanged from 1.2.0. That release's notes describe it.

### A TCP collector that acknowledges a batch and then resets still loses it uncounted

If the collector's kernel acknowledged a batch's frames and the collector then closed with them
unread, the end-of-batch check has already read the acknowledgement, so those frames stay reported
delivered; a round trip longer than the 0.25 s bound does the same. The next batch sees the reset and
goes out on a new connection, but does not count the earlier one. How much can be lost is at most the
collector's receive buffer, about 800 frames of 157 bytes on Linux and 1,200 on macOS at default
sizes.

### A full Kafka client queue is still not retried

A `KafkaSink` message librdkafka refuses because its local queue is full is counted in
`losses().dropped` and not retried, as in 1.x, when another message of the batch was handed over;
a full Pub/Sub client queue now fails its messages as a definitive refusal. Whether a full queue
should be retried is still open.

## What did not change

`emit` still raises when its run failed and returns when it settled. A run fails when nothing
was accepted and no event's fate is unknown; for the stream sinks, a line handed while the fault
latch is set counts as failed, not unknown. So a stream sink's `emit` can now return for the
batch during which a fault begins, where 1.x raised: see *The stream sinks never hand the stream
a line twice* under *Changed*. A batch that fails nowhere writes the bytes 1.x wrote, apart
from the `iso2022_*` and FIFO byte-order-mark cases under *Changed*. `losses()`, `SinkLosses` and every documented counter keep their names and
units; `SinkLosses` gains `resent`, appended with a default of zero. `SQSSink` and `SNSSink` each
gain one keyword-only argument, `max_message_bytes`, and so do `SyslogSink` and `LogstashSink`,
`ack_wait`, and `RabbitMQSink`, `confirm`, each appended; no existing argument's default changed,
and `KafkaSink`'s and `GooglePubSubSink`'s signatures did not change; `FlushResult`'s only gains
keyword fields that default to zero. `StderrSink`
still binds `sys.stderr` when it is built, and `StdoutSink` still binds `sys.stdout` the same
way. The stream sinks still take no transport lock and keep accepting after `close()`.
