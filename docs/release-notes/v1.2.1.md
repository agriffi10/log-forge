# log-foundry 1.2.1 — the file and stream sinks never write a line twice

**A release under the `1.x` freeze: nothing removed and nothing renamed.** `FileSink`,
`RotatingFileSink`, `StdoutSink` and `StderrSink` move onto the delivery engine that 1.2.0
introduced. A write that fails partway no longer leads the worker to write the batch's lines
again, and these sinks now count and announce what they lose. Each of the four gains `deliver`,
`log_foundry_counters` and `log_foundry_stop_signal`. No constructor signature or default
changed, and the core still has no runtime dependency.

A `>=1,<2` pin takes this release without a code change, with four exceptions:

- code that matches the text of these sinks' loss lines, or of the lines a `TransformSink` or
  `FilteringSink` around a stream sink writes;
- code that relies on the worker resending a failed batch to one of these sinks whole;
- a subclass of one of them that overrides `emit`;
- code that alerts on `losses().failed` for the stream sinks, which never moved before.

*Changed* lists each one.

**This release follows `1.2.0`.** It carries SPEC-082 (the file sinks) and SPEC-084 (the stream
sinks). It closes the 1.2.0 known gap *A file or stream write that fails partway can leave lines
written twice*.

## Changed

### The file sinks resend only what did not land (SPEC-082)

- A `FileSink` or `RotatingFileSink` write that fails partway returns where it raised. What did
  not land is counted in `losses().failed`. Through the worker it is resent, and only it is.
- On a run of one round, an inline `emit` or a `MultiSink` child, a partial write loses the rest
  of that batch, counted. 1.x could deliver it, with the head of the batch on disk twice.
- `failed` counts each lost event once per run, not once per worker attempt.
- An error no resend cures (`EACCES`, `EPERM`, `EROFS`, an `OSError` with no `errno`, or any
  exception that is not an `OSError`) costs one attempt. 1.x's worker resent on every raise.
- A closed file-sink subclass that inherits `emit` is not resent, even if it would re-open
  itself. A subclass that wants the resend overrides `emit`.
- The loss line reads `<Class>, N attempt(s), <Type>` where 1.x wrote `<Class>, <Type>`. Each is
  followed by `errno=N` only when the exception carries one. Some events have a line of their
  own that ends `; outcome unknown; they may have landed`: those whose line a write cut partway,
  and which the run will not offer again. The next write finishes such a line, and the event is
  still counted in `failed`.
- A codec that is not a text encoding is refused at construction, now before any file is
  created.
- `FileSink(fifo, encoding="utf-8-sig")` no longer writes a byte order mark into a pipe. 1.x
  wrote one on every open, including a second open of the same FIFO. `utf-16` and `utf-32` wrote
  none into a pipe and write none now.
- A third-party wrapper whose `emit` calls the file sink's `emit` is a one-round caller too, like
  the inline `emit` and a `MultiSink` child. When a write lands part of a batch, the rest is lost
  and counted, and `emit` returns. The count shows in two places:
  - the file sink's own `losses()`;
  - its `lost N event(s); FileSink, 1 attempt(s), OSError errno=N` line, with the torn event on
    a line of its own that says it may have landed.

  It shows nowhere the worker reads: `flush()` returns true, `failed_batches` stays 0, and
  `health().sink` stays `None` for a wrapper that offers no `losses()`. In 1.x the raise reached
  the worker through the wrapper, and its resend put the head of the batch on disk twice.
- When a file sink lands nothing of an orphan log, one written outside any span, the loss is
  announced by the engine's line. The sink writes `lost 1 event(s); FileSink, 1 attempt(s),
  OSError errno=N`, and the orphan path then writes `lost 1 event(s); orphan log not delivered
  after 1 delivery round(s)`. In 1.x, for the same `ENOSPC`, the sink's line had no
  `1 attempt(s),` and the second line was `absorbed a failure while emitting an orphan log
  (OSError); the event was lost`. `orphan_lost` and `losses()` count the same as before.
- For the `iso2022_*` codecs, a file sink appending to a non-empty file no longer writes the
  three bytes `ESC ( B` ahead of its first line, which 1.x's text stream wrote there. Every
  other codec into a regular file, and these codecs into an empty file, get the bytes 1.x wrote.

### The stream sinks never hand the stream a line twice, and count what they lose (SPEC-084)

- **`StdoutSink` and `StderrSink` now count `failed`.** Each event that did not land is in
  `losses().failed` once per run. In 1.x these sinks counted no `failed` at all, and only the
  worker's abandon line said anything. Each loss is announced on a line of the sink's own, such
  as `lost 3 event(s); StdoutSink, 4 attempt(s), OSError errno=28`. The lines the stream was
  handed before the fault are on a line of their own that ends `; outcome unknown; they may have
  landed`, or `; after an earlier fault; they may have landed` while a fault persists.
  `losses()` is still `None` until something is counted.
- **A failed run raises both types.** When nothing of a batch landed, `emit` raises an instance
  of both the stream's own exception class and `SinkDeliveryError`, with the original as
  `__cause__`. So `except OSError`, `except BrokenPipeError`, `except ValueError` and
  `except SinkDeliveryError` all still catch it. 1.x raised the stream's exception itself.
- **An error no resend cures costs one attempt.** Only `ENOSPC`, `EDQUOT`, `EFBIG`, `EIO` and
  `EAGAIN` are retried. These fail at the first attempt:
  - a broken pipe (`EPIPE`) or `EBADF`;
  - an `OSError` with no `errno`;
  - a closed stream's `ValueError`;
  - any exception that is not an `OSError`.

  1.x's worker resent the batch on every raise.
- **A fault's handed lines are counted rather than written again.** When a buffered stream
  raises partway through a batch, the lines it was already handed are counted in `failed`, as
  lines that may have landed, and are never handed to it again. The lines not yet handed are
  resent through the worker when the error is retryable. 1.x's worker resent the whole batch,
  writing up to all of it twice. On a run of one round, an inline `emit`, a log outside any span
  or a `MultiSink` child, the lines not yet handed are counted lost and not resent.
- **On a buffered stream, the batch during which a fault begins returns, and later batches
  raise.** That batch has handed lines whose fate is unknown, so it settles with them counted,
  where 1.x's `emit` raised. While the fault lasts, every later batch raises. On the unbuffered
  stream that `python -u` gives `sys.stdout`, a line written before the fault is known to have
  landed, and a batch of which nothing landed raises.
- **A wrapper around a stream sink takes the engine path.** A `TransformSink` or `FilteringSink`
  around a stream sink now offers `deliver`, so a caller-code failure writes a different line.
  The counts are unchanged.
  - `TransformSink` now writes `absorbed a failure while transforming a batch (ValueError);
    TransformSink did not forward 1 event(s) its function failed on`, in place of
    `lost 1 event(s); TransformSink, the transform failed with ValueError`.
  - `FilteringSink` now writes `absorbed a failure while filtering a batch (<Type>);
    FilteringSink did not forward N event(s) its predicate failed on`, in place of
    `lost N event(s); FilteringSink, the predicate raised <Type>`.
- **A subclass that overrides `emit` and calls `super().emit` runs one round per call.** A
  retryable tail is therefore counted lost, where 1.x's worker resent the whole batch. If a
  sustained fault clears between the worker's attempts, such a subclass can also write a line
  twice: a line the stream did take during the fault is resent.

## Known gaps

### A stream the sink does not own can still tear a line, or lose one counted as delivered

A stream sink cannot see inside a stream it does not own. Four cases remain:

- **A torn line.** A buffered stream that drops the unwritten tail of a line it cut leaves that
  line's start in its output, and the next line joins it as one line that does not parse. On
  the unbuffered `python -u` stream, a short write can tear a line that is counted as delivered.
- **A non-blocking unbuffered stream.** If that unbuffered stream's descriptor is non-blocking, a
  write that would block writes nothing and raises nothing, so whole lines are lost while counted
  as delivered, with no diagnostic line.
- **Another writer's fault.** Another writer on the same stream, such as the application's own
  `print()`, can hit a fault that drops this sink's pending lines. Those lines are then counted as
  delivered.
- **A fork.** A forked child's flush can write the parent's pending lines a second time.

Each was true of 1.x too, and none duplicates a line through the sink's own resend.

### One value `ClickHouseSink`'s typed columns refuse still costs its whole insert chunk

This is unchanged from 1.2.0. That release's notes describe it.

## What did not change

`emit` still raises when its run failed and returns when it settled. A run fails when nothing
was accepted and no event's fate is unknown; for the stream sinks, a line handed while the fault
latch is set counts as failed, not unknown. So a stream sink's `emit` can now return for the
batch during which a fault begins, where 1.x raised: see *The stream sinks never hand the stream
a line twice* under *Changed*. A batch that fails nowhere writes the bytes 1.x wrote, apart
from the `iso2022_*` and FIFO byte-order-mark cases under *Changed*. `losses()`, `SinkLosses` and every documented counter keep their names and
units. No constructor signature or default changed. `StderrSink` still binds `sys.stderr` when
it is built, and `StdoutSink` still binds `sys.stdout` the same way. The stream sinks still take
no transport lock and keep accepting after `close()`.
