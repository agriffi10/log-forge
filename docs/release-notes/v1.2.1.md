# log-foundry 1.2.1 — the file and stream sinks never write a line twice

**A release under the `1.x` freeze: nothing removed and nothing renamed.** `FileSink`,
`RotatingFileSink`, `StdoutSink` and `StderrSink` move onto the delivery engine that 1.2.0
introduced. A write that fails partway no longer leads the worker to write the batch's lines
again, and these sinks now count and announce what they lose. Each of the four gains `deliver`,
`log_foundry_counters` and `log_foundry_stop_signal`. Under a backlog the worker now sends
larger batches, and at exit it sends its backlog in batches it can finish inside the
`shutdown()` budget. No constructor signature or default changed, no setting was added, and the
core still has no runtime dependency.

A `>=1,<2` pin takes this release without a code change, with seven exceptions:

- code that matches the text of these sinks' loss lines, or of the lines a `TransformSink` or
  `FilteringSink` around a stream sink writes;
- code that relies on the worker resending a failed batch to one of these sinks whole;
- a subclass of one of them that overrides `emit`;
- code that alerts on `losses().failed` for the stream sinks, which never moved before;
- a sink that relies on being handed at most ten spans per call, or the whole exit backlog in
  one call, or a process that goes on running after an expired `shutdown()` and relies on the
  exit drain delivering its later batches late;
- a wrapper of your own whose `close()` leaves its member alone, configured over a sink it holds,
  where `configure()` used to close that sink;
- code that matches the text of the expired-`shutdown()` line or of the line a dying worker
  thread writes, or that reads the loss counters SPEC-088 corrects (*Fixed*, the event ledger).

*Changed* lists the first five and *Fixed* the last two. *Added* lists the one new public name.

**This release follows `1.2.0`.** It carries SPEC-082 (the file sinks), SPEC-084 (the stream
sinks), SPEC-087 (a sink the old and the new sink graph share), SPEC-088 (the event ledger) and SPEC-090
(larger batches under a backlog, and an exit drain that sends its backlog in batches). It closes the 1.2.0 known
gap *A file or stream write that fails partway can leave lines written twice*.

## Added

### Every accepted event is counted in one term: `health().events` (SPEC-088)

`Health` gains one field, `events`, appended and defaulting to an all-zero ledger, so a `Health`
built by keyword still constructs and a reader never tests the field for `None`. It holds an
`EventLedger`, a new public frozen keyword-only type exported from `log_foundry` and
`log_foundry.worker`. Every event is credited to `accepted` at the call that asks for it, and is
then in exactly one other term: the gauges `open_spans`, `queued` and `in_flight`, the exits
`delivered` and `skipped`, or the losses `in_span_lost`, `orphan_lost`, `overflow_lost`,
`batch_lost`, `sink_lost`, `drain_lost` and `stranded`; the properties `pending` and `lost` sum the
gauges and the losses. `unaccounted` is the events the terms cannot place, zero in a correct
library, and `shutdown()` writes one line when it ends above zero, never raising:
`log-foundry: lost <n> event(s); the event ledger does not balance at shutdown(): these are in no term; health().events.unaccounted counts them`.
`events.queued` counts events where `queued` counts submissions and markers, and
`events.in_span_lost` and `events.orphan_lost` are the existing fields. No existing field changes
its unit. README → *Flushing and shutdown* → *The event ledger* lists the terms.

## Changed

### The file sinks resend only what did not land (SPEC-082)

- A `FileSink` or `RotatingFileSink` write that fails partway returns where it raised. What did
  not land is counted in `losses().failed`. Through the worker it is resent, and only it is.
- On a run of one round, an inline `emit` or a `MultiSink` child, a partial write loses the rest
  of that batch, counted. 1.x could deliver it, with the head of the batch on disk twice.
- `failed` counts each lost event once per run, not once per worker attempt.
- An error no resend cures (`EACCES`, `EPERM`, `EROFS`, an `OSError` with no `errno`, or any
  exception that is not an `OSError`) costs one attempt. 1.x's worker resent on every raise.
- A closed file-sink subclass that inherits `emit` is not resent, even if it would re-open
  itself. A subclass that wants the resend overrides `emit`.
- The loss line reads `<Class>, N attempt(s), <Type>` where 1.x wrote `<Class>, <Type>`. Each is
  followed by `errno=N` only when the exception carries one. Some events have a line of their
  own that ends `; outcome unknown; they may have landed`: those whose line a write cut partway,
  and which the run will not offer again. The next write finishes such a line, and the event is
  still counted in `failed`.
- A codec that is not a text encoding is refused at construction, now before any file is
  created.
- `FileSink(fifo, encoding="utf-8-sig")` no longer writes a byte order mark into a pipe. 1.x
  wrote one on every open, including a second open of the same FIFO. `utf-16` and `utf-32` wrote
  none into a pipe and write none now.
- A third-party wrapper whose `emit` calls the file sink's `emit` is a one-round caller too, like
  the inline `emit` and a `MultiSink` child. When a write lands part of a batch, the rest is lost
  and counted, and `emit` returns. The count shows in two places:
  - the file sink's own `losses()`;
  - its `lost N event(s); FileSink, 1 attempt(s), OSError errno=N` line, with the torn event on
    a line of its own that says it may have landed.

  It shows nowhere the worker reads: `flush()` returns true, `failed_batches` stays 0, and
  `health().sink` stays `None` for a wrapper that offers no `losses()`. In 1.x the raise reached
  the worker through the wrapper, and its resend put the head of the batch on disk twice.
- When a file sink lands nothing of an orphan log, one written outside any span, the loss is
  announced by the engine's line. The sink writes `lost 1 event(s); FileSink, 1 attempt(s),
  OSError errno=N`, and the orphan path then writes `lost 1 event(s); orphan log not delivered
  after 1 delivery round(s)`. In 1.x, for the same `ENOSPC`, the sink's line had no
  `1 attempt(s),` and the second line was `absorbed a failure while emitting an orphan log
  (OSError); the event was lost`. `orphan_lost` and `losses()` count the same as before.
- For the `iso2022_*` codecs, a file sink appending to a non-empty file no longer writes the
  three bytes `ESC ( B` ahead of its first line, which 1.x's text stream wrote there. Every
  other codec into a regular file, and these codecs into an empty file, get the bytes 1.x wrote.

### The stream sinks never hand the stream a line twice, and count what they lose (SPEC-084)

- **`StdoutSink` and `StderrSink` now count `failed`.** Each event that did not land is in
  `losses().failed` once per run. In 1.x these sinks counted no `failed` at all, and only the
  worker's abandon line said anything. Each loss is announced on a line of the sink's own, such
  as `lost 3 event(s); StdoutSink, 4 attempt(s), OSError errno=28`. The lines the stream was
  handed before the fault are on a line of their own that ends `; outcome unknown; they may have
  landed`, or `; after an earlier fault; they may have landed` while a fault persists.
  `losses()` is still `None` until something is counted.
- **A failed run raises both types.** When nothing of a batch landed, `emit` raises an instance
  of both the stream's own exception class and `SinkDeliveryError`, with the original as
  `__cause__`. So `except OSError`, `except BrokenPipeError`, `except ValueError` and
  `except SinkDeliveryError` all still catch it. 1.x raised the stream's exception itself.
- **An error no resend cures costs one attempt.** Only `ENOSPC`, `EDQUOT`, `EFBIG`, `EIO` and
  `EAGAIN` are retried. These fail at the first attempt:
  - a broken pipe (`EPIPE`) or `EBADF`;
  - an `OSError` with no `errno`;
  - a closed stream's `ValueError`;
  - any exception that is not an `OSError`.

  1.x's worker resent the batch on every raise.
- **A fault's handed lines are counted rather than written again.** When a buffered stream
  raises partway through a batch, the lines it was already handed are counted in `failed`, as
  lines that may have landed, and are never handed to it again. The lines not yet handed are
  resent through the worker when the error is retryable. 1.x's worker resent the whole batch,
  writing up to all of it twice. On a run of one round, an inline `emit`, a log outside any span
  or a `MultiSink` child, the lines not yet handed are counted lost and not resent.
- **On a buffered stream, the batch during which a fault begins returns, and later batches
  raise.** That batch has handed lines whose fate is unknown, so it settles with them counted,
  where 1.x's `emit` raised. While the fault lasts, every later batch raises. On the unbuffered
  stream that `python -u` gives `sys.stdout`, a line written before the fault is known to have
  landed, and a batch of which nothing landed raises.
- **A wrapper around a stream sink takes the engine path.** A `TransformSink` or `FilteringSink`
  around a stream sink now offers `deliver`, so a caller-code failure writes a different line.
  The counts are unchanged.
  - `TransformSink` now writes `absorbed a failure while transforming a batch (ValueError);
    TransformSink did not forward 1 event(s) its function failed on`, in place of
    `lost 1 event(s); TransformSink, the transform failed with ValueError`.
  - `FilteringSink` now writes `absorbed a failure while filtering a batch (<Type>);
    FilteringSink did not forward N event(s) its predicate failed on`, in place of
    `lost N event(s); FilteringSink, the predicate raised <Type>`.
- **A subclass that overrides `emit` and calls `super().emit` runs one round per call.** A
  retryable tail is therefore counted lost, where 1.x's worker resent the whole batch. If a
  sustained fault clears between the worker's attempts, such a subclass can also write a line
  twice: a line the stream did take during the fault is resent.

### Under a backlog the worker sends larger batches, and the exit drain sends its backlog in batches (SPEC-090)

No argument, setting or environment variable was added; the queue still holds 10,000
submissions. What you can see:

- **A sink sees batches of up to 1,000 events under a backlog, where it saw ten spans.** While
  more is waiting in the queue, a batch grows by whole spans up to what the sink delivered in half
  a flush interval on its last batch, and never past 1,000 events unless it holds ten spans or
  fewer, which a batch could always be. With nothing waiting a batch is ten spans or a second's
  worth, as before. A burst therefore drains in a few large calls: 30,000 spans into a sink
  costing 20 ms a call left its queue in under a second, where it took more than 25 seconds in
  calls of 20 events, and fewer were dropped to a full queue.
- **A sink sees several batches at exit, where it saw one.** `shutdown()` sends what was queued
  when it began by the same rule, so the exit hands no sink more than 1,000 events in one call
  unless the batch holds ten spans or fewer. Submissions made after the exit drain began stay
  queued and are counted, as before, rather than keeping it running.
- **A `flush()` marker met at exit is answered in queue order**, once the batches carrying the
  events ahead of it are sent, where it was answered only after the whole backlog.
- **The expired-`shutdown()` line's in-flight figure can name more than one batch's events.**
  The figure is `health().events.in_flight`, as SPEC-088 made it; what changes is what the worker
  thread can hold when the join expires: besides the batch inside the sink, the batch it was
  building and at most one span it carried over, so the figure counts all three.
- **An exit drain predicted to overrun declines its later batches.** The first batch of the exit
  is always attempted. A later batch predicted, from the longest call the exit has made so far, to
  end after the `shutdown()` deadline, and every batch after it, is not attempted: each moves
  `failed_batches` by one, its events go to `health().events.batch_lost`, and all of them are
  named in one line,
  `log-foundry: lost <n> event(s); <k> exit batch(es) declined unattempted; each was predicted to end after the shutdown() deadline`.
  So the join completes and `close()` runs, where the join used to expire with the sink left open.
  In a process that goes on running after an expired `shutdown()`, those batches used to be
  delivered late by the worker thread; they are now counted lost.
- **The exit drain's abandoned batches after its first share one line.** The first abandoned exit
  batch writes the usual line, and the rest are tallied into one,
  `log-foundry: lost <n> event(s); <k> more exit batch(es) abandoned`, so a dead sink at exit
  writes a few of the worker's own lines rather than one per batch. When the join expires, that
  line comes before the expiry line. A sink that writes its own line per failed call, as
  `HTTPSink` does, or a sink run through the delivery engine, still writes one per exit batch,
  and an abandoned exit batch leaves the batch size as it was, so a dead sink is handed the exit
  backlog in batches of up to 1,000 events: a refusing `HTTPSink` with 10,000 spans at exit wrote
  22 lines, against 21 before. When the sink was already failing before the `shutdown()`, the exit
  batches are `batch_size` spans (ten by default) and those lines are one per batch.

## Fixed

### A sink the old and the new sink graph share is no longer closed by `configure()` (SPEC-087)

Since `1.0.0`, a `configure(sink=...)` whose new sink still held the previous one closed it while
it was the live destination. A caller who logged to a file and later added a second destination
with `configure(sink=MultiSink(file, other))`, or who dropped that destination again with
`configure(sink=file)`, had `file` closed at the swap, and a sink that has released its transport
refuses from then on: a `FileSink` kept 1 of 4 events logged with no span and 2 of 8 span events.
Now the shared sink stays open and is closed once, at `shutdown()`, at exit, or by a later
`configure()` whose sink no longer holds it. The same holds for `FilteringSink`, `TransformSink`
and a wrapper nested in another, in both directions, and for a change from a `sink_factory=`
configuration to the sink its factory built. A change the other way, from a sink to a
`sink_factory=` that will return that same sink, still closes it, because the factory has built
nothing when the change is made; a factory is meant to build a sink of its own. What you can see:

- **The loss lines of those two sequences are gone.** No `orphan_lost`, no abandoned batch and no
  skipped `MultiSink` child for the shared sink, and its events all arrive.
- **A shared sink that delivers only when it is closed now delivers at `shutdown()`, not at the
  swap.** A sink that buffers and writes on `close()` keeps buffering through the swap; `flush()`
  asks it sooner, and its one close delivers the rest.
- **A sink the new graph does not hold is closed by the swap, as before.** Dropping `other` from
  `MultiSink(file, other)` closes `other` at that `configure()`.
- **A wrapper of your own that leaves its member alone now leaves it unclosed where the swap used
  to close it.** `configure(sink=file)` then `configure(sink=MyWrapper(file))`, where your
  wrapper's `close()` does not close `file`, no longer closes `file` at the swap, and nothing else
  closes it either: close it yourself after `shutdown()`. *Writing your own sink* in the README
  gives the two ways to write a wrapper that loses nothing, and the one sequence to avoid with a
  wrapper that closes its member itself.
- **One new stderr line, in two forms.** When the library's read of the sinks beneath a sink
  stops short, it writes, each time it happens, either
  `log-foundry: reading the sinks beneath a sink stopped short; a sink it shares with another may be closed while still in use`
  when the read passed its bound, or
  `log-foundry: absorbed a failure while reading the sinks beneath a sink (<Type>); it stopped short; a sink it shares with another may be closed while still in use`
  when reading an object raised, naming the exception's type and never its value. What the read
  did not reach is then decided as it was before this release.

### Every accepted event is now in exactly one loss term (SPEC-088)

The ledger's check found these, and each is fixed so the books balance. What you can see:

- **`submitted_after_shutdown` counts a late submission only once its put succeeded.** One that
  met a full queue is in `dropped` alone, where it was counted in both, so the field now reads 0
  when every late submission overflowed.
- **A span that fails to open counts its two boundary events in `in_span_lost`**, where it counted
  nothing, and a span whose close fails counts its `span.end` as well as its buffer, one more than
  before. So `in_span_lost` no longer tells its two causes apart by the size of each step; the
  stderr line still names the site.
- **A failed close's buffer is counted lost and is no longer delivered later** by another thread
  or task that shares the span and flushes, where it was both counted and delivered.
- **An interrupted close's buffer is counted lost in `in_span_lost`**, where a later `flush()` in
  that context delivered it without `span.end`. A `KeyboardInterrupt` or `SystemExit` through any
  of the four guards (an orphan log, an in-span log, a span opening or closing) is now counted in
  the same term an `Exception` is, re-raised unchanged and announced by nothing but itself: an
  interrupted orphan log, such as a sink raising `KeyboardInterrupt`, now moves `orphan_lost`, and
  the other three move `in_span_lost`.
- **An in-span log another thread sharing the span buffered before the close gave up is counted
  lost with that buffer**: in an unforced race measured while the spec was reviewed, 3 events were
  delivered before and 0 after, with `in_span_lost=4`.
- **A level call made after a close that failed or was interrupted, in a context that still holds
  the span, ships at once as an orphan on the span's own trace and span ids**, where it waited in
  the dead span's buffer for a flush that might never come. Such a context is the caller's own
  after an interrupt, and a task created inside the span after either. A log after a span that
  closed normally still gets a fresh trace.
- **A `span.end` built while another thread flushes the span is now delivered**; it could land on
  a buffer already handed over and be lost with every counter at zero.
- **A forked child's `orphan_lost` and `in_span_lost` start at zero.** The child reported the
  parent's counts as its own; its ledger now starts as what it holds, its open spans' events.
- **Two stderr lines changed.** An expired `shutdown()` with a batch still in the sink says
  `<n> event(s) in flight (health().events.in_flight)` where it said "counted when the emit
  returns", a count that never came if the process exited first. A worker thread that dies says
  `worker thread stopped; lost <n> event(s) in <k> undrained event-list(s) it held and <q> queued item(s) undelivered, nothing further will be delivered`,
  and those `<n>` events are now in `drain_lost`, where they were in no counter.

## Known gaps

### A stream the sink does not own can still tear a line, or lose one counted as delivered

A stream sink cannot see inside a stream it does not own. Four cases remain:

- **A torn line.** A buffered stream that drops the unwritten tail of a line it cut leaves that
  line's start in its output, and the next line joins it as one line that does not parse. On
  the unbuffered `python -u` stream, a short write can tear a line that is counted as delivered.
- **A non-blocking unbuffered stream.** If that unbuffered stream's descriptor is non-blocking, a
  write that would block writes nothing and raises nothing, so whole lines are lost while counted
  as delivered, with no diagnostic line.
- **Another writer's fault.** Another writer on the same stream, such as the application's own
  `print()`, can hit a fault that drops this sink's pending lines. Those lines are then counted as
  delivered.
- **A fork.** A forked child's flush can write the parent's pending lines a second time.

Each was true of 1.x too, and none duplicates a line through the sink's own resend.

### A JetStream `NATSSink` with a `publish_timeout` under half a second can lose the tail of a backlog batch

A batch under a backlog grows to what the sink delivers in half a flush interval, half a second
at the default, and `NATSSink` bounds a whole call by one `publish_timeout`. With a budget below
that, a backlog batch can outlast it: the events it did not reach are counted in `sink.failed`
and announced, never lost silently. With a 2 ms ack, 200 spans and a 0.2 s budget, 193 of 400
events were acked, where before this release all 400 were. The default 10 s budget is twenty
times the half interval.

### One value `ClickHouseSink`'s typed columns refuse still costs its whole insert chunk

This is unchanged from 1.2.0. That release's notes describe it.

## What did not change

`emit` still raises when its run failed and returns when it settled. A run fails when nothing
was accepted and no event's fate is unknown; for the stream sinks, a line handed while the fault
latch is set counts as failed, not unknown. So a stream sink's `emit` can now return for the
batch during which a fault begins, where 1.x raised: see *The stream sinks never hand the stream
a line twice* under *Changed*. A batch that fails nowhere writes the bytes 1.x wrote, apart
from the `iso2022_*` and FIFO byte-order-mark cases under *Changed*. `losses()`, `SinkLosses` and every documented counter keep their names and
units. No constructor signature or default changed. `StderrSink` still binds `sys.stderr` when
it is built, and `StdoutSink` still binds `sys.stdout` the same way. The stream sinks still take
no transport lock and keep accepting after `close()`.
