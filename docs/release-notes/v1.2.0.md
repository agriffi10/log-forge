# log-foundry 1.2.0 — one delivery engine, and a sink per process

**A minor release under the `1.x` freeze: additive, nothing removed, nothing renamed.** `emit`'s
contract, `losses()`, `SinkLosses` and every documented counter keep their names and units, so code
written against `1.x` reads what it read. New are an optional per-event sink contract — `Outcome`,
`Verdict`, `SinkCounters`, `read_deliver` and `emit_via_deliver`, importable from
`log_foundry.sinks.verdict` and from `log_foundry`, whose `__all__` goes from 30 names to 35 — and
`configure(sink_factory=)`, appended last to `configure()` and to `Config`. The core still has no
runtime dependency, and a `>=1,<2` pin takes this release without a code change unless the code
configures a sink with both an injected client and the option it would have built one from, passes
`auth=` beside an `Authorization` header or to `SplunkHECSink`, passes an `auth` pair that is not
two `str` or an empty or blank `auth` token or an empty pair, gives a platform sink an empty or
blank credential argument (`api_key`, `token`), gives an HTTP sink a header name holding
whitespace, a header naming a platform sink's own credential header or two names folding to one,
or, with the library's own body, gives `gzip=True` beside a `Content-Encoding` naming another
coding or a `Content-Encoding` naming any coding but `identity` beside `gzip=False`, the default,
passes a non-callable where a constructor declares a callable (which `mypy` already refuses),
matches the old tail of an injected-client refusal or the old text of an HTTP sink's
total-failure `SinkDeliveryError`, assigns `max_retries` or `max_retry_after` on a `FilteringSink`,
`TransformSink` or `LogstashSink` or in a subclass of one, assigns `_closed`, `_lock` or `_close_lock`
in a subclass of a sink that releases its transport, logs from a forked child to the `SQLiteSink`
its parent configured, or relies on a counter this release moves (see *Changed*).
**This release follows `1.1.0`.** These are the pending notes for the `stability-redesign` arc, SPEC-069 to
SPEC-079. An entry for a spec that has been built says what it does; one for a spec still in Draft
says what that spec, as specified, makes visible to a caller.

## New

### An optional per-event `deliver(batch) -> Verdict` for sinks (SPEC-072)

A sink may now add `deliver(batch)`, which returns a `Verdict` saying, for each event by its index
in the batch, whether it was accepted, rejected for good, dropped by the sink, deliberately skipped,
of unknown outcome, or worth sending again, plus an optional retry-after hint. When a sink offers it,
the worker and the no-span logging path call it instead of `emit`, and one shared engine resends
only the events a verdict called retryable, waiting on the shutdown signal and keeping the exit drain
inside `shutdown()`'s budget.

- **The same outage tolerance as `1.x`.** A batch survives the number of attempts it does in 1.1.0:
  the sink's `max_retries` and the worker's still multiply, `(sink + 1) × (worker + 1)`, which is 16
  attempts at the defaults of 3 and 3, and on the no-span path the sink's own `max_retries`. The
  waits keep the `1.x` schedule too: the sink's backoff from 0.1 s, restarting each cycle, and the
  worker's shorter backoff between cycles. What changes is that each attempt after the first
  carries only the events still retryable, so an event the destination already accepted is never
  sent again. The sink's own `max_retry_after` still bounds a server's retry-after hint.
- **The counts land where they did.** The engine writes into a `SinkCounters` object the sink owns,
  so `losses()`, `.failed` and `read_losses(sink)` read as before.
- **What the engine cannot settle is not resent.** An exception escaping `deliver` is a failed
  delivery (`flush()` reports it), and the engine resends one only for a sink that declares
  `log_foundry_idempotent = True` **and** whose private retry predicate, `_retryable_error`,
  accepts the exception — a predicate the library's own sinks define and a subclass of one
  inherits, so a sink written from scratch has none and is never resent. A verdict the engine
  cannot read, or an outcome it reports as unknown, is counted as unconfirmed and is resent only if
  the sink declares `log_foundry_idempotent = True`. No shipped sink declares it.
- **A loss decided in a round with no line of its own is always announced.** The engine writes one
  stderr line per round that decided such a loss, `lost N event(s); rejected …, unresolved …,
  raised …, unknown …, dropped … after R delivery round(s) to <YourSink>`, where `R` is the round
  that decided those losses rather than the number of rounds the run took, naming each loss decided
  in a round of your `deliver` that registered no line of its own, or whose verdict the engine set
  aside because it raised or could not be read. A run whose losses were decided in two rounds
  writes two lines, in round order. A round in which a library sink you subclass or wrap wrote a line keeps that line and
  the engine adds none for it, so a loss is announced at most once, but a round that announces some
  of its losses owns the rest: return them with a line too. An event a round leaves retryable when
  the run ends there is owned only by a line registered for the run's last round. A `deliver` of
  yours that returns a loss silently in a later round, beside a library line in an earlier one, now
  gets the engine's line where it had none. A round of yours that raises, or returns something the
  engine cannot read, has whatever a library sink you subclass or wrap registered during it
  discarded, counts and lines alike, since the engine decides that round's outcomes itself and
  names them in its own line.

**Added** in `log_foundry` and `log_foundry.sinks.verdict`: `Outcome`, `Verdict`, `SinkCounters`,
`read_deliver`, the probe a wrapper asks whether its inner sink offers `deliver`, and
`emit_via_deliver(sink, batch, *, deliver=None)`, which a sink defining `deliver` makes its `emit`
(`def emit(self, batch): emit_via_deliver(self, batch)`), so a wrapper calling `inner.emit(batch)`
runs the same engine and sees the `1.x` `emit` contract: it returns when anything landed and raises
`SinkDeliveryError` when the run failed outright. `sink` and `batch` are its only positional
parameters, and anything it gains in `1.x` is keyword-only. **Added** as
optional sink members, each read from the sink without running its code: `deliver`,
`log_foundry_counters` (a `SinkCounters`, which `deliver` requires) and `log_foundry_idempotent`.
**They are inert for every shipped sink in SPEC-072 itself**: no shipped sink defines `deliver`
there, and the shipped sinks move onto the engine in the later 1.2.0 specs listed under *Changed*.
A sink without `deliver` is delivered to exactly as in 1.1.0. Nothing changes for a caller who does
not write a sink.

### `configure(sink_factory=...)`: each process builds a sink of its own (SPEC-079)

`configure(sink_factory=lambda: LogstashSink(host="logs", port=5000))` gives every process its own
sink, a forked child included. The library calls the factory **lazily, on the first event a process
sends**, in every process. For events inside a span that call runs on the background worker thread,
and outside a span on the thread that logged. `configure()` itself never calls it, and neither does
the fork handler, so a prefork master that never logs never opens a connection. Each gunicorn or
uWSGI worker opens its own on its first log, and that process closes it at `shutdown()` or at exit.

- **Refused at the call.** `configure()` raises `ValueError` if `sink=` and `sink_factory=` are both
  given, and `TypeError` if `sink_factory` is not callable or cannot be called with no arguments
  (`sink_factory=FileSink` is refused).
- **One setting.** A later `sink=` clears the factory, and a later `sink_factory=` replaces the sink,
  with the usual drain and close.
- **What `get_config()` shows.** `get_config().sink_factory` is the factory; `get_config().sink` is
  the library's own wrapper around it, which is a `Sink`.
- **A factory that fails** — raises, or returns something that is not a sink — costs the event or
  batch that needed it, counted and announced as a delivery failure: in `orphan_lost`, or as a failed
  batch after the worker's usual retries. The next event calls the factory again. Nothing reaches
  your code.
- **Build a new sink on every call.** A factory that hands back one object built before the fork
  shares it across processes, as configuring that object in each child would.

## Fixed

### One event a sink cannot encode costs only itself (SPEC-069)

A batch is the worker's unit of retry, so one event a sink could not encode used to cost every event
beside it. In eight sink classes it also duplicated delivery: `StdoutSink`, `StderrSink`, `FileSink`,
`RotatingFileSink`, `ClickHouseSink`, `RabbitMQSink`, `KafkaSink` and `AzureEventHubsSink` wrote or
produced the events ahead of the bad one, raised, and the retry sent them again. Every sink that
builds a record per event now encodes the whole batch before its first write, produce, request or
insert. An event it cannot encode (only a third-party wrapper or a direct `emit` can hand it one) is
dropped alone, counted in `health().sink.dropped` and announced once per batch in one stderr line,
`lost N event(s); <Sink>, encoding raised <ExceptionType>`, naming the sink and the exception's type
(never its message or the event), and the rest are delivered once.

**A batch of nothing encodable settles, counted.** It returns normally, its events counted in
`health().sink.dropped`, instead of raising. `flush()` is truthy and `failed_batches` stays 0 for it,
as for a batch of nothing but oversized events. **If you alert on `failed_batches` alone, add
`health().sink.dropped`.**

Every counter that moves, for an unencodable event:

| Sink | Before | Now |
|---|---|---|
| `StdoutSink`, `StderrSink`, `FileSink`, `RotatingFileSink`, `SQLiteSink`, `ClickHouseSink`, `RabbitMQSink`, `KinesisSink`, `FirehoseSink`, `SNSSink`, `SQSSink`, `MongoDBSink`, `AzureEventHubsSink`, `SyslogSink`, socket-mode `LogstashSink` | raised `TypeError`, nothing counted by the sink | `dropped` +1, the rest delivered |
| `KafkaSink` | raised `TypeError`, nothing counted | `rejected` (reported as `dropped`) +1 |
| `PostgresSink`, `RedisStreamsSink`, `RedisListSink` | the whole batch retried, then `failed` + batch size and `SinkDeliveryError` | `dropped` +1, the rest delivered, no retry |
| `GooglePubSubSink` | `dropped` +1, one `refused the publish, <Type>` line per event; a batch of nothing encodable raised | `dropped` +1 as before, but one `encoding raised <Type>` line per batch replaces the per-event line; a batch of nothing encodable settles |
| `NATSSink`, `SentrySink`, the HTTP family | — | unchanged (`failed` for NATS and Sentry, `dropped` for HTTP) |

`StdoutSink`, `StderrSink`, `FileSink`, `RotatingFileSink` and `SQLiteSink` gain a public `losses()`.
It returns `None`, as before, until the sink has counted something, so a process that only logs
clean events reads `health().sink is None` as it did.

### PostgreSQL and MongoDB repair what they would refuse, and deliver it (SPEC-069)

Two destinations refuse values that `@trace`, `info()` and `configure()` accept, and each refusal
used to cost the whole batch, retried to no effect:

- **`PostgresSink`** refused U+0000 anywhere in an event (JSONB cannot hold it) or in a text column.
  That included a `service`, `version` or `env` stamp, so `configure(service="s\x00x")` lost every
  event with `failed` counting them all. Each U+0000, in a value, a key or a stamp, is now replaced
  by U+FFFD and the event is delivered.
- **`MongoDBSink`** refused an integer outside the signed 64-bit range and a NUL in a key name. The
  integer is now replaced by the `<int: ~N digits>` placeholder assembly already uses for a number
  too large to render, and the NUL in the key by U+FFFD. What is refused is decided by the driver's
  own `bson.encode`, imported on the first `emit` rather than at construction; with an injected
  client and no `bson` installed there is no check, and nothing is repaired.

**A repaired event carries `truncated: true`**, exactly as when assembly makes the same
substitution; an untouched event is byte-identical to before. A repair is not a loss: nothing is
counted and nothing is written to stderr. Where these sinks counted the whole batch in `failed` and
raised, they now count nothing and deliver every event. The six characters `\u0000` written as text
are left alone.

### `SQLiteSink` and the file sinks count and announce a driver error (SPEC-069)

A `sqlite3.Error` from `SQLiteSink.emit`, or an `OSError` from `FileSink.emit` and
`RotatingFileSink.emit` (a full disk, a revoked permission), escaped with nothing counted by the
sink and nothing written by it. Each now adds the batch to `health().sink.failed` and writes
`lost N event(s); <Sink>, <ExceptionType>` (with `errno=N` for `OSError`), then raises. The raised
exception is an instance of **both** `SinkDeliveryError` and the driver's own class, so an
`except sqlite3.Error`, `except OSError`, `except PermissionError` or `except SinkDeliveryError`
around `emit` still matches, and its `str()`, `args`, `errno`, `filename` and `sqlite_errorcode` are
the original's. Its `__name__` is the driver exception's too, so a log line naming it reads as it
did, and pickled it comes back as the driver's own exception. It is not a new public name: ask with
`isinstance(exc, SinkDeliveryError)`. A file write that fails partway through a batch still leaves
the earlier lines on disk, and the worker's retry writes them again.

### `SyslogSink` stamps a forked child's own process id (SPEC-069)

`SyslogSink` read the process id once, at construction, so a child forked afterwards (a prefork
server that configures once in the master) sent every message with its parent's id as the RFC 5424
PROCID. It now reads the id per message, so a child's messages carry the child's.

### `OTLPSink` counts a `2xx` whose body could not be read (SPEC-070)

A `2xx` response whose body was cut short, stalled or reset after the status line used to be
reported by `OTLPSink` as full success, because the hook that reads the body could not tell it from
an empty body. It is now counted in `.dropped_unadjudicated` (and so in `health().sink.failed`),
announced with the line an unreadable `partialSuccess` already wrote — `lost N log record(s);
OTLPSink could not read the partial-success response; they may have landed; not retried` — and
never re-sent, which is how `ElasticsearchSink`, `OpenSearchSink` and `HoneycombSink` already
treated it. A `2xx` with an **empty** body is still success for `OTLPSink`. A subclass of your own
that overrides `_handle_response` keeps its signature and still receives a payload equal to `b""`
for an unreadable body.

### `KinesisSink` and `FirehoseSink` count a reply whose failed count contradicts its records (SPEC-070)

Each reply carries a failed count and one result per record. The two sinks read the count first and
stopped when it was `0` or missing, so a reply saying `0` failed while its records carried error
codes, or one with no count at all beside coded records, counted nothing and printed nothing; a reply
claiming failures with no record coded did the same. Every such reply — a count that is present
but not an integer, `None` and `True` included, among them — is now counted in `.dropped_unadjudicated`
(and so in `health().sink.failed`), announced as possibly landed, and not retried, because the
reply cannot say which records were taken. So is a reply whose result array is present but
unreadable — an entry that is not an object — beside a `0` or missing count, which used to hide
a coded entry beside it; its line says `an unreadable result array` in place of the result
count. A consistent reply is read exactly as before. The
unadjudicated line, which a reply of the wrong length already wrote, now also says how many records
were coded and what the count said: `KinesisSink could not adjudicate a put_records response (2
record(s) sent, 2 result(s) returned, 2 coded, failed count 0); abandoned, not retried`, with `no
failed count` or `a failed count of type <Type>` in place of the number when there is none or it
is not an integer (`put_record_batch` and `FirehoseSink` for Firehose).

### A sink handed a client no longer ignores the options it would have built one from (SPEC-071)

`RedisStreamsSink` and `RedisListSink` given both `client=` and `url=`, `AzureEventHubsSink` given
`producer=` with `connection_str=` or `eventhub=`, `PostgresSink` given `connection=` with `dsn=`
or `connect_timeout=`, `ClickHouseSink` given `client=` with `dsn=`, `KafkaSink` given `producer=`
with `bootstrap_servers=`, `MongoDBSink` given `client=` with `uri=`, and `RabbitMQSink` given
`connection=` with `url=` used to construct and silently never read the second argument, so what
the caller configured was not what was in use. Each now raises `ValueError` at construction, naming
the argument: drop it, or drop the injected object and let the sink build its own. A 1.x program
passing both breaks here, on purpose. Where such a call also passes a non-`int` `max_retries`,
`ClickHouseSink` and `RabbitMQSink` report this `ValueError` first, as their existing refusals
did, and the other sinks report the `max_retries` `TypeError` first.

`PostgresSink`'s `connect_timeout` default is now `None`, meaning the same 5 seconds as before, so
the sink can tell a value you gave from one you left out; `sink.connect_timeout` still reads `5` by
default, and passing an `int` type-checks and behaves as it did. `SQLiteSink(database, connection=c)`
is still accepted: `database` is required and documented as ignored beside an injected connection,
so refusing it would break every caller that injects one.

### An HTTP sink handed `auth=` beside an `Authorization` header refuses the pair

`HTTPSink(url, auth=..., headers={"Authorization": ...})` used to construct and send only one of
the two, and which one depended on how the header was spelled: written exactly `Authorization`, the
header was sent and `auth` never was; in any other case (`authorization`, `AUTHORIZATION`), `auth`
was sent and the header never was. It now raises `ValueError` at construction, whatever the
header's case, naming the conflict and neither value: `HTTPSink auth and an Authorization header
cannot both be given, since each sets the one Authorization header a request carries; drop auth= or
the header`. The same holds for every HTTP sink that forwards `auth` — `DatadogSink`,
`ElasticsearchSink`, `OpenSearchSink`, `HoneycombSink`, `LokiSink`, `NewRelicSink` and `OTLPSink`,
each under its own name, and `LogstashSink` in HTTP mode, under `HTTPSink`'s. A 1.x program passing
both breaks here, on purpose: keep whichever one you meant to send and drop the other.
`SplunkHECSink` sends its `token` as the `Authorization` header itself, so any `auth=` it was given
was silently dropped; it now raises `SplunkHECSink auth cannot be given, since this sink sends its
token as the Authorization header; drop auth=`. Pass the HEC token as `token`.

### `AzureEventHubsSink` with an injected producer refuses a missing extra at construction (SPEC-071)

`AzureEventHubsSink(producer=p)` without `azure-eventhub` installed used to construct and then raise
`ModuleNotFoundError` out of every `emit`. It now raises at construction, with the message naming
the `azure-eventhubs` extra (below), since the sink cannot build an event without the extra's
`EventData` class. `AzureEventHubsSink()` with neither a producer nor a connection string still
raises its `ValueError`, with or without the extra.

### A value lying about its type is refused with the argument named (SPEC-071)

`configure()`'s `service`, `version`, `env` and four payload ceilings, `flush()`'s and
`shutdown()`'s `timeout`, the sinks' integer and duration arguments, `OTLPSink`'s `endpoint` and the
HTTP sinks' `auth` already refused a value of the wrong type at the call. They asked the value
itself what it was, though, so a value lying about its type got the wrong message. One whose
`__class__` claimed to be a `str` got `descriptor '__str__' requires a 'str' object…`, or for
`OTLPSink` a `ValueError` about the URL scheme. One whose `__class__` raised got that exception. One
whose metaclass renamed its type got `service must be a str, got str`. Each is now the door's own
`TypeError`, naming the argument and the value's real class, and nothing of the value runs. `auth`
is judged by its real type too: a value claiming `str` takes the `(user, password)` route without
its `__class__` or `__contains__` running, and one that cannot be unpacked as a pair gets the
existing `ValueError` naming `auth`, while one that unpacks into two real `str` is sent as Basic
auth (and any other pair is refused, as the `auth` entry below says). A wrong type that does not
lie gets exactly the message it got before. A `float` subclass whose `__class__` claims `int`, passed as a duration
or a `timeout`, used to be refused, and is now accepted as the float it holds.

### A sink handed a non-callable where it calls one refuses it at construction (SPEC-071)

`SQSSink`'s `message_group_id` and `message_deduplication_id`, `FilteringSink`'s `predicate`,
`HTTPSink`'s `opener` (and so every HTTP platform sink's), `CallbackSink`'s `fn` and `on_close`,
and `TransformSink`'s `fn` accepted any value. One that was not callable, such as `message_group_id=5` or a constant
`message_deduplication_id="x"`, then raised `TypeError: 'int' object is not callable` out of every
`emit`, or out of `close()` for `on_close`. Each now raises `TypeError` at construction, naming the
sink, the argument and the type: `SQSSink message_deduplication_id must be callable or None, not
str`, or `must be callable, not NoneType` for the two required `fn`s, which refuse `None` too, or
`must be a str, a callable or None, not int` for `message_group_id`, which still takes a non-blank
`str`. A platform sink's `opener` is refused by the `HTTPSink` it builds, so `SentrySink(dsn,
opener=5)` names `HTTPSink`; `SentrySink(backend="sdk", opener=...)` keeps its existing
`ValueError`. **`SQSSink` refuses these on a standard queue too**, which never reads either id and
so delivered: the value was already outside the declared type, so a type-checked program is not
affected.

### An HTTP sink's `auth` is read once, and a pair that is not two `str` is refused

`HTTPSink(url, auth=iter(("u", "p")))`, or a generator in its place, used to construct and then
raise `ValueError: not enough values to unpack` out of every `emit`, uncounted: the construction
check consumed the iterator, and every request unpacked it again. Credentials are now copied once,
at construction, as exact text, and the `Authorization` value is built from the copy then; every
request sends that value, on `HTTPSink` and every HTTP sink that forwards `auth`. So such a sink
sends Basic auth on every request, and a `list` changed afterwards, an object yielding new values
each time it is iterated, or a `str`-subclass token whose methods would answer differently later,
is frozen at what it held then. A `tuple` or `list` of two `str`, or a `str` token, sends what it
sent before.

A pair that unpacked into two items but was not two `str` used to construct and send whatever the
unpack gave: a `set` or `frozenset` in hash order, so the order changed with `PYTHONHASHSEED`, a
mapping's keys, `b"to"` as two integers, a `bytes` or `None` half as its `repr`. None of those ever
authenticated. Each now raises `ValueError` at construction naming only the real types, `HTTPSink
auth must be a str token or a pair of two str, not set`, or `… not a pair of (str, NoneType)` for a
half. A 1.x program passing one breaks here, on purpose; such a value is already outside the
declared `tuple[str, str]`, so a type-checked program is not affected. Pass a `tuple` of two `str`.
A `set`, `frozenset` or mapping is judged before it is unpacked, so one of the wrong length now gets
this message where it got `auth cannot be sent over HTTP (ValueError)`; every other value refused
before (`auth=123`, a `tuple` of the wrong length) keeps its message.

### An HTTP sink refuses an empty `auth` or credential

`HTTPSink(url, auth="")` used to construct and send `Authorization: Bearer ` on every request, and
`auth=("", "")` sent `Basic Og==`, so against an endpoint that requires credentials every `emit`
was refused for the life of the process. Both now raise `ValueError` at construction, naming `auth`
and never a value: `HTTPSink auth is empty, so every request would carry an empty credential; drop
auth= or give it a value`. A token of only spaces and tabs is refused the same way, since a
recipient strips them from the header (RFC 9110 §5.5) and receives a bare `Bearer`. The platform
sinks' own credential arguments follow the same rule: an empty or blank `api_key` for
`DatadogSink`, `NewRelicSink` and `HoneycombSink`, and `token` for `SplunkHECSink`, used to send
their credential header with nothing in it, and now raise `ValueError` naming the argument, such as
`DatadogSink api_key is empty, so every request would carry an empty credential; give it a value`.
Each is judged by what it sends, so `b""` or `b"  "` is refused as `""` is; `SplunkHECSink`
formats a `bytes` token into `Splunk b''`, as 1.x did, which is a wrong credential rather than an
empty one and is not refused. That refusal runs last, so a configuration refused for another
reason keeps its message. The empty-`auth` refusal holds for every HTTP sink that forwards `auth`,
under its own name, and `LogstashSink` in HTTP mode, under `HTTPSink`'s. An empty `auth` beside an
`Authorization` header gets the conflict's message above, and `SplunkHECSink` its own refusal of any
`auth`. A 1.x program passing one breaks here, on purpose: the credential was empty on every
request. Drop `auth=`, or give it a value. A pair with one empty half, `("key", "")` or
`("", "token")`, still constructs and is sent as before: RFC 7617 allows it, and services that take
an API key as the user with no password accept it. So does a pair of whitespace halves, which
base64 turns into credential bytes that are not empty.

### An HTTP sink refuses a header that would silently replace another

`urllib` sends one value per header name, folding case, and keeps the last one written. So a
`headers=` entry naming a platform sink's own credential header, in any case, was sent instead of
the argument that header carries: `DatadogSink(api_key=k, headers={"dd-api-key": x})` sent `x` and
never `k`, and the same held for `NewRelicSink`'s `Api-Key`, `HoneycombSink`'s `X-Honeycomb-Team`
and `SplunkHECSink`'s `Authorization: Splunk <token>`. Each now raises `ValueError` at construction,
naming the header, the argument and the header the sink sends, never a value: `DatadogSink header
'dd-api-key' collides with api_key, which this sink sends as DD-API-KEY; drop the header`. And two
`headers=` names that fold to one (`{"x-a": "1", "X-A": "2"}`, or `authorization` beside
`Authorization`) sent only the last; on every HTTP sink they now raise `HTTPSink headers 'x-a' and
'X-A' name the same header, which is sent once; drop one`. A 1.x program passing either breaks
here, on purpose, since one of its headers or arguments was never sent: drop the header, and pass
a credential through the sink's own argument. A non-credential header such as `Content-Type` is
still yours to override.

`merge_headers`, the public helper the four sinks use, gains keyword-only `owner=` and `argument=`,
both defaulted. The refusal is opt-in: only a call passing `argument=`, as the four sinks do,
treats the keys of `base` as credential headers a caller may not name. Without it the caller's
headers win as in 1.x, and a sink of your own built on `merge_headers` sends a caller's override
of one of its defaults byte for byte as before. The one difference is the returned map: a caller name in another case than
the default's (`x-default` over `X-Default`) now replaces the default in place, under the caller's
spelling, where the map used to hold both and `urllib` folded them into the same request.

### Datadog, New Relic, Honeycomb and Splunk send a `headers=` that is not a `dict`

These four sinks merge your `headers=` with their own, and the merge used to take only a `dict`: a
`MappingProxyType`, a list of pairs or any other mapping was dropped silently, so none of its
headers was sent, and an `Authorization` in it escaped the refusal beside `auth=` above. They now
read it with `dict()`, as `HTTPSink` reads its own, so it is sent and judged by every header rule; a
value `dict()` cannot read raises its `TypeError` or `ValueError` at construction, where it used to
be ignored. `HTTPSink` itself read any empty value as no headers, so `HTTPSink(headers=0)`
constructed; it now raises the same `TypeError`.

### A `Content-Encoding` header that `gzip=` makes untrue is refused

A caller's `Content-Encoding` header was found by its exact spelling only. Spelled exactly
`Content-Encoding`, it switched compression off whatever it said: `Content-Encoding: identity`
beside `gzip=True` sent an uncompressed body, silently ignoring `gzip=True`, and `Content-Encoding:
gzip` sent an uncompressed body labelled gzip, which the destination could not decode. Spelled any
other way (`content-encoding: identity`), it was missed: the body was gzipped and the sink's own
`Content-Encoding: gzip` was sent in its place.

And beside `gzip=False`, the default, a `Content-Encoding` naming a coding — `gzip`, `br` — was
sent over the body exactly as the sink built it, uncompressed, on every request, so a destination
honouring the label could not decode it.

The header is now found in any case, and its value is read by the bytes it sends, so `b"gzip"`
reads as `gzip` and `5` or `True` as a coding of that name. Beside `gzip=True`, one whose value
names gzip, `gzip` or `x-gzip` (which RFC 9110 §8.4.1.3 reads as `gzip`), in any case and with
surrounding spaces and tabs ignored, has the body compressed and is sent as written. Any other
value — `identity`, `br`, a list such as `gzip, br`, an empty value, `5` — raises `ValueError` at
construction, naming the header as you spelled it and never its value: `HTTPSink gzip=True cannot
apply beside header 'Content-Encoding', which names another encoding; drop gzip= or the header`.
Beside `gzip=False`, a value naming any coding other than `identity` — `gzip`, `br`, any list, `5` —
raises `HTTPSink gzip=False, the default,
cannot apply beside header 'Content-Encoding', which names an encoding the body is not in; drop the
header, or pass gzip=True if it names gzip`; `identity` in any case, and an empty or
whitespace-only value, construct and are sent over the uncompressed body as before.

Both refusals hold only when the body is built by the library's own `_body`. A subclass whose own
`_body` encodes the body, such as one returning `zlib.compress(...)` beside `Content-Encoding:
deflate`, owns both the body and its label, with `gzip` true or false: it is not refused, the
library never compresses its body beside your header, and it sends byte for byte what it sent in
1.1.0. Any subclass that defines `_body` on its class counts as its own, even one that only calls
`super()._body`, so such a pass-through built with `gzip=True` beside `Content-Encoding: gzip`
sends an uncompressed body under a gzip label, as it did in 1.1.0. The body is judged during
construction, so a `_body` assigned to the instance after `super().__init__` returns is not seen
and the sink is refused as the library's: assign it before calling `super().__init__`, or define
it on the class. Every HTTP sink that forwards `gzip` refuses both under its own name,
and `LogstashSink` in HTTP mode under `HTTPSink`'s. **A 1.x program passing either pairing breaks
here, on purpose.** Beside `gzip=True` this reverses the header-wins rule 1.0 shipped (SPEC-048
FR-007): drop `gzip=True` to send your header over an uncompressed body, or drop the header to let
the sink compress. Beside `gzip=False` the label was already untrue on every request: drop the
header, or pass `gzip=True` if it names gzip. Those remedies are for the library's own body; a
`_body` subclass is never refused here and needs no change.

Once you set a `Content-Encoding`, whether the body is compressed is fixed at construction, from
the `gzip` you passed then, and setting the sink's public `gzip` attribute afterwards changes
nothing. A sink built with `gzip=True` beside `Content-Encoding: gzip` and then set `gzip = False`
used to send an uncompressed body under the gzip label; it now still compresses, and an event that
fits only once compressed is no longer discarded unsent after a `413`. A `_body` subclass beside
its own `gzip` label used to be gzipped a second time whenever `gzip` was true, given at
construction or set later; it now sends its body as it built it, as 1.1.0 did. `gzip` itself is read
once: a value that is not a
`bool`, such as `gzip=1`, is read with `bool()` at construction and kept as `True` or `False`, so
its `__bool__` no longer runs on every request, and one whose `__bool__` raises now raises at
construction rather than out of every send.

### An HTTP sink refuses a header name holding whitespace

A header name holding a space, tab, vertical tab or form feed anywhere but its first character
(`"Authorization "`, `"X- Key"`), or one of the separators `\x1c` to `\x1f` anywhere, used to
construct, and `http.client` sent the name verbatim: `Authorization : V` went on the wire. A field
name is a token, which holds no whitespace, and RFC 9112 §5.1 requires a server to answer
whitespace between a field name and its colon with `400`, so against a conforming collector every
`emit` failed; a lenient one may have trimmed the name into a header you never wrote. It now raises
`ValueError` at construction, naming the header and never its value: `HTTPSink header name must
not contain whitespace: 'Authorization '`. The same holds for every HTTP sink that takes
`headers=`, under its own name, and `LogstashSink` in HTTP mode, under `HTTPSink`'s. A 1.x program
whose lenient server accepted such a header breaks here, on purpose: the name was already broken
against any server that follows the RFC, and SPEC-049 refuses an argument that is already broken.
Remove the whitespace from the name. A name refused before (one of those four characters first, a
non-ASCII space, `CR` or `LF`) keeps the message it had, and a header value holding spaces is
untouched.

### HTTP header names and values are read once, as the text they hold

A header name or value that was a `str` subclass was stored as your object, so its methods ran at
every check and on every `emit`. A name whose `capitalize` answered differently after construction
could pass every header rule and then go out as another header, a platform sink's credential
header among them, and a refusal quoted whatever its `__repr__` returned. Every header name and
`str` value is now copied once, at construction, as the exact text it stores, and every check and
request reads the copy. A header name that is not a `str` was already refused, by the first check
that read it, with a bare `TypeError` such as `argument of type 'int' is not iterable`; it now
raises `TypeError: HTTPSink header name must be a str, not int`.

A value that is not a `str` sends the bytes it sent before, and is now copied once too, at
construction, into those bytes. An `int`, `bool` or `bytes` is kept as given. Any other value used
to be kept as your object, so `http.client` ran its code on every request — an `int` subclass's
`__str__`, an object's `encode` — and a `bytearray` changed after construction sent its new
contents. That code now runs once, at construction, and a `bytearray` changed afterwards, or an
object that would answer differently later, is sent as it was then. No value refused before is
accepted now, and none accepted before is refused.

### `KafkaSink` no longer loses a message to a concurrent `close()` (SPEC-076)

An `emit` that had passed `KafkaSink`'s closed check before `close()` began, on another thread,
could hand its message to the producer after `close()` had flushed it. Nothing flushed that message
again, nothing counted it, and nothing was written to stderr. `close()` now waits up to 0.5 s for any
`emit` or `flush` still inside the sink before it flushes. If an `emit` is still inside when the wait
ends, every message that `emit` handed to the producer is counted in `health().sink.failed` (an upper
bound, since the flush may have delivered some of them), with one stderr line:
`log-foundry: lost N message(s); KafkaSink, produced while the sink was closing`.

### `shutdown()` waits on a stuck swapped-out close for one grace, not two (SPEC-078)

When a late `configure(sink=...)` left the previous sink inside a `close()` that outlived the swap's
budget, `shutdown()` waited on that close twice, once for the close and once more for its thread, so
it spent two `DEFAULT_CLOSER_GRACE` periods (about 4 s) where it documents one (about 2 s), on both
delivery paths. It now waits once. Every sink is still closed, and the live sink's own close still
runs inline on the thread that called `shutdown()`.

### A `configure(sink=...)` during `shutdown()` no longer takes over the shutdown's closes (SPEC-078)

A `configure(sink=B)` arriving while `shutdown()` was draining, after the background worker had
stopped, could close the sink being drained on a background thread. That thread gets only the short
closer grace and is killed at interpreter exit, which could cut short a sink whose `close()` does its
delivery. The same call also closed `B`, though nothing had been written to it. Now, when no worker
is still delivering, a `configure(sink=...)` made during a shutdown, before the shutdown has taken
the sinks it closes, only updates the config: the shutdown closes the drained sink on the thread
that called it, and `B` is owed a close only once an event reaches it. One that lands after that
point behaves as before. A worker started during the shutdown that is still delivering is switched
to the new sink as before.

### A forked child no longer hangs on a library sink held inside your own wrapper (SPEC-079)

If you configured a wrapper of your own around a library sink, such as `MyWrapper(FileSink(...))`,
and forked while another thread was inside that sink's `emit`, the child inherited its lock still
held, and the child's first event through the wrapper blocked forever. The child now repairs every
library object it can reach from what you configured, including one inside a wrapper it did not
write, and one two lists deep inside a library sink. A `FileSink` there is re-opened for the
child, as a directly configured one already was, so the child no longer risks writing the parent's
unflushed lines a second time. The reach is bounded: a child reading through an unusually large
object graph stops at a ceiling and announces it, and a library sink your wrapper holds only through
a bound method, such as `self._emit = file_sink.emit`, is not reached. Your wrapper's own locks are
still yours. A child still delivers to a sink it inherited, and still refuses to close it unless it
re-opened the sink itself, as it does a `FileSink`.

### An engine sink's counters never hang a forked child, however they are held (SPEC-079)

A sink offering `deliver` keeps a `SinkCounters` whose lock the engine takes at the end of every
run. A child used to repair that lock only for a sink it could read the counters from directly, so
a sink of yours held inside your own wrapper, or reached only through a bound `emit`, left the lock
held by a thread that does not exist, and the child's first event through it blocked. Every live
`SinkCounters` is now repaired in the child, wherever it is held.

### Configuring a sink, and forking, run none of your sink's own code (SPEC-079)

`configure(sink=...)` and the fork repair used to read your sink through ordinary attribute access
and `isinstance`, which ran its `__class__` property, `__getattribute__` and its metaclass's
`__hash__` and `__eq__`. They now read every attribute statically, so none of that code runs. The
sink you pass is still recorded as this process's whatever it looks like, so a `weakref.proxy`, a
`super(...)` object or a `__getattr__` proxy passed as `sink=` is closed by the process that
configured it and refused its close in a forked child, as any other sink is.

### `configure(sink=...)` and the wrapper sinks refuse a value that can never be a sink (SPEC-079)

`configure(sink=object())`, or a `str`, a number, a list or a dict passed as `sink=`, used to be
accepted. Every batch was then lost on the drain thread, counted in `failed_batches` and announced,
with `flush()` falsy. `FilteringSink(object())`, `TransformSink(object(), fn)` and
`MultiSink(..., object())` constructed and then failed every `emit`. Each now raises `TypeError`
where it is written, naming the argument and the type, and `configure()` leaves the configuration
as it was. Of the values themselves, only one that can never gain an `emit` is refused, and nothing of it runs. A sink
with no `close` is still accepted, as is any object of your own, a proxy, or a sink that is given
its `emit` after `configure()`. If such an object never gains an `emit`, its batches are still lost
counted and announced, as before.

### A sink that contains itself is refused instead of recursing

A `MultiSink`, `FilteringSink` or `TransformSink` that reached itself, directly or through another
of them, was accepted, and then recursed until Python's recursion limit: one `emit` on a
`MultiSink` holding itself and a `MemorySink` wrote the batch to the `MemorySink` 998 times, and
every `flush()` raised `RecursionError`. Such a graph can be built without touching a private
attribute, by calling `__init__` again on an existing wrapper or by a subclass passing `self` to
its base. Now the wrapper's constructor raises `ValueError` naming the argument, before it stores
anything; `configure(sink=...)` raises the same for a graph holding such a loop and leaves the
configuration as it was; and a `sink_factory=` that returns one — for example by wrapping
`get_config().sink` — fails that build, announced and counted like a factory that raises. A
`weakref.proxy` pointing back at a wrapper on the loop is caught too. Only the library's own
wrappers are followed, so a sink of yours that keeps a reference to its parent is never refused, nor
is a cooperative mixin that hands a wrapper `super(Wrapper, self)` resolving to your own `emit`;
a loop that runs through your own sink's code is not detected.

### `shutdown()` in a forked child cuts short your sink's backoff when no worker runs

A sink of yours that backs off on `log_foundry_stop_signal`, in its `emit` or its own `flush`, is
handed the process's stop signal when logs with no span open reach it and no worker runs. A forked
child kept the parent's signal, because the sink had already been handed one, so the child's
`shutdown()` set a signal the sink was not waiting on, and a thread inside that backoff served all
of it. The child's first such log, or its first `flush()`, now hands every sink the child still
owes a close the child's own signal, in a grandchild too, so `shutdown()` cuts the wait short as it
does in an unforked process. A child forked after the parent's worker was shut down had the same
defect and is fixed too, as is a sink inside `MultiSink`, `FilteringSink` or `TransformSink`. A
child whose worker is still delivering, and a sink built by `sink_factory=`, already behaved this
way.

### Two `configure(sink=...)` calls at once no longer close a sink twice

With a background worker running, two threads passing `sink=` (or `sink_factory=`) to `configure()`
at the same moment could close one of the sinks twice with nothing written to it in between, and
could leave `get_config()` naming one sink while events went to the other. Such calls now run one
after the other: whichever runs second wins both the configuration and delivery, and every sink is
closed once. The second call waits for the first, and that wait comes out of its own swap budget
(`DEFAULT_SWAP_TIMEOUT`, 5 s), so neither call takes longer than it did before. If the wait runs out,
which is common when the sink being drained is slow enough to use most of the budget, the second
call proceeds anyway, alongside the first, and says in one line on stderr that the two were not
serialized, rather than hang or drop your configuration; its own drain then has no budget left, so
it is counted in `health().incomplete_swaps` and the sink it replaced is closed at exit. A
`configure()` that changes no sink or factory, and logging itself, take no part in this and never
wait. A `configure(sink=...)` made by a sink's own code from inside the library, such as from its
`close()` or `emit()`, does not wait either: it swaps at once, leaves the sink it replaced to be
closed at exit, and says so on stderr, where it used to be able to close a sink twice. A span finishing on another thread during a swap may still land on either
sink.

### A `shutdown()` during a `configure(sink=...)` closes each sink once and leaves none open

With a background worker running, a `shutdown()` (or the exit drain) landing while another thread's
`configure(sink=B)` was switching delivery from A to B could close A twice, and could return with B
open although events had already been delivered to it. A `shutdown()` now waits for a sink change
already in flight to take effect before it drains, so B is closed by that call, and A is closed
once whichever of the two reaches it first. The wait comes out of the call's closer grace
(`DEFAULT_CLOSER_GRACE`, 2 s), never out of the drain's share of the budget, and an uncontended
`shutdown()` does not wait at all. If the sink change has not taken effect within the grace, the
call goes on without it, and A is still closed once; if the change still has not taken effect by
the time the call has finished collecting the sinks it closes, it says in one line on stderr that
the sink it installs may be left open until the process exits. A `shutdown()` made by a sink's own code from
inside the library, such as from its `emit()` or its stop-signal setter, never waits on the change
it is part of.

### A sink whose stop-signal setter calls back into the library no longer hangs it

The library assigns `log_foundry_stop_signal` with a plain attribute assignment, and a sink may
make that a property whose setter runs code. A setter that called `configure()`, `info()`,
`flush()` or `shutdown()`, or ran a `@trace`d function, hung the whole process, because the
library made the assignment while holding one of its own locks: on the first log with no span, a
`flush()` after a fork, a `configure(sink=...)` with no background worker, the first `@trace`
call, a `flush()` that built the worker for an open span, and the first event through
`configure(sink_factory=...)`. The assignment now runs with none of the library's locks held that
such a call would wait on, so those calls return; a `configure()` from a setter during a
`configure(sink=...)` swap is still the re-entrant kind, which swaps without waiting and says so. Three consequences you can see:

- The setter can run more than once for one signal, from more than one thread at the same moment,
  so make it tolerate that.
- A setter that swaps the sink or shuts down while a log is being delivered closes the sink that
  log then writes to. That sink is now closed again at exit, as any sink written to after its close
  is.
- With `sink_factory=`, a `configure(sink=...)` that replaces the wrapper while its first sink is
  being built, from that sink's setter or from another thread while the factory is still running,
  now leaves the built sink closed at exit, also when the wrapper sits inside a `MultiSink` or
  `FilteringSink`. It used to be written to and closed by nobody.

Three more corrections to how the signal is handed:

- A `@trace`d call made while `shutdown()` is closing your sink no longer holds that shutdown for
  your sink's whole backoff: the sink keeps the signal the shutdown set until its close is over,
  and is then handed the new worker's. A `shutdown(timeout=1)` measured 4 s against a 4 s backoff
  before.
- A `shutdown()` on another thread no longer waits out a slow stop-signal setter during a
  `configure(sink=...)` made while no background worker is delivering — before anything was
  traced, or after an earlier `shutdown()` retired the worker — and no longer writes the line
  saying the sink change could not take effect; it can now close that sink while the setter is
  still running.
- A `configure(sink=...)` whose new sink's setter calls `shutdown()` no longer counts
  `health().incomplete_swaps` or writes the "could not be confirmed drained ... left open" line
  for a sink that shutdown had already closed.

### A forked child no longer crashes on the `SQLiteSink` it inherited

A process that configured `SQLiteSink`, logged and then forked handed the child its SQLite
connection, and a SQLite connection cannot cross a fork. On macOS the child died of `SIGSEGV` on
its first log, and also at its exit when it never logged at all; on Linux its rows went into the
parent's database through that shared connection. Now the child refuses: every event it sends to
the inherited sink is lost, counted (`health().orphan_lost`, a batch the worker abandons, or
`health().sink` when the sink sits inside a `MultiSink`) and announced on stderr, and the sink's
`emit` raises `SinkDeliveryError` naming the forked child. The worker abandons each refused batch
at its first attempt rather than retrying it (see *Changed*).
`close()` in the child returns without touching the connection, and the connection is kept open
until the child exits rather than freed. On Linux a child that should log to SQLite builds its own
sink, with `configure(sink_factory=...)` or a `configure(sink=SQLiteSink(...))` after the fork. On
macOS that is not safe either: once the parent has used SQLite, Apple's SQLite library can crash a
forked child that opens any connection of its own, so there the child logs to another sink.

### A `sink_factory` that calls back into the library no longer hangs it

The library called your `sink_factory` while holding a lock of its own. A factory that ran a
`@trace`d function and then called `flush()`, `shutdown()` or `configure(sink=...)` hung the
process with no timeout, or stalled for the call's whole timeout with one, because the background
worker it waited on was itself waiting for that lock. The factory now runs with none of the
library's locks held, and these calls return. Two consequences you can see:

- While your factory is inside one of those three calls, an event on another thread that needs the
  sink being built is not delivered: the background worker retries it and then counts it in
  `failed_batches`, and a log with no span counts it in `orphan_lost`, with a line on stderr either
  way. An event that only meets a factory that is taking its time waits for it and is delivered,
  as before.
- A factory that starts a thread of its own which logs, and waits for that thread with no timeout,
  still hangs: the thread's first event waits for the very build the factory is running.

### Superseded sinks are collected, and a long-lived process's children no longer trip the marking (SPEC-081)

The library kept every sink you ever passed to `configure(sink=...)` alive for the life of the
process, so a process that reconfigured repeatedly grew without bound: about 90 KiB for each
superseded `MemorySink` holding 100 events. A child forked from such a process after about 500
reconfigures also hit the ceiling on the objects its fork repair reads, and wrote a line saying so.
The library now holds a sink only while it still delivers to it, owes it a close or is closing it,
so a superseded sink is freed once your code drops it, and a child no longer walks the closed
library sinks a parent left behind. A sink whose class cannot be weakly referenced, such as one
declaring `__slots__` without `__weakref__`, is still kept, as before.

### A forked child whose marking trips no longer closes a parent's sink it hands over again (SPEC-081)

A child whose fork repair hit that ceiling refused to close an inherited sink it had no record of,
unless the child passed that sink to `configure(sink=...)` again, bare or inside a `MultiSink` or
`FilteringSink`, in which case its `shutdown()` closed the parent's transport. Such a child now
marks every sink on its inherited heap as one it did not open, refuses to close each, and writes
one line saying so. A sink it builds itself after the fork is still closed. If the child cannot
read its heap, because the scan fails or because the parent called `gc.freeze()`, or if its fork
repair itself fails, it writes one line when it is forked saying it cannot tell what it inherited.
It then closes only the sinks the library builds for it, the lazy default and a `sink_factory=`
sink, and writes a further line the first time it refuses a `configure(sink=...)`; configure
`sink_factory=` there so each process builds a sink of its own. When the heap scan failed or the
heap was frozen, an inherited sink that took over its own transport in the child (a `FileSink`,
whose `reacquire_after_fork` returned) is still closed by the child; when the repair itself
failed, it is not.

## Changed

### A sink retries the failures that can pass, and gives up at once on the rest (SPEC-070, SPEC-072, SPEC-074)

The eleven sinks that call a vendor SDK or driver (`SQSSink`, `SNSSink`, `KinesisSink`, `FirehoseSink`,
`ClickHouseSink`, `MongoDBSink`, both Redis sinks, `RabbitMQSink`, `AzureEventHubsSink` and
`PostgresSink`) used to retry **any** exception, so a `TypeError` from your own code, a validation
error or a constraint your data breaks cost the sink's attempts, their backoff and then the worker's
whole-batch resends before it was counted. Each now retries only the exception classes its driver
documents as transient (a dropped connection, a timeout, a throttle, a server-side `5xx`), plus the
builtin `ConnectionError` and `TimeoutError`, and fails at once on anything else: **one sink
attempt per `emit`** with no backoff wait (SPEC-070), counted in `health().sink.failed` and
announced on stderr in one line of the form `<Sink>, 1 attempt(s), <Type>`
(`AzureEventHubsSink, one batch, 1 attempt(s), <Type>` for Event Hubs); once SPEC-072's
verdict and delivery engine reach these sinks, which SPEC-074 does, it is **one attempt in total**,
the worker no longer resending it. A subclass of yours that overrides `emit` keeps the worker's
resend of a batch that raised, so there a failure that fails at once costs one call per worker
attempt rather than `max_retries + 1`. That line used to name the full retry count, `max_retries + 1`,
whatever was made, and six of these sinks (`ClickHouseSink`, `AzureEventHubsSink`, `MongoDBSink`,
`PostgresSink`, `RabbitMQSink` and both Redis sinks) wrote it as `N attempts`; every one now writes
`N attempt(s)` with the attempts actually made. The four AWS sinks' line for entries the service
kept failing, `still failing after N attempts; abandoned`, now reads `attempt(s)` too. A `PostgresSink` whose reconnect is refused by the
server (a wrong password, an unknown user or role, or a database that does not exist) also gives up at once; a
refused port, a server still starting up or one with too many clients is retried as before. psycopg
gives such a failure no error code, so the refusal is recognised from libpq's English message, and a
server whose `lc_messages` is set to another language keeps today's retry. The reconnect's
once-per-outage line used to read `absorbed a failure while PostgresSink.reconnect (<Type>)`; the
failure is no longer absorbed, so it now reads `PostgresSink could not reconnect (<Type>); this attempt fails, and a lost line follows only if the batch is given up`, and the attempt fails with the
connect's own error, where it used to go on and fail on the closed connection.

`HTTPSink`-based sinks and the socket transport (`SyslogSink`, `LogstashSink`'s TCP and UDP modes)
still retry transport errors only; an exception of any other kind used to escape `emit` raw with
nothing counted, and is now counted and abandoned at once like the rest — for the HTTP sinks with
the line an exhausted connection error already wrote, `lost 1 request(s); <Sink>, 1 attempt(s),
connection error, <Type>`, and then `SinkDeliveryError` if nothing landed. That includes the
`OverflowError` an `HTTPSink` `timeout` too large for a socket raises on every call. `SentrySink` keeps counting such an
exception on `.transport_errors`, as before. An injected client from a different library
than the one named (a Redis-compatible client that raises its own `ConnectionError` class, say) is
retried only if it raises the builtin `ConnectionError` or `TimeoutError` or the named driver's
class; anything else fails on the first attempt. `NATSSink` declares no such set and keeps its
1.1.0 retry: a batch in which nothing was published, because every publish raised or because the
sink could not reach its server before the first, is still resent by the worker, and one in which
something was published is not.

### `SNSSink` stops retrying entries SNS rejects as a sender fault (SPEC-070)

SNS marks each entry it rejects in a `PublishBatch` reply with `SenderFault`, the same field SQS
uses. `SQSSink` already treated a sender fault as permanent; `SNSSink` retried every failed entry.
It now sends a sender-fault entry once, counts it in `failed`, writes `SNSSink, rejected as invalid
(first code: <Code>); not retried` on stderr as `SQSSink` does, and resends only the entries SNS
failed for its own reasons. A batch rejected
entirely as sender faults returns rather than raising, as the SQS equivalent does. Kinesis and
Firehose keep retrying every failed record: every per-record code the vendors document for them is
transient, and a code they do not document is retried too, within the retry budget.

### The HTTP sinks resend only what can still land (SPEC-073)

`HTTPSink` and every sink built on it — `DatadogSink`, `ElasticsearchSink`, `OpenSearchSink`,
`HoneycombSink`, `LokiSink`, `NewRelicSink`, `OTLPSink` and `SplunkHECSink` — now offer `deliver`
(HTTP-mode `LogstashSink` follows through SPEC-075, below), so the worker and the no-span logging path run one retry loop,
within SPEC-072's budget; `max_retry_after` and the `Retry-After` clamp are as before. What changes
is what each retry carries:

- **Only the failed chunks are resent.** A `503` or a dropped connection on one chunk resends that
  chunk's events alone; chunks that landed are no longer sent again, which used to duplicate them. A
  batch whose several chunks failed waits once per round, not once per chunk, and during
  `shutdown()` a round predicted to end past the deadline is declined.
- **A chunk refused for good is sent once** — a `4xx`, an Elasticsearch item error, a Honeycomb
  per-event rejection, an OTLP rejected record. Before, the worker re-POSTed it once per retry when
  nothing else in the batch landed: four POSTs at the defaults of a batch that could never land. It
  is still counted in `failed_batches`, and `flush()` is still falsy.
- **`emit`'s total-failure message counts events.** A direct `emit` that delivers nothing still
  raises `SinkDeliveryError`, now with the delivery engine's message, `delivered none of 3 event(s):
  rejected 3, unresolved 0, raised 0 after 1 delivery round(s) to HTTPSink`, where 1.1.0 wrote
  `HTTPSink delivered none of 3 chunk(s)`. Code matching the old text needs to match the new.

`SentrySink`'s HTTP fallback has no `deliver` in this release and is unchanged. A subclass you wrote
that overrides `emit`, or whose `_handle_response` returns a bool and defines no `_outcomes` below
it, is not offered `deliver` and keeps its 1.1.0 path: the worker and the no-span path call its
`emit`, which still chunks, retries within `max_retries`, searches after a `413` and raises when
nothing landed, and the worker resends that raise whole. Two things change for it all the same.
A hook of yours that raises costs only its chunk (below), and a `_handle_response` returning
`False` beside a chunk that landed now gets one more stderr line, `lost N event(s); <YourSink>,
refused for good; not retried`, since your override registers no line of its own and the loss
would otherwise be silent. A `_handle_response` of yours that returns a shipped reader's answer
through `super()` keeps that reader's own line, as in 1.1.0, and gains none. A subclass that also defines `_outcomes`, the per-event hook the shipped
readers now use, is offered `deliver`. A subclass that overrides `_send` still sees `SentrySink`'s
calls, but no longer sees the batch's chunks. An `_items` override that returns its events
rebuilt (enriched or copied), one per event and in order, is delivered as before; one that leaves
an event out without counting it now has that event counted as rejected and announced, in
`log_foundry_counters` and toward a failed batch if nothing else landed, where 1.1.0 left it
unsent and uncounted. `HTTPSink._handle_response`'s signature is unchanged.

### The SDK and driver sinks resend only what failed (SPEC-074)

`SQSSink`, `SNSSink`, `KinesisSink`, `FirehoseSink`, `ClickHouseSink`, `MongoDBSink`,
`PostgresSink`, both Redis sinks, `RabbitMQSink`, `AzureEventHubsSink`, `NATSSink` and `SyslogSink`
now report what happened to each event, and the engine resends only the events that can still land,
within SPEC-072's budget. Each gains `deliver(batch)` and `log_foundry_counters`, and `RabbitMQSink`
and `SyslogSink` gain a read-only `max_retries`. Socket-mode `LogstashSink` sends through the same
engine from its `emit`.

- **A batch is no longer resent whole.** Chunks that landed are not sent again, and a chunk that
  keeps failing beside chunks that landed is retried for as long as a wholly failing batch would be.
- **Order within a batch.** A message, frame or chunk that failed is resent after the later ones of
  its batch, where it used to be retried before the next was sent. An SQS FIFO message group keeps
  its order: a message waits while an earlier one of its group is being retried, for that one's
  `max_retries + 1` sends, and the delivery's last round holds nothing, so a waiting message is sent
  right after the earlier one's final send, as before. A delivery the worker ends early, or a direct
  `deliver()` call, can leave one unsent, counted in `.failed` with the line `0 attempt(s), held behind an earlier message of its
  FIFO group`.
- **The exception a failed `emit` raises** is the engine's `SinkDeliveryError`, reading `delivered
  none of N event(s): …`, where each sink used to raise its own text (`inserted none of …`,
  `published none of …`), as the HTTP family's already does. A refusal — a closed sink, a `NATSSink`
  that is stuck or refused, a batch that produced nothing to send — still raises its 1.1.0 error.
- **A `close()` during a retry wait returns at once** for `ClickHouseSink`, `PostgresSink`,
  `RabbitMQSink`, `AzureEventHubsSink`, `SyslogSink` and socket-mode `LogstashSink`, where it used to
  wait for the retries to finish; the rest of that batch is refused.
- **The stderr line for an exhausted retry** now comes from the sink once per batch, naming how many
  times those events were sent and the exception type, beside the worker's `batch abandoned` line.

`KafkaSink`, `GooglePubSubSink`, `MultiSink` and the file, stdout and SQLite sinks offer no
`deliver` and keep their 1.1.0 retry behaviour.

### `FilteringSink`, `TransformSink` and `LogstashSink` pass the verdict through (SPEC-075)

When the sink you wrap offers `deliver` — the HTTP family and the SDK and driver sinks above, but not
`KafkaSink`, `GooglePubSubSink` or `SentrySink` — `FilteringSink`, `TransformSink` and `LogstashSink`
(HTTP and socket mode) offer it too, and report their inner sink's losses exactly as that sink
reports them alone. The worker and the no-span logging path then run one retry loop, with the
wrapped sink's own `max_retries` and `max_retry_after`, resending only the events that can still
land. Before, the worker's whole-batch loop ran around the wrapped sink's own loop, nested; the
total number of attempts is the same, `(2 + 1) × (3 + 1)` for an inner `max_retries=2` under the
default worker, but there is now one loop, and the exit drain's shutdown prediction sees every
attempt. An event your filter declines, or that your transform maps to `None`, is reported as
`Outcome.SKIPPED` and counted nowhere, as before. The one exception is a delivery attempt in
which the wrapped sink's `deliver` raises: that attempt's events, declined ones included, are
counted in the wrapped sink's `log_foundry_counters.failed_events` (which is its
`health().sink.failed` for the SDK and driver sinks; the HTTP family's `failed` counts requests),
the upper bound `failed` has always been. A wrapper over a sink without `deliver`, every
wrapper's own `emit` and a third-party wrapper that calls `emit` behave exactly as in 1.1.0.
`MultiSink` is unchanged: it calls each child's `emit`, so a child on the new engine retries inside
one fan-out call.

- **New read-only attributes.** The three classes gain public `max_retries` and `max_retry_after`,
  copied from the wrapped sink (from the backend, on `LogstashSink`) when the wrapper is built, as
  the delivery engine reads them, or `None` when it offers no `deliver` or the wrapped sink
  declares none. Assigning either raises `AttributeError` (`max_retries is read-only; it is copied
  from the wrapped sink`). **A subclass of yours that assigns `self.max_retries` or
  `self.max_retry_after`, in its `__init__` or anywhere else, now raises.** Set the budget on the
  wrapped sink instead.
- **A transform runs once per event per delivery.** Over a sink that offers `deliver`,
  `TransformSink` keeps each event's result for the whole delivery and forwards that same object on
  every retry. Before, the worker's whole-batch resend ran your function again on every attempt, so
  a function with side effects, or one returning something different each call, now sees fewer
  calls. A deterministic function sees no difference beyond that.
- **A predicate is asked once per forwarded event per delivery.** Over a sink that offers
  `deliver`, `FilteringSink` remembers each event it forwarded for the whole delivery, and a retry
  sends that event again without asking your predicate or the level floor a second time. Before,
  the worker's whole-batch resend asked again on every attempt. A predicate that keeps state, one
  that drops duplicates, limits a rate or samples, therefore sees fewer calls and can no longer
  decline its own retry and lose the event. A predicate that is a pure function of the event sees
  no difference.
- **A new stderr line when your code raises.** Over a sink that offers `deliver`, a predicate or
  function that raises makes the wrapper write `log-foundry: absorbed a failure while filtering a
  batch (<Type>); FilteringSink did not forward N event(s) its predicate failed on` (`transforming
  a batch` and `its function failed on` for `TransformSink`), at once, naming the type and never the
  message. Your code runs only in the first attempt that sees an event, since a retry reuses what
  the wrapper decided, so the line is written once per delivery. It takes the place of the `lost N event(s); FilteringSink, the
  predicate raised <Type>` line (`TransformSink, the transform failed with <Type>`) that the `emit`
  path still writes.
- **A direct `deliver()` call is one attempt.** Calling a sink's `deliver` yourself, outside the
  library's delivery, is a single attempt with no memory of earlier calls, so a loop of your own
  sees the sink's still-failing or held line on every call and an `SQSSink` FIFO hold is never
  released. Call `emit_via_deliver(sink, batch)` to get the retries. This is documentation only,
  on `Sink.deliver`; nothing about the call changed.

### Counts that move on the engine (SPEC-073, SPEC-074, SPEC-075, SPEC-076)

Every loss is still counted, in a documented term. These move:

- **A total failure is counted once per batch, not once per worker attempt.** For the HTTP family
  that covers `.failed` (abandoned requests), `.item_errors`, `.rejected_events` and
  `.rejected_records`: an outage that exhausts every attempt counts one `failed` per abandoned
  request where 1.1.0 counted one per worker attempt (4 at the defaults), and its stderr line names
  the attempts actually made (`16 attempt(s)`). For the SDK and driver sinks `.failed` counts each
  lost event once: a dead Redis with `max_retries=3` under a worker with `max_retries=2` is still
  called 12 times for one batch, and `health().sink.failed` reads 5 for its 5 events, not 15.
  `NATSSink` is the exception: it counts as it did in 1.1.0, once per raised publish per call.
  A run that settles while ending on a round in which `NATSSink` published nothing — an idempotent
  delegate resending an `UNKNOWN` after an earlier accept, or a wrapper of yours accepting part of
  the batch itself — now counts and announces that round's unattempted events (`NATSSink
  publish_timeout …`), where nothing counted or named them. A wrapper of yours that settles some
  of its own events as lost in a round where the `NATSSink` it wraps published nothing now gets the
  engine's line for those losses beside the NATS line, where the NATS line used to silence it.
  Socket-mode `LogstashSink` joins them through SPEC-075: against a peer that refuses every connect,
  2 events under the default worker read `failed == 2`, where it counted them once per worker
  attempt (`8`).
  `failed` was always an upper bound; it is a tighter one now.
- **A lone event refused with a `413`**, in a batch whose other chunks all failed, is no longer
  counted in `dropped`. The batch fails, and the event is counted with it in `failed_batches` (or
  `orphan_lost`), as an event over the per-event size limit already was.
- **An HTTP subclass whose `_body`, `_prepare` or `_apply_auth` raises**, or whose request cannot
  be built, no longer makes `emit` raise and the worker resend the batch. That chunk is counted in
  `dropped`, and the rest of the batch is still sent; one line per delivery round names the first
  exception's type, `lost N event(s); <Sink>, rendering raised <Type>`, as a render failure's does.
  A batch whose every chunk fails this way returns with `flush()` truthy and `failed_batches` at 0.
- **A `_handle_response` that raises** costs only its chunk, counted on `.dropped_unadjudicated`
  (inside `failed`) and never resent, with the line `lost N event(s); <Sink> reading a 2xx response
  raised <Type>; they may have landed; not retried`. Before, it escaped `emit` and the worker resent
  chunks that had landed. `HTTPSink` itself gains `.dropped_unadjudicated`, which is 0 unless that
  happens.
- **Any other private HTTP hook of yours that raises** — `_retryable_status`, `_items`, `_take`,
  `_event_ceiling`, `_chunk_budget`, `_drop_refused`, `_abandon_unreduced`, or any other method the
  delivery round calls — now reports partial delivery instead of total failure: it costs only the
  chunk it was handling, and every other chunk keeps its outcome. A fault before that chunk's
  request was sent counts it in `dropped`, with the `rendering raised <Type>` line above; a fault
  after the request was sent counts it on `.dropped_unadjudicated` with the line `lost N event(s);
  <Sink> handling its response raised <Type>; they may have landed; not retried`, and it is not
  resent unless your sink declares `log_foundry_idempotent = True`. A raise from `_chunk_budget` or
  `_items` costs the whole round, in `dropped`. A raise from `_attempt`, from the
  `_response_limit` it reads or from `_retryable_error` is the attempt's own failure, as before:
  `failed`, with a `connection error, <Type>` line. Before, the other faults escaped the round,
  `emit` raised, and the batch was reported undelivered even when some of its chunks had landed.
  Whatever the hook counted before it raised is discarded, so the loss is counted once. A
  `KeyboardInterrupt` or other `BaseException` still propagates.
- **An event your `_items` override leaves out without counting it** is announced on its own line,
  `lost N event(s); <Sink>, _items returned no item for them; not retried`, when the batch
  settles. Before, its only announcement was the delivery engine's summary line, which is not
  written when the sink writes a line of its own, so beside any other loss in the batch it showed
  only in `log_foundry_counters`. The same holds now for any loss your `_outcomes` or
  `_abandon_unreduced` reports without a line: the round writes `lost N event(s); <Sink>, refused
  for good; not retried`, or `lost N event(s); <Sink>, outcome unknown; they may have landed` for
  an unknown one.
- **An SQS or SNS `Failed` list, or a MongoDB `writeErrors` list, that the sink cannot read** is
  counted in `health().sink.failed` and never resent, as a Kinesis or Firehose positional result it
  cannot read already was, on `.dropped_unadjudicated`. A malformed SQS or SNS reply used to escape
  `emit` as a raw exception, and a MongoDB `writeErrors` list was counted by its length alone.
- **A refused batch** — a closed sink, or `NATSSink` with no answer from its server — moves
  `failed_batches` or `orphan_lost`, never `health().sink.failed`, unless an earlier attempt at the
  same batch had already landed part of it: that batch settles, no catcher counts it, and its refused
  events are counted once in `health().sink.failed` with one line.
- **Through a wrapper on the engine**, a filter or transform that declines events no longer stops a
  batch from counting as failed when everything it was asked to deliver was refused. An event your
  predicate or function raises on beside delivered siblings is still counted in
  `health().sink.dropped`.
- **When your own code raises on every event of a batch** — a `FilteringSink` predicate or a
  `TransformSink` function over a sink that offers `deliver`, or every `SQSSink` FIFO
  `message_group_id` or `message_deduplication_id` callable — the batch is tried once and **no longer
  retried**: before, the worker re-ran your code on each of its retries. It still fails
  (`failed_batches` or `orphan_lost`, `flush()` falsy), no sink counter moves, and a direct `emit`
  still re-raises your first exception unchanged. A wrapper names the exception's type on stderr in
  an `absorbed` line. A wrapper over a sink without `deliver` keeps the 1.1.0 retry.
- **Under `MultiSink`**, a new-engine child's failed events are counted both by the child and in the fan-out's
  absorbed count, the upper bound `failed` has always been.
- **Counts land when the delivery ends**, not as each request finishes, and a family sink's stderr
  lines for one batch are written together, in order, after the counts. For the HTTP family that
  covers `.failed`, `.item_errors`, `.rejected_events`, `.rejected_records` and
  `.dropped_unadjudicated`; `dropped` already landed only when `emit` returned. A
  `KeyboardInterrupt` or other `BaseException` raised in the middle of a delivery now discards the
  counts and lines of that delivery, where 1.1.0 had already made those of the requests before it.

### A closing sink refuses new calls at once and waits only for the ones already inside (SPEC-076)

`ClickHouseSink`, `PostgresSink`, `AzureEventHubsSink`, `RabbitMQSink`, `FileSink`,
`RotatingFileSink`, `SQLiteSink`, `MongoDBSink`, both Redis sinks, `KafkaSink`, and `SyslogSink` and
`LogstashSink` in TCP or UDP mode (through their socket transport) now share one rule for closing:

- **From the moment `close()` is called, a new `emit` is refused**, and so is a `KafkaSink.flush()`,
  including a call already waiting for the sink's lock. Before, a call that won the lock first could still write before the close took
  effect. A `close()` on a sink that serialises its writes waits for at most the one call inside, not
  for every caller queued behind it.
- **`MongoDBSink`, the Redis sinks and `KafkaSink`** used to release their client without waiting
  for a call in progress on another thread. Now `close()` waits up to 0.5 s for such calls to
  finish, then releases the client. A call still inside after that meets the released client:
  `MongoDBSink` counts its events in `health().sink.failed`, a Redis batch fails into
  `failed_batches` or `orphan_lost`, and `KafkaSink` counts as *Fixed* describes. This wait is
  inside `shutdown(timeout=...)`'s inline close too, so a shutdown can overrun its timeout by up to
  0.5 s when an application thread is inside one of these sinks' calls: measured, `timeout=0.1`
  returned after 0.51 s, where `c810333d` returned at once and lost the Kafka message uncounted.
- **A second `close()` on a syslog or Logstash socket** is a no-op, like every other sink's.
- **The private `_closed`, `_lock` and `_close_lock` on these sinks are now read-only properties.**
  A subclass that reads them keeps working: `_closed` is the sink's closed state, and `_lock`
  (`_close_lock` on `MongoDBSink`, the Redis sinks and `KafkaSink`) is the lock the sink's close
  holds, so `with self._lock:` in a subclass of a sink that serialises its writes still holds them
  off. A subclass that assigns one, including in its own `__init__`, gets `AttributeError`.
  `_closed` now reads true from the moment `close()` is called, while the close may still be
  waiting for a call inside; before, it turned true only once the close held the sink's lock.

`emit` after `close()` still raises `SinkDeliveryError` with the same message, and its counting is
the refused-batch rule above. Sinks that release nothing on `close()`, such as the HTTP family, SQS,
SNS, Kinesis, Firehose and stdout, still accept events after it.

### A sink that refuses for good is not retried

A batch the background worker sent to a sink that is closed or closing, or to the `SQLiteSink` a
forked child inherited, used to be resent `max_retries` times with a backoff wait
between, though no resend could succeed: a forked child running 2000 `@trace` calls took 17.3 s to
`flush()`, measured at `2ff9de9e`. Now the worker gives such a batch up at the attempt that raised it. It is counted in
`failed_batches` once, as before, and the stderr line names the attempts actually made:
`batch abandoned after 1 emit attempts`, where it read `after 4`. This covers `SQLiteSink`,
`FileSink`, `RotatingFileSink`, `KafkaSink` and `GooglePubSubSink`, and, inside a `MultiSink`, the
sinks that refuse after `close()` listed under *A closing sink refuses new calls at once* above, and
the forked child's `NATSSink`. The error each raises is unchanged:
exactly `SinkDeliveryError`, with the same message. A sink of your own keeps the resend whatever it
raises, including a library sink's refusal that reaches the worker through it, whether your sink
raises it again, forwards `emit` to the library sink, or hands the batch to it from a
`CallbackSink` callable, so a sink that swaps in a fresh destination still gets its retry. A library wrapper (`MultiSink`, `TransformSink`,
`FilteringSink`) around a sink of your own keeps the resend the same way. A `MultiSink` whose children all failed re-raises the first child's error unless that one
refused for good and another child's failure might pass on a retry, in which case it re-raises that
child's, so the worker still retries the batch for it.

### A missing optional extra says which extra to install, and the injected-client refusals share one tail (SPEC-071)

Constructing a sink whose client is not installed used to raise the interpreter's own
`ModuleNotFoundError: No module named 'boto3'`. It now raises a `ModuleNotFoundError` whose message
names the extra and the command, for example `The "aws" extra is not installed (No module named
'boto3'): pip install "log-foundry[aws]"`. It is a private subclass of `ModuleNotFoundError`, and so
still an `ImportError`; `.name` is still the missing module, and an `except` clause written against
either keeps matching.
A client that is installed but fails to import for another reason raises exactly what it did.

Every refusal of an option beside an injected client now reads `<Sink> cannot apply <names> to an
injected <kind>; pass them where the <kind> is built, or drop <kind>=`, with `<kind>` one of
`client`, `producer` or `connection` and the names sorted. The five existing ones keep the prefix
they had, and only their tail changed. **A program matching the old tail (`already built`,
`already connected`) needs to match the prefix instead.**

### `shutdown()`'s docstring describes logging after it accurately (SPEC-078)

The behaviour has not changed; only the documentation is corrected. A `@trace` call after a
`shutdown()` that never started a background worker starts a fresh one and is delivered. After a
`shutdown()` that stopped a worker, the same call is counted in `health().submitted_after_shutdown`
and announced. A level call outside a span still reaches the configured sink. The docstring said
every later event was queued where nothing would drain it.

## What did not change

`emit` still raises `SinkDeliveryError` when nothing landed and returns otherwise, so code calling
`emit` directly, and a wrapper calling `inner.emit`, sees what it saw; only an HTTP sink's message
changed (*Changed*). `losses()`, `SinkLosses`,
`read_losses` and every documented counter keep their names and units; what moves is when and how
often some of them count, which *Changed* lists. One shipped constructor default changed:
`PostgresSink`'s `connect_timeout` is now `None`, meaning the same 5 seconds, and its type only
widens (*Fixed*); no other sink's constructor signature or default changed. The public additions
are `deliver`, `log_foundry_counters`, `log_foundry_idempotent`, the read-only `max_retries` on `RabbitMQSink` and
`SyslogSink`, the read-only `max_retries` and `max_retry_after` on `FilteringSink`, `TransformSink`
and `LogstashSink`, `HTTPSink.dropped_unadjudicated`, and `losses()` on `StdoutSink`, `StderrSink`,
`FileSink`, `RotatingFileSink` and `SQLiteSink`, and `merge_headers`'s keyword-only `owner=` and
`argument=`, the second opting in to the credential refusal. The refusals under *Fixed* reject only
configurations that were broken or outside their declared type: an argument silently ignored (a sink
given `client=` with `url=`, for instance, delivered to the injected client and never read `url`), a
non-callable where a callable is wanted, which a type-checked program never passes, or a value
that can never be a sink. The type refusals change nothing for an honest value: a value lying
about its type now gets the door's own message, and a `float` subclass claiming `int`, passed as a
duration or a `timeout`, is accepted (at an `int` door it is refused as the float it is). No sink's wire format
changed, apart from the repaired values `PostgresSink` and `MongoDBSink` now deliver, the PROCID
a forked child's `SyslogSink` stamps, and the HTTP headers and bodies *Fixed* says are now sent (a
non-`dict` `headers=` on the four platform sinks, a body compressed under a gzip `Content-Encoding`
in any case), and the SQS chunk boundaries are what they were. `KafkaSink`, `GooglePubSubSink`, `SentrySink`, `MultiSink`,
the file, stdout and SQLite sinks keep their 1.1.0 retry behaviour. The core still has no runtime
dependency.

The library's lifecycle bookkeeping moved to one private home (SPEC-077); no public name, signature,
default or behaviour moved with it.
