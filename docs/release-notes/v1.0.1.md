**No library code changed.** `1.0.1` carries no behaviour change at all — upgrading from `1.0.0`
is a no-op for anything your code does. If you already pinned `1.0.0`, there is no reason to move
off it; if you install fresh, you get the same library either way. `git diff v1.0.0..v1.0.1 --
src/` is empty, and that is the whole of the compatibility story.

This release exists to refresh the PyPI project page, which PyPI only regenerates when a new
version is published. Two pull requests improved the README after the `v1.0.0` tag was cut, so
everything they added has been sitting on `main` unreachable by anyone reading the package's own
page. `1.0.1` is what publishes them.

## What actually changed

- **The README now reads as a released `1.0.0` rather than as one being prepared.** It carries
  version, Python, build and license badges; a paragraph stating exactly what the `1.x` API freeze
  covers; a `pip install 'log-foundry>=1,<2'` example showing how to depend on that freeze; and an
  upgrade callout addressed to any `0.x` reader rather than only a `0.10.x` one, which names the
  deleted `log_foundry.sinks.util` module explicitly. It also links `CHANGELOG.md`, a version index
  that did not exist when `1.0.0` shipped.
- **The README's links are now absolute**, so they resolve on the PyPI page the same way they do on
  GitHub, and the pipeline architecture diagram renders inline instead of showing as a broken
  image. PyPI serves the README as a flat page with no repository root behind it, so every link
  written relative to the repository returned a 404 there.
- **The project now lists a `Changelog` URL** in its PyPI metadata, pointing at `CHANGELOG.md`, so
  a reader on the PyPI page has a direct link to the version history.

## One thing worth reading, if you rely on the freeze

`1.0.0`'s release body promises that everything in `log_foundry.__all__`, the `Sink` protocol and
every shipped sink class is frozen for `1.x`. That promise was **widened** after publication, and
the release body cannot be amended because releases here are immutable. No concrete sink is in
`__all__`, so "every shipped sink class" pinned nothing a caller could actually write down; the
promise now also covers the class **at its documented import path**, along with the public names
its signatures use. `README.md` and `CHANGELOG.md` state the current form, and the repository is
the authority over any release body.

That widening happened after `1.0.0` was published and has never appeared on a published page,
because the PyPI page has not been rebuilt since. `1.0.1` is the release that carries it there. It
widens the promise and narrows nothing, so it cannot break a caller who relied on the `1.0.0`
wording; it is worth knowing only because the page you read it on has changed underneath the
version you may already have pinned.

No library code moved. No sink, no public name, no signature, no default and no wire format changed
between `1.0.0` and `1.0.1` — see
[`CHANGELOG.md`](https://github.com/agriffi10/log-forge/blob/v1.0.1/CHANGELOG.md) for the full
version history, and `1.0.0`'s own notes,
[`docs/release-notes/v1.0.0.md`](https://github.com/agriffi10/log-forge/blob/v1.0.0/docs/release-notes/v1.0.0.md),
for the reliability work and the upgrade items that release carried.
